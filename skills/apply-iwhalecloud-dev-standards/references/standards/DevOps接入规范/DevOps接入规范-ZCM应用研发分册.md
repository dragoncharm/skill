# 规范目录

【强制】与【建议】说明

1. 如不遵守，将会带来严重后果的，设置为【强制】规范
2. 如不遵守，可能造成不良后果，且框架服务需要为此承担责任的，设置为【强制】规范
3. 不满足以上条件的，都设置为【建议】规范
4. 本规范为最基本的接入规范，如有规范重叠，请以各中心细化的规范为准。

# 适用对象

1、使用ZCM的人员必须了解规范，遵守条款

2、本规范描述了云原生应用的架构和开发设计原则，适应浩鲸所有的研发和设计人员，建议学习

# 目的

为确保在云原生架构下实现高效、可靠、可扩展的软件交付与运维，统一团队的技术实践与操作流程，特制定本规范。旨在通过标准化的云原生方法论，提升系统弹性与可观测性，优化资源利用率，加速交付速度，并建立可持续的研发运维协同体系，最终支撑业务的快速创新与稳定运行。

# 规范内容

## 应用通用规范

### 云原生应用通用规范

#### 应用应遵循微服务应用金科玉律

- **规则等级：** 【建议】
- **规则描述：** 创建的应用应符合golden rules相关要求
- **检查方式：** 人工检查

方案说明：微服务应用金科玉律，链接：[https://docs.iwhalecloud.com/doi/SbzW/app-dev-solutions/cloud-native-app-guidelines/micro-serv-app-gold-rules](https://docs.iwhalecloud.com/doi/SbzW/app-dev-solutions/cloud-native-app-guidelines/micro-serv-app-gold-rules)

#### 应用应符合云原生应用12要素

- **规则等级：** 【建议】
- **规则描述：** 创建的应用应符合12要素的相关要求
- **检查方式：** 人工检查

方案说明：云原生应用12要素，链接：[https://docs.iwhalecloud.com/doi/SbzW/app-dev-solutions/cloud-native-app-guidelines/cloud-native-12-ele-traits](https://docs.iwhalecloud.com/doi/SbzW/app-dev-solutions/cloud-native-app-guidelines/cloud-native-12-ele-traits)

#### 云原生应用提供的服务应满足幂等机制

- **规则等级：** 【建议】
- **规则描述：** 一个服务无论被调用一次或多次，返回的结果都是一样的；考虑到研发和维护成本，性能，复杂度，规范语义与可读性等，不强制要求所有服务都必须幂等
- **检查方式：** 人工检查
- **反例：**
  - 重大故障：菲律宾PTO DC项目，幂等逻辑设计不合理，导致服务异常
  - 重大故障：印尼金光MCCM项目，因服务接口无幂等，导致服务异常

### 应用创建规范

#### 禁止在容器本地文件系统存放需要持久化的数据

- **规则等级：** 【强制】
- **规则描述：** 持久化数据都必须映射外挂至云盘，禁止直接存放在容器目录下。容器重启会丢失数据；容器文件系统被写满会导致容器异常。
- **检查方式：** 人工检查

#### 禁止在容器本地文件系统存放超过5G的临时文件

- **规则等级：** 【强制】
- **规则描述：** 容器内部文件系统的大小在各种云平台上都有严格的限制，需要注意控制大小，避免造成故障。应用运行过程中产生不需要持久化存储的文件：包含临时产生，上传下载等存储到容器中的
- **检查方式：** 人工检查

#### 生产环境禁止使用自动更新

- **规则等级：** 【强制】
- **规则描述：** 测试环境开启自动更新，保证提交的代码能及时的更新到测试环境上进行验证。正式环境必须关闭自动更新
- **检查方式：** 人工检查

方案说明：应用自动更新

#### 对于使用Springboot基础框架的应用，建议使用Springboot内置tomcat

- **规则等级：** 【建议】
- **规则描述：** springboot内置的tomcat做了很多优化，安全性和可用性都要强于外置tomcat，建议统一迁移
- **检查方式：** 人工检查

### 配置映射规范

#### 按文件映射时，映射文件内容禁止为空

- **规则等级：** 【强制】
- **规则描述：** 将配置管理的文件映射到应用容器内指定路径中，如果文件内容为空，就会导致docker认为该文件不存在，并在宿主机上创建文件夹，导致映射错误，启动应用错误
- **检查方式：** 人工检查

#### 建议按照文件映射，不建议按照目录映射

- **规则等级：** 【建议】
- **规则描述：** 目录映射为目录覆盖方式，存在文件被意外覆盖的风险
- **检查方式：** 人工检查

### 安全（权限）配置规范

#### 禁止使用特权模式；禁止使用root等特权账户

- **规则等级：** 【强制】
- **规则描述：** 容器用户权限过高时，部分操作会对宿主机产生影响，引发安全风险；容器root用户权限过高，有安全风险
- **检查方式：** 人工检查

方案说明：特权模式使用自查

#### 配置文件中禁止存放shell脚本等可执行脚本程序

- **规则等级：** 【强制】
- **规则描述：** 配置文件以只读模式挂载到容器中，存放可执行脚本程序存在安全隐患
- **检查方式：** 工具检查(暂未实现)

### 统一日志接入规范

#### 镜像中默认$HOME/log目录，要保持为空

- **规则等级：** 【强制】
- **规则描述：** 容器启动时，容器内的docker-entrypoint.sh会首先创建/tmp/zlogs/$appname/$containerid目录；针对$HOME/log目录，建立软链接到/tmp/zlogs/$appname/$containerid目录；如果目录$HOME/log不为空，软链接会创建异常，导致容器的日志无法被日志中心采集
- **检查方式：** 人工检查

#### 生产环境必须配置日志级别为ERROR类型

- **规则等级：** 【强制】
- **规则描述：** 不合理的日志类型会导致日志积压、日志告警延时等问题
- **检查方式：** 人工检查

#### 应用产生的日志必须支持自动轮转清理机制

- **规则等级：** 【强制】
- **规则描述：** 日志必须支持自动轮转清理机制，特别是生产环境。清理策略，根据业务应用的实际情况进行设定。日志目录不要超过5G
- **检查方式：** 人工检查

### 应用启动规范

#### 建议使用镜像默认设置的应用容器启动命令

- **规则等级：** 【建议】
- **规则描述：** 建议使用镜像默认的启动命令，不要覆盖平台侧发布的基础镜像中的docker-entrypoint.sh，避免自定义启动命令。如需使用自定义启动命令，请谨慎编写，避免应用启动异常； 默认启动命令如下：

```
ENTRYPOINT ["/usr/local/bin/tini", "-g", "--", "docker-entrypoint.sh"]
CMD ["start"]
```

- **检查方式：** 工具检查(暂未实现)

方案说明：使用平台侧基础镜像中的启动命令

### 定时任务配置规范

#### 定时任务执行完成后，必须退出进程

- **规则等级：** 【强制】
- **规则描述：** 执行完程序就退出，不要作为一个常驻进程存在。如果进程不退出，会导致有大量的pod在运行，占用资源
- **检查方式：** 人工检查
- **反例：** 启动一个web服务执行定时任务

#### 定时任务应当有保护机制及快速补救机制

- **规则等级：** 【建议】
- **规则描述：** 误操作导致的重复执行或者提前执行，以及定时任务错过执行后，有手段进行补救
- **检查方式：** 人工检查

#### 任务的执行可观测，任务执行了且执行结果符合预期

- **规则等级：** 【建议】
- **规则描述：** 需要确保定时任务正确的执行了
- **检查方式：** 人工检查

### 监控指标设计规范

#### 监控指标设计应符合指标设计规范

- **规则等级：** 【强制】
- **规则描述：** 详细的设计规范请参考相关文档，正确的设计tag、field等时序数据库亲和的指标设计规范，防止异常设计带来的指标无法被正确存储和告警
- **检查方式：** 工具检查(暂未实现)

方案说明：指标设计规范，链接：[https://docs.iwhalecloud.com/doi/cgu3L9/index-design-spec](https://docs.iwhalecloud.com/doi/cgu3L9/index-design-spec)

## 配置项管理

### 系统参数发布规范

#### 配置文件必须是K-V的格式properties文件，文件编码必须是UTF-8（无BOM）

- **规则等级：** 【强制】
- **规则描述：** 配置文件必须使用标准的properties格式，文件编码必须为UTF-8（无BOM）
- **检查方式：** 工具检查(暂未实现)

#### 配置组下的配置文件总大小不可以超过1M

- **规则等级：** 【强制】
- **规则描述：** 在K8S的configmap模式下，k8s对configmap的大小有限制，不可以超过1M的大小
- **检查方式：** 工具检查(暂未实现)

#### 应用内部使用的参数必须跟随应用一起打包发布

- **规则等级：** 【强制】
- **规则描述：** 应用内部使用的参数，各个项目现场的内容会严格与代码库保持一致。适用场景包括：1）应用自身使用的内部参数场景，例如文件编码等；2）三方包或者程序使用的默认配置。规范：1）应跟随应用一起打包发布，且对外不可见；2）版本发布的时候必须定义默认值，优先级最低，可被其他配置或者环境变量覆盖；3）如果某个项目的某个参数与默认值不同，可以用"if 项目ID=环境变量 用A值， else 用 default 值。"的形式；4）不允许手工修改
- **检查方式：** 人工检查

#### 系统内部接口类的配置由ZCM统一托管

- **规则等级：** 【强制】
- **规则描述：** 系统内部接口类的配置，由ZCM统一托管，比如注入、批量更新等。
- 主要适用以下场景：
- 1）应用使用的中间件等配置项场景，例如数据库、zookeeper等；
- 2）系统内部配置，需要根据不同现场进行个性化配置的场景，项目现场个性化配置。
- 规范：
- 1）在首次部署时确定，对外可见；
- 2）允许ZCM在一键部署的时候根据项目现场的实际信息来自动改写文件；
- 3）不建议手工修改参数值，需要通过一键升级进行替换升级
- **检查方式：** 人工检查

#### 设计和开发人员在设计某一新需求的时候，建议保证配置项对原有功能的兼容

- **规则等级：** 【建议】
- **规则描述：** 兼容性原则主要目的是便于灰度发布、升级回退。这样在升级发生问题的时候，可以只回退应用，无须回退配置文件
- **检查方式：** 人工检查

#### 配置为项目环境个性化的配置，产品标准化登记中必须登记为项目现场个性化配置类型

- **规则等级：** 【强制】
- **规则描述：** zcm一键升级会基于此数据提示项目现场进行配置，配置后，一键升级
- **检查方式：** 人工检查

方案说明：项目现场环境相关的个性化配置，如三方ip地址，数据库地址，三方接口地址；项目自身个性化配置在产品标准化登记中登记发布

### 环境变量使用和命名规范

#### 环境变量命名规范

- **规则等级：** 【建议】
- **规则描述：** 1）环境变量的字母之间通过下划线来区分，比如MYSQL_IP；2）环境变量全部为大写字母；3）业务单元的私有变量，统一使用前缀，比如OCS_PROFILE_CLUSTER_IP, CRM_ACCOUNT_ID；4）环境变量名必须有一定的意义，同一个作用域下需要保证唯一
- **检查方式：** 人工检查

#### 禁止使用平台保留的环境变量

- **规则等级：** 【强制】
- **规则描述：** APP_OPTS，ZCM_EX_JAVA_OPTS，CLOUD_APP_*等 为平台保留的供内部使用的环境变量，随着平台底座K8S版本的持续迭代，值的内容和值的类型都可能发生变化，私自使用会带来较大的隐患，禁止业务应用使用
- **检查方式：** 工具检查(暂未实现)

#### 禁止将业务配置项放到项目环境变量中

- **规则等级：** 【强制】
- **规则描述：** 项目环境变量无法实现灰度发布、版本管理、回溯、一键升级等功能。因此环境变量仅用于在特定场景下统一注入全局配置，禁止存放业务配置项
- **检查方式：** 人工检查

#### 禁止私自创建项目级环境变量，必须向平台申请

- **规则等级：** 【强制】
- **规则描述：** 项目级环境变量会注入到项目下所有的应用中，禁止私自创建项目级环境变量，以免发生冲突覆盖的异常情况
- **检查方式：** 人工检查
- **适应范围：** 国际业务中心。其他业务中心，也不可私自创建项目级环境变量，防止和应用的变量冲突，要充分的拉通。

#### 建议不要覆盖项目下自动注入的环境变量

- **规则等级：** 【建议】
- **规则描述：** 应用创建时，默认包含项目级环境变量和默认注入的环境变量，这些环境变量会可能会被别的地方使用，请勿随意修改
- **检查方式：** 人工检查

#### 在PATH环境变量的设置中，禁止把当前目录设置在PATH最前面

- **规则等级：** 【强制】

- **规则描述：** 永远不要在PATH开头或中间包含.，如果需要只能放在最后。使用绝对路径或./执行当前目录命令。在K8s环境中采用最小权限原则，固定PATH变量；会导致k8s 执行“docker-entrypoint.sh liveness”命令进行探测时，找不到对应的脚本，探测失败。

- **检查方式：** 工具检查(暂未实现)

- **反例：**

  ```bash
  PATH=.:$PATH          # ⚠️ 高风险！，禁止，当前目录在开头
  PATH=$PATH:.:$HOME    # ⚠️ 中风险！禁止，当前目录在中间
  ```

### 配置文件管理规范

#### 系统级配置必须支持通过环境变量获取，且必须包含默认值

- **规则等级：** 【强制】
- **规则描述：** 不修改任何配置文件或者配置项，仅通过配置环境变量，应用即能够正常启动，且可以处理业务。用于在紧急场景下的配置修改
- **检查方式：** 人工检查

#### 配置项必须向下兼容，禁止修改历史配置项的名称

- **规则等级：** 【强制】
- **规则描述：** 如果勘误，通过新增配置项，并逐步废弃原配置项方式
- **检查方式：** 人工检查

#### 配置文件必须强受控，且遵循相应规范

- **规则等级：** 【强制】
- **规则描述：** 应用配置文件中有配置项新增时，需要及时更新应用配置包中的配置文件内容；标准应用配置包中的配置项需要保证是最完整的内容
- **检查方式：** 人工检查

方案说明：标准化配置统一登记方案

#### 需要ZCM在一键升级时进行自动化处理的标准化配置必须统一登记

- **规则等级：** 【强制】
- **规则描述：** 系统内部接口配置项或外部参数配置项，需要在标准化配置项中进行录入；不同项目有特异化的配置，需要按项目进行录入
- **检查方式：** 人工检查

## 无状态应用

### 端口映射规范

#### 无状态应用禁止使用主机网络

- **规则等级：** 【强制】
- **规则描述：** 无状态应用禁止使用主机网络模式
- **检查方式：** 工具检查(暂未实现)

#### 对外提供HTTP服务的端口，必须配置端口映射

- **规则等级：** 【强制】
- **规则描述：** 对外提供HTTP服务的应用必须配置端口映射，只有配置端口映射ZCM才会创建svc，对外提供服务
- **检查方式：** 工具检查(暂未实现)

### 探针配置规范（就绪/探活）

#### 必须启用就绪探针和存活探针

- **规则等级：** 【强制】
- **规则描述：** 无状态应用必须配置就绪探针和存活探针，配置方法参照补充说明中对应的产品手册；
- **检查方式：** 工具检查(暂未实现)
  存活探针配置说明：[https://docs.iwhalecloud.com/doi/YHk/user-guide/SvUq/stateless-app/app-config/probe-config](https://docs.iwhalecloud.com/doi/YHk/user-guide/SvUq/stateless-app/app-config/probe-config)
  就绪探针配置说明：[https://docs.iwhalecloud.com/doi/YHk/user-guide/SvUq/stateless-app/app-config/ready-probe-config](https://docs.iwhalecloud.com/doi/YHk/user-guide/SvUq/stateless-app/app-config/ready-probe-config)

#### 就绪探针的校验逻辑必须具备有效性

- **规则等级：** 【强制】
- **规则描述：**  就绪探针用于判断应用是否完成初始化且能够对外提供服务和正常接收业务流量，就绪探针失败超过设置的阈值会将该应用的IP从业务网关中移除，不对外提供服务。就绪探针通过，必须代表应用已经可以正常对外提供服务；就绪探针失败，代表应用无法对外提供服务。
- **检查方式：** 人工检查  
  说明：就绪探针失败仅支持从业务网关移除未就绪应用的IP，不支持Dubbo等使用自己注册中心的异常实例的移除。
- **正例：**  
  如下：访问应用专用的业务就绪接口，可以正常对外提供服务，返回状态码200，代表就绪探针通过，其他状态码代表就绪探针失败。

```
APP=( "app" )  
app=(  
"replace with the real start command" # start command  
"replace with the real process key" # process key  
"replace with the real liveness check command" # liveness check command  
"replace with the real liveness successful result code" # liveness successful result code  
"curl -s -o /dev/null [http://127.0.0.1:8080/health/ready](http://127.0.0.1:8080/health/ready) -w %{response_code}" # readiness check command  
"200" # readiness successful result code  
)  
```

- **反例：**  
  如下：就绪探针命令直接返回OK，与期望值永远相等，就绪探针永远通过，无法真实反映应用是否可以对外提供服务。

```
APP=( "app" )  
app=(  
"replace with the real start command" # start command  
"replace with the real process key" # process key  
"replace with the real liveness check command" # liveness check command  
"replace with the real liveness successful result code" # liveness successful result code  
"echo OK" # readiness check command  
"OK" # readiness successful result code  
)
```

#### 存活探针的校验逻辑必须具备有效性

- **规则等级：**【强制】
- **规则描述：** 存活探针用于检测应用是否异常且不可自愈，存活探针失败超过设置的阈值平台会自动重启应用。存活探针校验失败时，代表应用处于异常状态，且必须重启应用才能恢复服务；应用可自愈的异常状态，不应该包含在探针失败场景中。
- **检查方式：** 人工检查
- **正例：**  
  如下：访问应用专用的业务存活接口，应用正常或者可以自愈，返回状态码200，代表存活探针通过，其他状态码代表存活探针失败。

```
APP=( "app" )  
app=(  
"replace with the real start command" # start command  
"replace with the real process key" # process key  
"curl -s -o /dev/null [http://127.0.0.1:8080/health/live](http://127.0.0.1:8080/health/live) -w %{response_code}" # liveness check command  
"200" # liveness successful result code  
"replace with the real readiness check command" # readiness check command  
"replace with the real readiness successful result code" # readiness successful result code  
)  
```

- **反例：**   
  如下：存活探针命令仅检查8080端口是否处于监听状态，只要端口处于监听状态，存活探针就一直通过，无法真实反映应用是否处于异常状态且不可自愈。

```  
APP=( "app" )  
app=(  
"replace with the real start command" # start command  
"replace with the real process key" # process key  
"echo $(netstat -lnpt|grep -c -w 8080)" # liveness check command  
"1" # liveness successful result code  
"replace with the real readiness check command" # readiness check command  
"replace with the real readiness successful result code" # readiness successful result code  
)
```

#### 首次延迟时间必须大于应用的启动时间

- **规则等级：** 【强制】
- **规则描述：** 就绪探针和存活探针的首次延迟时间都必须稍微大于启动时间，防止探针频繁失败，导致应用不断重启；存活，就绪探针的探测检测间隔时间要大于1秒，默认是15秒。
- **检查方式：** 人工检查

#### 必须使用默认检查方式

- **规则等级：** 【强制】

- **规则描述：** docker-app.def中，只定义启动、存活、就绪的检测命令，不可以编写自定义的业务脚本；会影响存活和就绪探针的判断时长


- **规则等级：** 【建议】
- **规则描述：** 就绪和存活探针的检测时间不能太短，防止应用容器在压力较大情况下，可能出现的偶发超时
- **检查方式：** 人工检查

## 有状态应用

### 探针配置规范

#### ZCM中传统docker类型的有状态应用ZCM无法提供统一探针，应用在异常时必须支持自动退出

- **规则等级：** 【强制】
- **规则描述：** ZCM中传统docker类型的有状态应用使用原生的容器机制，无法K8S存活和就绪检测探针能力，因此需要应用实现自我检测，异常后主动退出，容器会自动重新启动。或者通过内部脚本探测异常后自动重启; 参考样例：

```
#!/bin/bash  
APP=( "java" "health_check" )  
java=(  
     "start command" # start command  
     "key"       # process key  
     "health_check command"    # liveness check command  
     "HEALTH RESULT"         # liveness successful code  
     "health_check command"    # readiness check command  
     "HEALTH RESULT"         # readiness successful code  
)
health_check=(  
    "sh /app/health_check.sh" # start command  
     "health_check.sh"       # process key  
     "echo OK"    # liveness check command  
     "OK"         # liveness successful code  
     "echo OK"    # readiness check command  
     "OK"         # readiness successful code  
)

```

配置参考链接：[https://docs.iwhalecloud.com/doi/YBd/%E8%AE%BE%E8%AE%A1/%E5%AE%B9%E5%99%A8%E5%B9%B3%E5%8F%B0/%E6%9C%89%E7%8A%B6%E6%80%81%E5%BA%94%E7%94%A8/%E6%9C%89%E7%8A%B6%E6%80%81%E5%BA%94%E7%94%A8%E6%A8%A1%E6%8B%9F%E8%87%AA%E5%AE%9A%E4%B9%89%E6%8E%A2%E9%92%88%E6%96%B9%E6%A1%88](https://docs.iwhalecloud.com/doi/YBd/%E8%AE%BE%E8%AE%A1/%E5%AE%B9%E5%99%A8%E5%B9%B3%E5%8F%B0/%E6%9C%89%E7%8A%B6%E6%80%81%E5%BA%94%E7%94%A8/%E6%9C%89%E7%8A%B6%E6%80%81%E5%BA%94%E7%94%A8%E6%A8%A1%E6%8B%9F%E8%87%AA%E5%AE%9A%E4%B9%89%E6%8E%A2%E9%92%88%E6%96%B9%E6%A1%88)
- **检查方式：** 人工检查

### 高级配置规范

#### ZCM传统的docker类型有状态应用，建议开启应用重启策略

- **规则等级：** 【建议】
- **规则描述：** ZCM传统的docker类型有状态应用，开启重启策略时，应用异常或者主机重启或Docker重启，docker类型的有状态应用容器可被dockerd自动拉起
- **检查方式：** 人工检查

- **规则等级：** 【建议】
- **规则描述：** 优雅时间指等待容器内进程完全退出的时间，一般建议为默认值；如果应用较大，则可以动态调整，但不建议超过30s
- **检查方式：** 人工检查

### 时区映射配置规范

#### 建议不要删除时区等默认的目录映射

- **规则等级：** 【建议】
- **规则描述：** 默认映射宿主机 /etc/localtime、/etc/timezone到容器中，保持容器的时区和主机的时区相同。如果删除，会影响应用的时区，避免造成应用和主机时区不一致
- **检查方式：** 人工检查

方案说明：三方的云平台时区需要通过TZ环境变量注入，用户容器内切换用户操作会导致读取不到问题

- **规则描述：** 应用发布必须具备回滚能力，确保在升级出现问题时可以快速恢复
- **检查方式：** 人工检查

## 业务网关

### 业务网关规则

#### 需要根据实际业务场景和与应用部署模式选择适当的分发策略

- **规则等级：** 【强制】
- **规则描述：** 网关分发策略有轮询、ip_hash、最小连接数；轮询和最小连接数尽可能保证分发均衡，ip_hash以客户端ip（ip前三段）取模分发
- **检查方式：** 人工检查
- **反例：** 配置策略为ip_hash导致流量分发不均，落在同一个节点上，系统挂掉

#### 网关必须根据性能压测结果配置限额和work进程数

- **规则等级：** 【强制】
- **规则描述：** 网关配置必须基于性能压测结果
- **检查方式：** 人工检查
- **反例：** 项目现场work进程数配置不合理，导致网关出现性能问题

方案说明：性能测试团队根据每个线程的实际情况进行压测，ZCM新版本默认出场业务网关配置为8C+8G

#### 必须明确指定根路径，且配置根路径时，必须为应用上下文路径

- **规则等级：** 【强制】
- **规则描述：** 应用上下文路径：Spring Boot应用一般server.servlet.context-path或server.context-path参数配置路径，默认为:/；外置tomcat应用根路径一般为实际部署路径webapp目录下的项目名称
- **检查方式：** 工具检查(暂未实现)
- **反例：** 任意配置，导致访问异常
