# 收尾文档——自测说明与影响说明

研发云单据流程在开发完成时期望的两份文档的格式。两个结构都取自真实提交过的单子；严格按格式执行，草稿才能不经返工直接贴回单子。

以下格式即权威格式——起草时不要再拉取其他单子来重新确认格式，那种重复查询付出大响应却毫无收益。只有在返工时更新同一单子的旧草稿，才需要查该单的已有文档。

## 自测说明

挂在单子上的开发视角测试用例。在研发云上它呈现为以下字段的用例：

| 字段 | 取值模式 |
| --- | --- |
| 用例名称 | `#<单号> <单子标题>`——单号前加 `#`，后接完整单子标题，如 `#11983974 V9L-哥伦比亚ETB-...字段同步给spc` |
| 用例类型 / 等级 | 默认 功能 (0) / P3 (3)；核心路径变更时提高等级 |
| 角度 | 开发角度 (angle 0)——这是自测说明区别于测试用例的关键 |
| 前置条件 | 验证前必须成立的条件，如 `代码变更升级应用`（代码已部署/升级已执行）或 `无` |
| 步骤 | 一到多步，每步三要素齐全——`步骤描述`（具体操作或观察动作）、`预期结果`（该步应看到什么）、`实际结果`（实际看到什么）。直接观察型检查也写明观察动作（如「查看 spc 记录的 addressName 字段」），不写「无」 |
| 实际结果 | 每步分别记录，附截图或文字证据（见下） |
| 状态 | 仅当描述的验证真实执行并通过时才写 通过 |

### 步骤与证据的写法

每个步骤按「步骤描述 → 预期结果 → 实际结果 → 证据」四段写：

```markdown
1. 步骤描述：调用 queryProfileAndOffers 接口，入参 subscriberId=xxx
   预期结果：接口调用成功，responseCode 为 0
   实际结果：调用成功，返回码 0
   ![截图占位：接口调用报文——证明入参正确、返回码为 0]

2. 步骤描述：查询 spc 库 xxx 表最新同步记录
   预期结果：addressName 字段值为变更后的值
   实际结果：查询结果与预期一致
   ![截图占位：查询结果集——证明 addressName 已同步]

3. 步骤描述：打开 spc 记录详情页查看同步信息
   预期结果：页面展示同步后的 addressName
   实际结果：页面正常展示
   ![截图占位：详情页效果——证明最终可见结果]
```

### 边界覆盖要求

复用测试方案中依据需求、代码和风险选定的用例清单，回填真实结果。仅在实施出现新行为或风险时补充用例，不因进入收尾阶段重读全部文档或重新建立矩阵。

覆盖变化的行为、关键边界及不同调用契约；合并等价用例。以下是按需查阅的提示，不是每次必须逐项执行的清单。数据写入仍需验证范围、失败恢复和相关并发风险：

| 维度 | 应检查的典型边界 |
| --- | --- |
| 缺失与空值 | 节点缺失、`null`、空字符串、纯空白、空集合、集合中的 `null` 元素 |
| 数量与长度 | 0/1/N、最小值、最大值、临界值前后（如 max-1/max/max+1）、超长与截断风险 |
| 数值与时间 | 0、负数、精度/溢出；生效前/生效时/失效时、跨日月年、时区及合法/非法格式 |
| 枚举与操作 | 每个合法值、非法值、大小写、前后空格；新增/修改/删除对应的存在与不存在状态 |
| 集合与关联 | 重复项、顺序变化、多条混合合法/非法；父子 ID、归属、主从节点及跨字段一致性 |
| 数据状态 | 正常、停用、过期、历史、脏数据、数据库已有但业务查询不可见的数据 |
| 无变化与副作用 | 新旧值相同、空变更、重复提交；确认不产生空订单、无关落库、消息或缓存副作用 |
| 批量与事务 | 全成功、首/中/末项失败、部分变化；验证原子性、失败回滚和无半成品数据 |
| 幂等与并发 | 同请求重放、换业务键重试、失败后重试、并发修改同一对象及竞态冲突 |
| 兼容与回归 | 新旧协议字段、可选字段、历史客户端、共享 DTO/方法/表的其他调用方及既有事件 |
| 持久化与可观测性 | 订单、主表、子表、映射表、日志和返回值前后一致；只允许目标字段发生预期变化 |

每个边界用例至少写清「前置/输入 → 操作 → 预期结果 → 实际结果 → 证据 → 状态」。同类边界可以用参数化表格合并，但不同错误码、校验顺序、数据状态或副作用不得被一句“异常场景符合预期”替代。尚未真实执行时，保留完整的用例设计并把实际结果和状态写为「未执行（待验证）」；不得据代码推断填写「通过」。

规则：

- 步骤顺序遵循 接口调用 → 数据核对 → 最终可见效果；多步操作的每一步独立成项，各自带预期和实际。
- 有可用截图工具时保存真实截图，避免暴露敏感数据；没有时使用脱敏文字结果，或写明「截什么图——证明什么信息」的待补占位。不得伪造截图或结果。
- 只把真实执行过的验证填写为实际结果或「通过」。如果测试方案（第四阶段）中某项计划检查未执行，保留完整用例设计，把实际结果和状态写为「未执行」，并说明原因及补测条件——绝不给未验证的内容写通过。
- 脚本单的步骤即执行序列：执行前验证查询 → 脚本执行 → 执行后验证查询，每步的查询输出作为证据粘贴或截图。
- 自测说明应从第四阶段的边界矩阵逐项回填；若受环境或数据限制未覆盖某个适用边界，明确记录未执行原因和补测条件，不得悄悄删除。

## 影响说明

六个字段，中英文成对。提交时六个都要填——英文字段留空不可接受。

| 字段 | 内容 |
| --- | --- |
| 修改内容 (changeContent / changeContentEn) | 一句话讲清技术层面改了什么。真实单据示例：`增加addressName字段` / `Add the "addressName" field.`；或 `在多个视图中添加acctRes非空判断，避免访问属性时报错`。 |
| 业务影响说明 (bizImpact / bizImpactEn) | 业务可见的影响。对业务透明时按真实单据写 `无影响，<一句话说明优化点>`，如 `无影响，优化同步信息，bill_contact_man.addressName字段同步给spc`；修复用户可见问题时，写清问题和覆盖范围。 |
| 其他项目影响说明 (projectImpact / projectImpactEn) | 对其他项目或分支的影响。无影响时：`无` / `NONE`。触碰共享产品分支时写明改了哪个面，如 `修改了产品分支的前端页面展示bug`。 |

内容取材于第二阶段（修改内容）、第三阶段（业务与跨项目影响）和第四阶段（验证了什么）——影响说明是批准方案的压缩版，不是新一轮分析。每个字段保持一到两句。

## 草稿输出格式

开发完成后复查通过后，两份草稿一起呈现：

```markdown
## 自测说明（草稿）
- 用例名称：#<单号> <标题>
- 前置条件：<…>
- 边界用例：

  | 编号 | 前置/输入 | 操作 | 预期结果 | 实际结果 | 证据 | 状态/未执行原因 |
  | --- | --- | --- | --- | --- | --- | --- |
  | B01 | <具体数据与边界值> | <调用/查询/观察动作> | <应看到什么> | <实际看到什么；未执行则写“未执行”> | <截图或文字证据；未执行则写补测条件> | <通过/失败/未执行及原因> |
  | B02 | … | … | … | … | … | … |
- 详细步骤：<需要多步操作的边界用例，按“步骤描述 → 预期结果 → 实际结果 → 证据”展开>
- 总体状态：<所有要求执行的用例均真实通过时写“通过”；任一用例失败时写“失败”；无失败但存在未执行项时写“部分执行/未执行”并说明>

## 影响说明（草稿）
- 修改内容：<中文> / <English>
- 业务影响：<中文> / <English>
- 其他项目影响：<中文> / <English>

以上为草稿，确认后可自行登记到单子，或明确让我通过 MCP 提交。
```

## 提交（仅在明确要求时）

默认只出草稿。用户明确要求提交时：

- 影响说明——devspace MCP `addTaskImpact`，六个字段全填（taskNo 加三段中文和三段英文）。
- 自测说明——cloudtest MCP `addAndRelaTestCase`，对准单子的 taskNo，`angle: 0`（开发角度）、`caseType: 0`、用例名称、前置条件和 stepList（`setpDesc` / `result` / `actualResult`）；草稿为 AI 辅助生成，设置 `generatedByAI: "Y"`。
- 仅当所有要求执行的验证均真实执行并通过时才可提交自测说明；存在失败或未执行项时不得提交，并说明失败项或补测条件，报告失败项或补测条件；在已有授权和可用环境内继续修复、补测，确需用户操作时才请求协助。
