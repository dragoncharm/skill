**前 言**

本文规定了浩鲸科技数据库模型设计的规范，并明确各角色的工作职责。随着本规范的发布，参考文章《数据模型设计规范及脚本管理流程V1.0》中有关数据库的设计的规定不再有效，以本文为准。

# 编写目的

本文用于描述浩鲸科技软件产品中数据库模型的设计规范（Oracle部分）。

# 适用范围

适用于业务相关的数据模型设计，涉及数据库的种类包含Oracle。

本文所指数据库模型仅包含表（表中主键、索引、外键及分区）、触发器、序列和视图（部分版本和项目可能存在），以及一些域表（定义见5.2.1.1节）的配置数据。

本文所指脚本范围不包含开发人员负责管理的存储过程或者存储函数等脚本、不包含客服人员以维护系统或者割接为目的而使用的脚本；不包含数据库用户、权限、数据库实例、表空间、DBLink等的建立和维护，此部分由相关集成部门提供，但建议各建库、运维等脚本也参考本标准规范。

# 角色和职责

2. 测试：负责对数据库脚本进行第二次检查。

3. CMO：负责导出指定事务单中的相关数据库脚本，用于发布。

# ORACLE数据库模型设计规范

## 基本设计规范

### 构成规范

【强制】数据库中各种名称必须以字母开头，但严禁使用SYS开头。【例外】中国电信集团规范中要求SYS开头的表可以不遵守此条；**检查方式：**【人工检查】

【强制】名称只能含有字母，数字和下划线“\_”三类字符。 **检查方式：**【工具检查。检查工具：通过研发云的脚本录入界面检查，以下工具检查条目相同。】

【强制】表名、字段名不能使用系统保留字。参见附录六《Oracle保留字参考》 **检查方式：**【工具检查】

【强制】命名应采用能够准确反映其中文含义的英文单词或英文单词的缩写构成，避免出现英文单词和汉语拼音混用的情况。如果英文单词已定义了缩写，应该用缩写。缩写规则参见附录六《通用中英文对照及缩写表》，可以借助模型设计工具对配置表进行管理。【例外】政企产品的数据库由于特殊的市场环境，允许使用拼音。但也应避免中英文混用。 **检查方式：**【人工检查】

【推荐】在不同位置出现的、表示相同含义及内容的字段名称命名应该一致。

### 大小写规范

【强制】数据库中的各种名称的所有字符，必须使用大写，也即在脚本中，对任何名称不能添加双引号""来设定字符的大小写形式。 **检查方式：**【工具检查】

### 长度规范

【强制】所有对象标识符均不能超过30个字符（尽管Oracle12.2后支持大于30字符小于128字符，但是数据库导入导出时需要用跟服务端相同版本的客户端。故仍旧保留此要求），也即：Oracle中的表名、字段名，函数名，过程名，触发器名，序列名，视图名的长度均不能超过30个字符。**检查方式：**【工具检查】

### 对象命名规范

【强制】针对1.4规范发布以后的新版本和新产品，公司内部对各数据库对象统一命名规范，如下参考：

## 表

### 表的分类

此节为描述文字，用来明确表的分类。以便后续章节的规范使用表分类描述。非规范。

#### 域表（不提供配置界面，可以在程序中写死）

域表中的基础配置数据需要在程序中一一对应，即可以以'写死'的方式标记每条记录，增加或者修改记录都会引起程序变更。不提供配置界面。

例子：付款方式类型,PAYMETH_TYPE表， 主键字段PAYMENT_TYPE
CHAR(1),取值C、B等,全部字母采用大写。

域表的表名格式通常为XXX\_TYPE。此时主键字段名称和表名要保持一致，对应的数据类型为CHAR(1)
。表名格式也可以存在例外，如SUBS_EVENT、ALL_SERV_TYPE，对应的主键和表名不一致。主键格式一般为表名_ID，对应的数据为类型
NUMBER(3) 或者NUMBER(6)。

域表的字段通常有三个：主键 CHAR(1)/NUMBER(3)/NUMBER(6)、表名+_NAME
VARCHAR2(60)、COMMENTS VARCHAR2(120)/VARCHAR2(255)

#### 配置表（提供配置界面，不可以在程序中写死）

配置表中的数据可以通过界面配置增加或者减少，对应的配置数据不能在程序中一一对应，即不可以以‘写死’方式标记每条记录。数据的增减不引起程序变更。

例子：证件类型，CERT\_TYPE表，主键字段CERT_TYPE_ID NUMBER(3)。

配置表的主键和表名一般不一致，格式一般为表名_ID，对应的数据为类型 NUMBER(3)
或者NUMBER(6)。配置表字段至少包含有三个：主键 NUMBER(3)/NUMBER(6)、表名+_NAME
VARCHAR2(60)、COMMENTS VARCHAR2(120)/VARCHAR2(255)

#### 实例表（在运行过程中产生的生产数据）

资料表：类似订户、帐户、客户、个性化资费实例等保存客户资料的表。记录数量和现场用户数相当。

流水表：类似订单、账簿等和业务操作对应的表。通常数据量会随着时间推移不断快速增长。

### 表名

【强制】规范发布后的后续版本中，产品版本新增表名为模块名+正常表名。产品模块名参考行销团队发布的产品列表。基本上都是4位以下，模块内部使用，就不需要再命名了，超过4位的再缩减。【例外】多个模块公共表，可不设置模块前缀。 **检查方式：**【人工检查】

【强制】项目版本，项目缩写+表名。如EBS项目的表都EBS为前缀。 **检查方式：**【人工检查】

【推荐】对于表名还可以增加相应后缀做标识，即成：[项目编码_模块编码\_]主体名_后缀，另外，考虑到跨域实体，为了不影响理解，并保证命名的非二义性，可以在主体名前增加“子域名”作为前缀。

对于**主体名**，包含三个及三个以上单词的，建议采取缩写方式。

例如: 客户表 CUST

客户信用度 CUST \_CREDIT

客户附加属性 CUST_EXTERNAL_ATTR

#### 说明字段

【推荐】描述、备注、说明用字段，使用COMMENTS VARCHAR2(120)/VARCHAR2(255)/
VARCHAR2(4000)

【强制】状态字段使用STATE CHAR(1) –中国电信集团规范可用STATUS\_CD VARCHAR2(10)/CHAR(3)
**检查方式：**【人工检查】

**检查方式：**【人工检查】

【推荐】生成时间用CREATED_DATE DATE -中国电信集团规范可用CREATE_DATE DATE

#### 字段命名原则

【强制】不使用RDBMS的保留字作为字段名，比如ALTER、SELECT等。 **检查方式：**【工具检查】

【推荐】字段命名结构如下:BODY(主体名)_SUFFIX（后缀名）

例如: 客户编码 CUST_NBR

其中，

- BODY为主体名，应该能够清楚地说明对象的含义,采用英文缩写

- SUFFIX 是后缀名，提供特殊的含义

- 字段名称不能出现数据库中的关键字

  以下是一些特别的前后缀，代表了这个字段特殊的含义。在其他的情况，应避免使用以下的前后缀：

| **前后缀**  | **定义**                                                                          |
|-------------|-----------------------------------------------------------------------------------|
| \_DESC      | 参数表内的描叙字段 如字段名是OFFER\_DESC,表示销售品描述                           |
| \_FLAG      | 布尔型字段                                                                        |
| \_NBR/NO    | 编号字段                                                                          |
| \_NUM/\_NBR | 号码字段                                                                          |
| \_ID        | 标识字段                                                                          |
| \_TYPE      | 类型字段，用来表示有类型含义的字段 如字段名是OFFER_TYPE，表示销售品类型           |
| IS\_        | 描述含有是否含义的字段,主数据值只有0/1或者N/Y两种情况，如IS_DEFAULT，表示是否默认 |

### 字段数据类型

【强制】布尔值字段：使用CHAR(1) **检查方式：**【人工检查】

【强制】固定长度字符串：使用CHAR(n),长度根据需要定义; **检查方式：**【人工检查】

【强制】可变字符串字段：使用VARCHAR2数据类型，对应长度为3/30/60/120/255/1000/4000。【例外】中国电信规范要求的可以按照集团规范使用的长度； **检查方式：**【人工检查】

【强制】数值字段：使用NUMBER数据类型，无小数，对应长度为3/6/9/12/15（此长度系列是为了和二进制字节存储接近从而避免空间浪费）。实例表ID尽量取大（新增资料表为12位，流水表为15位或者18位），确保整个生命周期离最大值还差1到2个数量级。存储金额时需要15（超过15时java前台应用需要特殊修改）或者18。【例外】中国电信规范要求的可以按照集团规范指定的长度；
【例外】对金额字段，BSS域外或者原系统一直沿用的小数形式存放可以保持。 **检查方式：**【人工检查】

【强制】日期型字段：统一使用DATE。注：本条是指时间类型用TIMESTAMP还是DATE，一些特殊场景，比如：考虑多种数据库兼容，日期使用字符串类型存放，不在此规范之列。【例外】如果有精确到1秒以下的需求，可以使用TIMESTAMP类型。 **检查方式：**【人工检查】

【推荐】大于4000个字节的字符串，可采用CLOB类型字段。（如某些接口表存储xml数据的字段）。

### 字段注释

【强制】要求每个字段有注释，默认中文便于理解，部分项目不能出现中文时用英文注释，或者在生成脚本时，配置管理员选择不生成注释的方式完成。 **检查方式：**【人工检查】

【强制】字段取值如果可以枚举，并且无对应域表时，需要在字段注释中针对每个字段取值进行枚举和含义解释。【例外】中国电信集团PDM中可以维护在standard checks 中的list of values。 **检查方式：**【人工检查】

【推荐】字段取值非枚举，但一些特殊取值有特定的含义，比如：NULL值用于区分是优惠还是原费用的税记录，需要在字段注释中说明。

【推荐】字段注释、DOMAIN和配置表的区分使用：如果仅仅代码用于判断使用的字段，无需在界面展示，则可用字段注释说明字段取值含义。如PROD表STATE字段，SUBS_GOODS_INST表的STATE字段,ACCT表的STATE等字段。DOMAIN表和配置表的使用由设计时具体分析判断。

【参考】外键字段需要说明参照于哪个表。

【推荐】主键备注写明对应的序列。

### 主键

【推荐】尽量保证每个表有自己的主键，仅针对分区表、有特殊性能要求或者特定业务需求时不需要主键。

【参考】为防止公共和私有定制域表主键冲突，主键按公共和私有定制进行分段。例如：Zsmart
v8分段规则参考文档《前台域表数据脚本维护方法.xlsx》，SVN地址：Product_Documentation/公共文档/规范约定/综合类/前台域表数据脚本维护方法.xlsx

【推荐】主键最好设计成单一主键，尽量不用复合主键，尽量使用没有业务语义的字段作为主键，一般采用一个XXX_ID字段做主键，类型为NUMBER，取值来自序列sequence。同时建议采用智能序列（字段取值=环境变量+序列值。写法参考开发规范）以减少数据库一致性读写竞争，提升性能。

【推荐】主键创建时，采用建表和添加主键约束分开的方式来创建主键。这样索引有碎片的情况下也可以重建；

例如：

```sql
create table CC.BANK    
(    
BANK_ID NUMBER(6) not null,    
PARENT_ID NUMBER(6),    
BANK_NAME VARCHAR2(120) not null,    
COMMENTS VARCHAR2(4000),    
STATE CHAR(1) not null,    
STATE_DATE DATE not null,    
SP_ID NUMBER(6),    
BANK_CODE VARCHAR2(254)    
);
alter table CC.BANK  
add constraint PK_BANK_ID primary key (BANK_ID) using index tablespace
IDX_CC;
```

> Tips：PDM 导出时默认使用create table … primary key …
> 方式，可修改导出选项为上述写法。

【推荐】BSS ZSmart v81系列，对于分布式下主键如果需要在序列前加路由前缀，则必须到
TFM_ROUTING_IDS表进行登记。以保证ZMC对主键最大值的监控准确。

### 约束

【推荐】尽量保证每个表的约束完整，仅针对分区表、有特殊性能或者数据归档需求时不需要约束。

【强制】配置表之间保持外键约束完整。这样可以保证各个表之间的数据一致性；  **检查方式：**【人工检查】

【推荐】考虑到数据量比较大的情况下外键对插入、删除的性能影响比较大。实例表上尽量不建立外键。也不要作为外键的父表；

### 表的分区

总体原则：

【强制】每个表必须包含以下属性参数：TABLESPACE；**检查方式：**【工具检查（暂未支持）】 【参考】这两个可以根据项目需求配置：PCTUSED，STORAGE。

【推荐】分区表：

对于数据量比较大的表，根据表数据的特性进行分区，以得到较好的性能。

1. 如果表按某些字段进行增长，则采用按字段值范围进行范围分区。

2. 如果按某个字段的几个关键字进行分布，则采用列表分区。

3. 对于资料表，则采用hash分区。

4. 在范围分区中，如果数据按某个关键字段均衡分布，则采用子分区的复合分区方法。

#### 表记录数和分区化规范

【推荐】大表（记录数超过5000万）在所有表中所占比例不要超过20%

【强制】预期表的数据量超过5000万，需要设计成分区表。 **检查方式：**【人工检查】

【强制】单表分区数量不能超过500个 **检查方式：**【人工检查】

【强制】全库分区数量不能超过20000个 **检查方式：**【人工检查】

#### 分区方式

【推荐】如果按时间分区的情况下，使用PART_ID 作为分区条件，SA给出分区方式

按照日分区，就是年月日；

按照月分区，就是年月；

按照小时分区，就是年月日小时；

【推荐】11版本后Oracle支持自动建立分区。可以用表中存在的时间字段进行自分区，对后期维护和查询效率都带来便利，建议此种方式。**但是需要注意单表分区总数500个的限制。可能超过时需要在设计时注意清理、备份。**

【参考】分区方式一般在原有表上增加PART_ID
NUMBER(6)字段，分区根据PART_ID取值列表进行分区。该字段默认取值一般根据分区要求使用如下两种赋值：

根据日分区成１－３１，则字段默认为TO_NUMBER(TO_CHAR(SYSDATE,'DD'))

根据月份分区成１到１２，则字段默认为TO_NUMBER(TO_CHAR(SYSDATE,'MM'))

#### 分区依据

【推荐】账务管理交易记录、订单流水记录相关的表一般按月份分区，此类表一般是日常业务轨迹记录，需要提供查询功能，例如ACCT_BOOK,SUBS_ORDER等。

【推荐】业务实现流程中使用的接口或者流水记录相关的表一般按日分区，此类表实时性较强，无需提供查询功能，例如CHANGE_NOTIF,ADVICE等。

#### 注意事项

【强制】分区表不能使用主键、全局唯一约束。 **检查方式：**【工具检查（暂未支持）】

【强制】分区表的索引需要为本地索引，需要增加LOCAL标识。主要有下面几个原因：
1.分区表存在全局索引的情况下，在生产库调整分区，比如：新增、删除分区，会导致该表相关业务操作中断；
2.如果数据插入、删除、更新频繁，全局索引需要维护的索引数据更多，网络和磁盘I/O的开销更多，从而影响性能；
3.Oracle低版本，比如：19.3，如果是全局索引，查询的时候又指定了分区，即使查询条件带了索引字段也可能会用不上此索引。【严重生产故障3551847】

#### RANGE分区规范

【推荐】SQL常依据某列的范围访问表，则对表使用RANGE分区，常见的情况是SQL根据时间范围进行查找更新，则使用时间字段作为分区关键字进行RANGE分区；需要结合对表的多种访问来确定分区的粒度：

1. 大多数SQL操作的分区关键字值的范围；

2. 数据维护的需要，比如以月为单位删除历史数据。

3. 数据访问的性能，以操作范围确定的分区数据量如果还是过大，则还需要进行细分。

4. 【强制】一个分区的数据量要小于3000万，这是一个硬性的尺度，比它小的话性能会更好，需要根据实际情况灵活掌握。 **检查方式：**【人工检查】

#### LIST分区规范

【推荐】SQL常居于某列的散列值访问表，则对表使用LIST分区。常见情况针对于某个地区或者某个业务进行数据访问，那么就使用地区编号或者业务编号作为分区关键字；需要结合对表的多种访问来考虑确定分区的粒度：

1. 一般使用一个分区关键字的值来划定一个分区。

2. 可以把分区关键字的值相对应数据比较少的几个分区合并作一个分区。

3. 如果一个分区关键字值所对应的数据量过大，比如大于3000万，则应该对表采用RANGE分区，然后再对该值的分区采用HASH子分区；也就是说，一个可以采用LIST分区的表，肯定可以转化成RANGE分区(可带子分区)，反之不然。

#### HASH分区规范

【推荐】SQL访问表不按照某列的范围进行，也不按某列离散值进行，而且对该表的数据不会依据某列的值范围或者离散值进行定期维护，那么使用HASH分区；HASH分区是不知道应该选择何种分区时的选择；HASH分区的各分区都可能存有各种情况的数据，故而不能用于依据分区清理数据的情况。HASH分区的数量是2的N次方个。

对确定分区粒度的考虑：

1. 依据分区的数据量规划和表的最大数据量来确定分区数。

2. 一个分区的数据量要小于3000万，也可根据实际情况灵活调整。

### 行记录长度建议

【推荐】一个表中的所有字段，尽量能存储在一个数据库BLOCK中，也即：表的单行字段总长度
< db_block
（减去pctfree）。例如，Oracle数据库中基本block_size为8k，默认pctfree为40%，那么表的单行记录大小最好就小于8k\*(1-40%)
= 4.8k

### 尽量规划在同一表空间

【推荐】对于每个应用系统都能用到的表放到同一个表空间中，比如系统配置表。如果系统还包括大量的图片等多媒体数据表，建议放到另一个库中或者文件存储中，以改善数据库性能。

### 大表的数据保留策略

【强制】大表需要有明确的数据保留策略。在设计阶段，需要明确业务字段的生命周期，并与数据生命周期匹配，制定表的数据迁移、归档、保留等策略。 **检查方式：**【人工检查】

【推荐】在表的物理设计阶段，建议每个表都添加几个有用的字段：记录创建日期、状态时间等，有助于分析记录中出现null数据或者数据丢失的原因。

### 临时表的清理机制

【强制】临时表需要业务本身考虑清理机制。业务真正需要用中间临时表，业务本身必须要考虑清理机制，表命名规范：TMP\_xxx； **检查方式：**【人工检查】

【推荐】个人备份或临时表，必须使用维护用户创建，个人表以PERS\_创建人名字全称\_为前缀，以跟业务用TMP\_临时表区分开，防止运维事故。

## 序列

【强制】一般格式为：1.SEQ\_+表名+\_ID或者表名\_+ID+\_SEQ；2.SEQ\_+序列值的字段名或者序列值的字段名+\_SEQ，比如SEQ\_CUST_ID/CUST_ID\_SEQ。如果序列名称超过规定字符长度，需要缩写部分字段，尽量保证通过序列名可以看出对应使用该序列值的字段名称。 **检查方式：**【工具检查（暂未支持）】

【强制】序列必须设置最大值，并和对应的主键字段长度一致，一般长度是6/9/12/15。步长为1，缓存20或100。特殊情况，基于性能要求，步长为1000，不缓存(nocache)。**检查方式：**【工具检查】通常不循环，拼接前缀的情况或者无唯一性要求可以循环； **检查方式：**【人工检查】

【强制】步长超过1000的序列对应表的主键必须为number(15)。【例外】中国电信集团规范模型中步长1000的序列可以不遵守此条。 **检查方式：**【人工检查】

【建议】在某些场景下，主键是取序列然后拼接前缀，序列长度比较短。比如：ORDER_ITEM_ID(15位) = ‘YYYYMMDD’+ORDER_ITEM_ID_SEQ.NEXTVAL(7位)'。在保证唯一性的情况下，建议根据业务量对序列设置循环。从而避免过早序列耗尽引发故障。

## 索引

【强制】索引正常命名是：索引前缀缩写[IDX\|UX\|FX\|BX]_表名/表名缩写_字段名。比如：ACCT表BANK_ACCT_NBR字段的普通索引命名为IDX_ACCT_BANK_ACCT_NBR。（【例外】普通索引电信集团规范为IX_表名/表名缩写_字段名）

如果索引名称正常情况下超30个字符，则IDX_表名单词首字母_字段，例如基于EBS_SUBS_SUSPEND_INFO表中的CREATED_DATE字段建立索引，对应索引名称为IDX_SSI_CREATED_DATE。
**检查方式：**【工具检查（暂未支持）】

【强制】分区表的索引必须有LOCAL标志。【例外】如果分区类型为Hash分区，且分区目标不是为了数据归档，则为提升查询性能，非分区字段上的索引可以为GLOBAL。但分区字段上的索引仍然必须是LOCAL的。 **检查方式：**【人工检查】

【推荐】如果字段值是要求唯一的，比如：分区前的主键字段，改为分区后建议加上分区字段建立本地唯一索引。

【强制】索引必须建立在指定的表空间，索引表空间默认和表存放的表空间是不同的。【例外】国内项目目前存在研发流程设计阶段不能确定表空间名的情况，各个项目表空间名可能不同。这种情况可以不设置。 **检查方式：**【人工检查】

【参考】对于有些表的列，虽然列值就几个，但是如果某些值数量较少，则可以建索引
比如PROD 表的PROD_STATE。

【强制】在现有的表上增加索引，需要加ONLINE。比如：

```sql
CREATE INDEX IDX_ACCT_BOOK_ACCT_ID ON ACCT_BOOK(ACCT_ID) ONLINE TABLESPACE IDX_CC;
```

【例外】如果现场是不支持此功能的Oracle版本，比如：标准版，可不强制。

> 规范来源：严重生产故障3732520

### 用不上分区条件的局部索引不宜建

【推荐】分区表建立分区索引后，如果在应用查询中无法用到这个分区索引列的条件，索引读将可能遍历所有分区，将严重影响性能，此时需要慎重考虑，判断是否需要修改代码或者修改索引字段。

### 函数索引

【推荐】一般需要避免函数索引。函数索引大多用于列运算，例如trunc(时间列)，这种可以转换成去掉trunc的写法。

### 位图索引

【推荐】位图索引需要谨慎设计。位图索引不适合用在表频繁更新的场合；位图索引不适合用在所在列重复度很低的场合。

### 外键对应列与索引

【强制】外键的子表为实例表时，必须为外键对应列建立索引(注：外键被参照的表称之为父表，创建外键的表称之为子表)。未建索引，将有可能导致：  
1.更新父表记录主键或删除记录时，由于会锁子表，可能导致死锁。  
2.两表做关联查询时，若以父表字段作为查询条件，可能导致查询性能低下。  
比如：CUST是一个实例表，CUST.CUST_TYPE_ID外键关联CUST_TYPE表，则CUST.CUST_TYPE_ID上应建立索引。  
【例外】当父表不存在删除的场景，比如：通过状态字段来标记逻辑删除，且不会修改主键，也不存在以父表字段关联查询时，则可以不建外键。  
关联说明：根据“5.2.7约束”章节中“实例表上尽量不建立外键”要求，实例表优先通过业务逻辑实现数据完整性，而非依赖数据库外键约束。若必须使用外键约束，则需严格遵循本规范的索引要求。

> 工具扫描发现违反此条目产品线整改的说明。有三个选择：1.对应列加索引；2.去除违反要求的外键；3.检查确认没有父表删除记录或改主键的场景。
> **检查方式：**【工具检查】

### 建立联合索引需要谨慎

【推荐】需要结合单列查询考虑，决定前缀。

例如，对于表中两列col1、col2，其中col1列单独查询较多的情况下，一般倾向于建立col1在前的的联合索引。

【强制】超过5个字段的联合索引需要避免。**检查方式：**【工具检查】

【参考】范围查询影响组合索引

组合查询中，如果有等值条件和范围条件组合的情况，等值条件在前，性能更高。

如WHERE col1=2 AND col2 >=100 AND
col2 <=120，此时是col1,col2的组合索引性能高过co2,col1的组合索引。

【推荐】需要考虑回表因素

一般情况下，如果建索引可以避免回表（在索引中即可完成检测），也可考虑对多列建组合索引，不过组合索引列不宜超过4个。

例如： PROD , PROD_ATTR, PROD\_ATTR\_VALUE可以考虑建立联合索引；

### 单表索引个数

【强制】单表索引个数需要控制，不能超过5个，包含主键附带的索引。对于高并发DML操作的表中，超过5个以上的索引，如果记录数很大时，将会极大影响该表的性能；如果表业务主要侧重于读操作，可以根据业务需要建立适当个数的索引。 **检查方式：**【人工检查】

【参考】剔除掉多余的索引，一般来说，2个月内从未被用到过的索引均是多余的。

### 单表无任何索引

【参考】单表无任何索引需重视。
