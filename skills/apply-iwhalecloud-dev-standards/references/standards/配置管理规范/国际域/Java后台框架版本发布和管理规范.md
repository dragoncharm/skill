# 前    言

本文档确立了Java后台框架的版本发布流程标准化，对各环节提出明确要求，确保版本生命周期的每一步操作都有明确的指导原则。通过提升流程的合规性和质量管理，保障框架产品的稳定性和可靠性。

本规范起草由国际产品运营中心平台技术部、国际质量效能部配置管理团队共同制定，并负责维护。

| :--------- | :---------------- | :-------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- |

| Build    | CMO             | maven、zip    | 基于主分支构建，版本性质与Snapshot(快照)版本一致，适用于所内无测试环境，必须发布到现场才能测试的场景，Build版本不能发布到生产环境                                                                                              | 申请发布 |
| 专项     | CMO             | maven、zip    | 生产项目需要框架主分支新特性，主分支稳定版本尚未发布时，由项目侧发起申请，在主分支发布项目专项版本；与规划版本相比，专项版本发布前**未经过联调测试、性能测试**，如果项目要求走正常发版流程，发布时间会因性能测试和联调测试延迟 | 申请发布 |

| Release  | CMO             | maven、zip    | 规划版本,基于主分支构建，发布周期固定，经过完整业务联调测试、性能测试，版本稳定性高，可以部署到生产环境                                                                                                                        | 主动发布 |

### 快照

快照（SNAPSHOT）版本是开发过程中的里程碑，通常用于开发和测试环境。这些版本是不稳定的，反映了最新的开发进展，供内部团队进行功能验证和测试。

#### 适用场景

* 用于研发联调的快照版本基于特性分支构建，发布在开发库，可能包含特定的功能特性和修复。
* 用户集成测试的快照版本基于最新的主分支构建，发布在过程库，可能包含新特性和修复。
* 频繁更新，每次代码提交或定期构建时生成。
* 用于开发和测试，不适用于生产环境。

#### 规范要求

- 快照属于临时版本，不在已经发布的快照版本上开发需求和修复BUG
- 下一个快照版本发布后，上一个快照版本失效
- 快照版本不提供SLA保障，非常不稳定，存在随时被清除的风险

### Build

Build 版本是用于内部测试或客户演示的构建版本。这些版本比快照版本更稳定，但仍然不推荐用于生产环境。

#### 适用场景

* 基于最新的主分支构建，可能包含新特性和修复。
* 需要通过内部测试，确保没有关键缺陷。

#### 规范要求

- Build版本属于临时版本，不在已经发布的Build版本上开发需求和修复BUG
- Build版本不提供长期支持服务，完成特定任务后即结束其生命周期

### 项目专项

项目专项版本是为了满足特定项目的紧急需求而发布的定制版本。这些版本可能包含特定于项目的修复或功能，不适用于其他项目。

#### 适用场景

* 基于最新的主分支构建，可能包含新特性和修复。
* 应项目要求定制，可能不包含在常规发布周期内。
* 需要与项目团队紧密合作，确保满足特定需求。

#### 规范要求

- 属于应急发布的非正式版本，最长维护周期 6 个月，项目侧应当在正式版发布后尽快升级到正式版本
- 已发布的专项版本可以提供BUG修复，但不提供新的需求开发
- 项目专项发布需要同时满足以下条件：
  - 接受本规范条款的约定；
  - 只有紧急情况下申请；
  - 需要项目经理发邮件给交付总监，片区领导申请备案，并承诺尽快升级到正式版本；

### 私有分支

私有分支版本是为特定项目或特定环境定制的版本，通常不公开发布。这些版本可能包含专有的修复或功能。

#### 适用场景

* 根据客户的特定需求定制。
* 可能不遵循公开的发布周期。

#### 规范要求

- 属于应急发布的正式版本，最长维护周期 6 个月，项目侧应当在正式版发布后尽快升级到正式版本
- 私有版本的需求只会同步到最新的主分支，中间的trunk分支不会被同步！
- 私有版本可以提供BUG修复，但不再提供新的需求开发
- 私有版本需要同时满足以下条件：
  - 接受本规范条款的约定；
  - 只有紧急情况下申请；
  - 需要项目经理发邮件给交付总监，片区领导申请备案，并承诺尽快升级到正式版本；

### Release

Release 版本是正式的、稳定的版本，经过完整的测试周期，包括功能测试、联调测试和性能测试，适用于生产环境。

#### 适用场景

* 遵循固定的发布周期。
* 经过全面测试，确保稳定性和性能。

### Hotfix

Hotfix 版本是为了快速修复生产环境中的紧急问题而发布的版本。这些版本通常基于最新的稳定版本，只包含必要的修复。

#### 适用场景

* 紧急情况下发布，以最小化生产环境的影响。
* 经过快速验证，确保修复的有效性。

#### 规范要求

- Hotfix 只做BUG修复，不能发布新的需求。

## 版本发布

### 发布流程

以下是规划版本发布流程示意图

![image](uploads/96339/0cc003f5-6601-44fe-a862-3d087c04d551/d8fe685ee706fb3f8d685e7b72aa3ad9.png)

规划版本分为研发、验收两个阶段，版本发布规则如下

1. **研发联调**：研发阶段只能发布快照版本到开发和过程仓库，目的是供研发和集成测试联调使用。
2. **集成测试**：框架版本不直接面向项目发布，必须通过产线，由产线随业务版本统一对项目发布；规划版本正式发布推送受控库之前，需要经过业务集成测试，集成测试环境基于过程库构建；集成测试在封版期进行，期间关闭研发版本计划，不再排入新的需求（BUG例外）。
3. **性能测试**：规划版本正式发布推送受控库之前，需要完成性能测试，提供性能测试报告；性能测试场景由框架团队和业务团队根据框架发布内容的影响范围共同评估，性能测试场景的设计应当尽可能的围绕核心业务进行，性能测试环境由对应产品的集成测试团队提供（基于过程库构建）；如评估没有性能影响，则可以申请SCCB讨论决议跳过性能测试，并且提交质量效能团队备案；性能测试需要在版本正式发布前至少提前半个月向性能测试团队发起申请，性能测试团队在接到性能测试单后，按照要求，在1~2周内完成性能测试，并输出测试报告作为性能单附件；如果性能测试无法按时完成，性能测试团队要及时预警，避免版本发布计划受到影响；
4. **正式发布**：规划版本正式发布推送受控库之前，至少要在过程库停留一周时间，以经过充分的联调和测试验证；（特殊情况可以例外，例如：trunk分支的紧急补丁。）版本发布前，CMO派发的版本确认单流转时，要提供对应版本的版本发布说明（Release Notes）以及性能单号，集成测试报告，CMO根据性能单获取性能测试报告，并随版本发布；

## 版本演进

### RoadMap

#### ZSmart_CORE_R9 Support

- 每半年发布一个规划版本，间隔3个规划版本发布一个长维护周期版本 （LTS版本）
- 常规规划版本生命周期包含长达9个月的全支持周期，以及3个月的维护期，生命周期总共12个月
- 长维护周期版本，除了包含常规规划版本生命周期，额外提供长达24个月的超长维护期。
- **全支持周期**：版本发布日后9个月内为版本全支持周期，定期发布版本新增功能特性、修复紧急安全补丁、产品bug修复。
- **维护期**：新版本发布后的第10-12个月为版本常规支持周期，此周期内只会定期发布bug修复补丁，不会发布新的功能。
- **LTS版本超长维护期**：每隔固定版本提供一个稳定版本（LTS版本），提供额外维护期，服务等级和内容保持维护期水平，主要用于希望长期稳定版本不升级的用户场景，最长版本服务支持周期3年。

> 第三方开源软件的大版本升级存在兼容性风险，默认只会在新版本迭代时进行，不会出现在版本全支持周期，维护期。
>
> 商务维保合同建议根据是否需要升级版本来评估成本和报价，例如：
> 例1：客户在整个维保周期内，没有开源软件安全治理需求，那这种情况就只要使用 LTS版本即可，最长可以支持3年。 如果维保合同超过3年，则根据升级次数重新报价。
> 例2：客户在整个维保周期内，有要求做开源软件安全升级，那这种情况需要根据这个 Roadmap去计算整个维保合同内的最小升级次数，按照每次升级的成本来报价。

#### ZSmart_CORE_R8 Support

- 每2个月发布一个规划版本
- **需求周期**：版本发布前2个月内为版本需求周期，支持在该版本上做定制化需求、bug修复、安全升级
- **维护周期**：版本正式发布后的6个月内为产品维护周期，只支持bug修复，不支持定制化需求开发、安全升级
- **技术支持周期**：维护周期结束后的6个月内为技术支持周期，只提供技术支持，不提供定制化需求开发、bug修复、安全升级；
- 常规规划版本生命周期包含长达6个月的维护周期，以及6个月的技术支持周期，生命周期总共12个月
- 提供企业级长维护周期版本（Enterprise Support），提供额外维护期，服务等级和内容保持维护期水平，主要用于希望长期稳定版本不升级的用户场景，最长版本服务支持周期3年。

### 安全治理策略

框架针对托管的第三方开源软件做集中式治理，产品线集中式升级和回归验证，避免频繁的变更对项目带来不稳定因素；治理周期参考本规范前文RoadMap相关章节；

# 版本质量管理

## 产品管理委员会（SCCB）

### 组织结构

- 委员会主席：由框架产品经理担任，负责会议的召集、主持和决策的最终批准。
- 固定成员：框架研发负责人，各产品线质量总监，GTSC交付总监，CMO
- 非固定成员：各产品线研发总监，各产品线产品经理，其他可能人员

### 职责

1. 变更管理：SCCB负责评估和管理项目中的变更申请。当项目发生变更时，团队成员可以向SCCB提交变更请求，并由SCCB进行评估和决策。这样可以确保项目变更得到适当的审批和控制，避免对项目进度、成本和质量产生负面影响。
2. 项目决策：SCCB作为项目的决策机构，负责审批和决定关键事项。例如，当项目遇到重大问题或需要做出重要决策时，团队可以向SCCB提出建议，并由SCCB协商和决策。这可以确保项目在关键决策上得到各方的共识和支持。
3. 问题解决：如果项目执行过程中出现问题或障碍，团队可以向SCCB寻求帮助和支持。SCCB成员可以提供专业建议和解决方案，帮助项目克服困难，顺利实现项目目标。
4. 监督和控制：SCCB对项目的执行情况进行监督和控制，确保项目按照计划进行，并满足质量要求。SCCB可以要求项目团队提供项目进度、成本和质量等方面的报告，并对项目执行情况进行评估和审查。

### 会议频率

原则上1个月组织一次SCCB例会，如有特殊情况，可由委员会主席或至少三名委员会成员提议召开临时会议。

### 会议议程

- 审查产品变更请求（CR），评估可能带来的风险，并制定相应的缓解措施。
- 对项目的执行情况进行监督和控制，确保项目按照计划进行，并满足质量要求。
- 讨论和解决版本发布过程中遇到的问题。

### 会议流程

* 预备会议： 由会议组织者提前一周准备会议议程，并分发给所有委员会成员。
* 会议开始： 由委员会主席宣布会议开始，并介绍会议议程。
* 议题讨论： 按照议程逐项讨论，每个议题由相关责任人进行汇报和讨论。
* 决策制定： 对于每个议题，委员会成员进行讨论并投票决定，投票结果由委员会主席宣布。
* 会议记录： 由委员会主席记录会议讨论内容和决策结果。

### 会议记录

会议结束后24小时内，委员会主席需将会议记录和决议发送给所有委员会成员，并存档备查。
