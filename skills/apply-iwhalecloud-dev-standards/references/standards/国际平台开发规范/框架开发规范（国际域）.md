# 前言

## 编写目的

- 统一 ZSmart Core 框架的使用方式，规范各模块的开发标准。
- 保障应用系统在异常处理、日志输出、配置管理、数据库访问、缓存、消息队列、批处理、安全、定时任务等方面的稳定性与可维护性。
- 避免因不当使用框架能力导致的生产事故（OOM、连接池耗尽、消息丢失、数据不一致等）。

## 适用范围

本规范适用于公司内部国际域所有基于 ZSmart Core 框架进行应用开发的业务团队，覆盖框架配置、核心 API 使用、模块依赖管理、Web 接口、数据库访问、缓存、消息队列、批处理与导出等全链路开发场景。

## 版本基础

本规范适用于Core8/Core9框架， 没有特殊说明规范适用范围的规范条目适用于所有框架版本。

## 角色和职责

- 开发人员：负责按照本规范进行编码，确保框架能力的正确使用。
- 架构师：负责评审模块依赖、线程池参数、连接池配置等关键架构决策。
- 运维人员：负责根据规范配置生产环境参数，确保 `handle-exception-enable` 等安全开关正确设置。

# 基础规范

## 模块依赖规范

### 【强制】通过 Starter 引入框架能力，禁止直接依赖核心模块

**说明：**

框架提供 28 个 starter 模块用于按需引入能力。业务应用应通过 starter 引入框架能力，而非直接依赖 `core-jdbc`、`core-cache` 等核心模块。Starter 确保传递依赖、自动配置、版本兼容性已由框架团队验证。

**正例**

```xml
<!-- 引入 Web 能力 -->
<dependency>
    <groupId>com.ztesoft.zsmart.core</groupId>
    <artifactId>core-boot-starter-web</artifactId>
</dependency>

<!-- 引入数据库 + MyBatis 能力 -->
<dependency>
    <groupId>com.ztesoft.zsmart.core</groupId>
    <artifactId>core-boot-starter-mybatis</artifactId>
</dependency>
```

<font color="red">反例</font>

```xml
<!-- ❌ 直接依赖核心模块，可能缺少必要的自动配置和传递依赖 -->
<dependency>
    <groupId>com.ztesoft.zsmart.core</groupId>
    <artifactId>core-web</artifactId>
</dependency>
<dependency>
    <groupId>com.ztesoft.zsmart.core</groupId>
    <artifactId>core-jdbc</artifactId>
</dependency>
```

## 配置管理规范

### 【强制】业务自定义配置禁止使用 ftf.\* 命名空间

**说明：**

框架所有配置项统一在 `ftf.*` 前缀下。业务自定义配置应使用自己的命名空间前缀，禁止使用 `ftf.*` 命名空间，避免与框架配置冲突。

核心配置前缀一览：

| 配置前缀           | 用途          |
| ------------------ | ------------- |
| `ftf.datasource`   | 数据源配置    |
| `ftf.transaction`  | 事务管理配置  |
| `ftf.cache`        | 缓存配置      |
| `ftf.mybatis`      | MyBatis 配置  |
| `ftf.mq`           | 消息队列配置  |
| `ftf.nbrtrace`     | Nbr 追踪配置  |
| `ftf.security`     | 安全配置      |
| `ftf.system`       | 系统配置      |
| `ftf.restResponse` | REST 响应配置 |
| `ftf.batch`        | 批处理配置    |
| `ftf.export`       | 导出配置      |

# 异常处理规范

## 异常分类与使用

### 【强制】所有业务异常必须使用 BaseAppException 或其子类抛出

**说明：**

`BaseAppException`（`com.ztesoft.zsmart.core.exception.BaseAppException`）是框架统一的异常类型，提供以下核心能力：

- **异常分类**：区分业务错误（`BUSS_ERROR = 0`）和系统内部错误（`INNER_ERROR = 1`）
- **异常嵌套与类型继承**：当 `BaseAppException` 包装另一个 `BaseAppException` 时，自动继承内层异常的错误类型
- **国际化支持**：`localeMessage` 字段独立于原始 `desc`，支持前端国际化展示
- **模块标识**：通过 `LogModule` 标记异常来源模块
- **追踪信息**：`getDetailMessage()` 方法返回包含错误码、国际化消息和原始描述的完整信息

**正例**

```java
// 业务异常
throw new BaseAppException("BILL_001", "账单不存在", BaseAppException.BUSS_ERROR);

// 系统异常，包装原始异常
try {
    // database operation
} catch (SQLException e) {
    throw new BaseAppException("DB_ERR_01", "数据库查询失败", BaseAppException.INNER_ERROR, e);
}
```

<font color="red">反例</font>

```java
// ❌ 直接抛出 RuntimeException，丢失错误码和类型信息
throw new RuntimeException("账单不存在");

// ❌ 使用通用 Exception，框架无法区分业务/系统错误
throw new Exception("操作失败");
```

### 【强制】构造BaseAppException或通过ExceptionHandler抛出异常时必须选择正确的异常类型

**说明：**

BaseAppException构造方法、ExceptionHandler#publish方法的众多重载方法中没有提供异常类型参数的重载方法默认异常类型为INNER\_ERROR， 业务研发在使用时必须仔细甄别， 业务异常场景必须手动指定异常类型；判断异常该用 `BUSS_ERROR` 还是 `INNER_ERROR`，遵循以下决策标准：

> **异常是由"外部输入/业务规则"触发的，还是由"系统自身基础设施"故障触发的？**

| 分类          | 触发源                          | HTTP 映射                 | 典型场景                                  |
| ------------- | ------------------------------- | ------------------------- | ----------------------------------------- |
| `BUSS_ERROR`  | 外部输入不合法 / 业务规则不满足 | 417 Expectation Failed    | 参数校验、权限检查、数据状态校验          |
| `INNER_ERROR` | 系统基础设施故障                | 500 Internal Server Error | 数据库故障、缓存故障、MQ故障、外部RPC超时 |

**正例**

```java
// 业务规则不满足 → BUSS_ERROR
throw new BaseAppException("BILL_001", "账单金额必须大于0", BaseAppException.BUSS_ERROR);
throw new BaseAppException("AUTH_001", "用户认证失败", BaseAppException.BUSS_ERROR);

// 系统基础设施故障 → INNER_ERROR
throw new BaseAppException("DB_ERR_01", "数据库查询失败", BaseAppException.INNER_ERROR, e);
```

<font color="red">反例</font>

```java
// 反例：将系统故障标为业务异常
throw new BaseAppException("CACHE_001", "缓存访问失败", BaseAppException.BUSS_ERROR);
// ❌ 缓存不可用是系统故障，不是业务问题！应使用 INNER_ERROR

// 反例：将业务校验失败标为系统异常
throw new BaseAppException("BILL_001", "账单金额必须大于0", BaseAppException.INNER_ERROR);
// ❌ 金额校验失败是业务规则不满足，应使用 BUSS_ERROR
```

## 异常处理配置

### 【强制】生产环境必须关闭 handle-exception-enable 配置

**说明：**

| 配置项                                     | 默认值  | 生产环境建议 | 说明                                                                                              |
| ------------------------------------------ | ------- | ------------ | ------------------------------------------------------------------------------------------------- |
| `ftf.restResponse.handle-exception-enable` | `false` | `false`      | 为`true` 时会将异常根因消息透出到前端响应体，可能导致敏感信息（SQL 语句、表结构、内部 IP 等）泄露 |

该配置 **仅在调试/测试环境开启，生产环境必须为 `false`**。

# 日志规范

## 【推荐】使用 ZSmartLogger 进行日志输出，禁止直接使用 SLF4J/Logback API

**说明：**

建议业务应用使用框架提供的统一日志输出工具类 `ZSmartLogger`（`com.ztesoft.zsmart.core.log.ZSmartLogger`）是框架的统一日志门面，提供了：

- 六种日志类型：APPLICATION、MESSAGE、FUNCPERFM、TRACE、HEARTBEATCHANGE、ALARM
- 自动 MDC 注入：operator\_id、busiId、host\_address、pid、threadId、module\_instance\_id、logSeq、module\_name
- 错误码自动提取：当日志参数包含 `BaseAppException` 时，自动从异常中提取 `errorCode` 写入 MDC
- 告警通道集成：`alarm()` 方法直接上报告警到 OPS 平台
- 性能指标上报：`stat()` 方法上报性能指标到 ZCM
- 日志脱敏集成：自动应用日志脱敏策略

**正例**

```java
// 获取类级别 Logger
ZSmartLogger logger = ZSmartLogger.getLogger(this.getClass());

// 带事务ID的info日志
logger.info(new TransId("TXN123456"), "订单处理完成, orderId: {}", orderId);

// 带错误码的error日志
logger.error(new ErrorCode("PAY_001"), "支付失败", e);

// 告警日志
logger.alarm(null, "ALARM_001", AlarmLevel.CRITICAL, "payment", "payFail", "支付通道异常");
```

<font color="red">反例</font>

```java
// ❌ 直接使用 SLF4J，丢失 MDC 自动注入和告警能力
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
Logger slf4jLogger = LoggerFactory.getLogger(this.getClass());
slf4jLogger.info("订单处理完成"); // MDC 中缺少 busiId、module_instance_id 等关键字段

// ❌ 使用 System.out 打印，完全不可追踪
System.out.println("debug info: " + data);
```

## 【推荐】业务Logback 配置文件引用框架日志模板

**说明：**

框架提供了满足鲲鹏日志规范的标准 logback 模板文件，同时内置了入SQL、Service、Boot等诸多阈值日志, 推荐业务应用在产品logback配置文件中引用(include)框架日志模板配置。

**正例**

```xml
<include resource="log/logback-docker-base-prod.xml"/>
```

## 【强制】日志必须输出到文件，禁止仅输出到控制台

**说明：**

容器化部署时，日志中心仅采集 `$HOME/log/` 目录下的日志文件，不支持采集 stdout/stderr，业务产品配置日志输出方式时必须保证日志不能仅输出到控制台。

**正例**

```properties
# logback 配置中指定日志输出路径
<appender name="STDOUT" class="ch.qos.logback.core.ConsoleAppender">
    <encoder>
        <charset>utf-8</charset>
        <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level %msg%n</pattern>
    </encoder>
</appender>

<logger name="SqlLog" level="${SQL_LEVEL:-${BASE_SQL_LEVEL}}" additivity="false">
    <appender-ref ref="STDOUT"/>
    <!-- 除控制台输出外， 日志还需要输出到日志文件中 -->
    <appender-ref ref="SQL_LOG"/>
</logger>
```

## 【推荐】在日志中携带错误码

**说明：**

框架 `ZSmartLogger` 支持传入 `ErrorCode` 对象，自动将错误码写入 MDC，便于日志检索和问题关联。

**正例**

```java
ZSmartLogger logger = ZSmartLogger.getLogger(this.getClass());
ErrorCode errorCode = new ErrorCode("BILL_001");
logger.error(errorCode, "账单查询失败", e);
```

# Web 接口开发规范

## 异常处理

### 【强制】业务 Controller 必须接入 Core REST 统一异常响应，禁止自行 catch 后吞异常

**说明：**

框架通过 `RestResponseEntityHandler`（`@RestControllerAdvice`）提供全局统一异常处理，自动将 `BaseAppException` 映射为标准 HTTP 状态码。Controller 方法中**禁止**自行 catch 异常后吞掉或返回非标准格式的错误信息，否则会导致：

1. 前端无法统一解析错误响应
2. 统一监控告警无法捕获异常事件
3. 错误码和国际化信息丢失

**正例**

```java
@RestController
@RequestMapping("/api/bill")
public class BillController {

    @PostMapping("/create")
    public ResponseEntity<BillDTO> createBill(@RequestBody BillRequest request) {
        if (request.getAmount() == null || request.getAmount().compareTo(BigDecimal.ZERO) <= 0) {
            throw new BaseAppException("BILL_001", "账单金额必须大于0", BaseAppException.BUSS_ERROR);
        }
        BillDTO result = billService.createBill(request);
        return ResponseEntity.ok(result);
    }
}
```

<font color="red">反例</font>

```java
@RestController
@RequestMapping("/api/bill")
public class BillController {

    @PostMapping("/create")
    public Object createBill(@RequestBody BillRequest request) {
        // ❌ 自行 catch 异常后返回 String，前端无法统一解析，监控无法捕获
        try {
            BillDTO result = billService.createBill(request);
            return result;
        } catch (Exception e) {
            e.printStackTrace();  // ❌ 吞掉异常，只打印堆栈，前端收到 200 但实际是错误
            return "创建失败";
        }
    }
}
```

## 审计日志

### 【强制】核心业务接口必须接入审计日志

**说明：**

审计日志（Audit Log）是运维审计和安全合规的基础数据。涉及**数据变更、资金交易、权限操作**等核心业务接口必须接入审计日志。

**审计日志配置参考：**

设置 `ftf.audit.log.type=local`，然后在 `ftf.audit.log.rules` 下以 Map 形式定义规则：

```properties
ftf.audit.log.enabled=true
ftf.audit.log.type=local

# key 可以任意命名（仅作为区分标识），value 是规则的 JSON 字符串
ftf.audit.log.rules.addUserRule={"serviceId":"com.ztesoft.zsmart.core.it.controller.ExportController.export","eventSource":"Core","eventType":"OPERATION","eventCode":"EXPORT","pattern":"${body.operator}在${body.exportTime}执行了导出操作","available":"Y"}
ftf.audit.log.rules.delUserRule={"serviceId":"com.example.UserController.deleteUser","eventSource":"Core","eventType":"OPERATION","eventCode":"DEL_USER","pattern":"${body.operator}删除了用户${body.userName}","available":"Y"}
```

**正例**

```properties
ftf.audit.log.rules.refundRule={"serviceId":"com.ztesoft.zsmart.bss.payment.PaymentController.refund","eventSource":"Bss","eventType":"OPERATION","eventCode":"REFUND","pattern":"退款操作：订单号${orderId}，退款金额${amount}元，操作人${operatorId}","available":"Y"}
```

```java
@RestController
@RequestMapping("/api/payment")
public class PaymentController {

    @PostMapping("/refund")
    public ResponseEntity<RefundResult> refund(@RequestBody RefundRequest request) {
        return ResponseEntity.ok(paymentService.refund(request));
    }
}
```

<font color="red">反例</font>

```java
// ❌ properties审计日志配置中不配置该接口方法
@PostMapping("/refund")
// ❌ 退款操作未接入审计日志，无法追溯谁在什么时间发起了退款
public ResponseEntity<RefundResult> refund(@RequestBody RefundRequest request) {
    return ResponseEntity.ok(paymentService.refund(request));
}
```

## 分页查询

### 【强制】分页查询返回 PageInfo 格式

**说明：**

分页接口必须使用 PageHelper 触发数据库分页，并让响应体包含 `PageInfo` 的分页元数据，例如 `total`、`pageNum`、`pageSize`、`pages`、`list`。业务代码可以显式返回 `PageInfo`；如果 Controller 方法声明返回类型为 PageHelper 的 `Page`，core框架 会通过 `PageInfoHandlerMethodReturnValueHandler` 在 `@ResponseBody` 写出前自动将需要总数的 `Page` 包装为 `PageInfo`。

> 注意：`PageInfoHandlerMethodReturnValueHandler` 只匹配方法声明返回类型为 `Page` 的场景；如果方法声明返回 `List`，框架不会自动包装为 `PageInfo`，将会丢失分页元数据。

**正例：显式返回 `PageInfo`**

```java
@GetMapping("/list")
public PageInfo<CustDTO> queryCustList(
        @RequestParam("pageIndex") int pageIndex,
        @RequestParam("pageSize") int pageSize) {
    PageHelper.startPage(pageIndex, pageSize);
    List<CustDTO> list = custService.queryByCondition(custName);
    return new PageInfo<>(list);
}
```

<font color="red">反例</font>

```java
@GetMapping("/list")
// ❌ 返回原始 List，丢失分页元数据，且框架不会自动包装为 PageInfo
public List<CustDTO> queryCustList(@RequestParam("pageIndex") int pageIndex,
                                   @RequestParam("pageSize") int pageSize) {
    List<CustDTO> all = custService.queryAll();  // ❌ 查询全量数据
    int start = (pageIndex - 1) * pageSize;
    return all.subList(start, Math.min(start + pageSize, all.size()));  // ❌ 内存分页，OOM 风险
}
```

## 批处理

### 【强制】大 Excel 文件必须启用 SAX 流式解析

**说明：**

当 Excel 文件大于 10MB 或行数超过 10000 行时，必须通过 `BatchInfo.setExcelSaxParser(true)` 启用 SAX 流式解析模式。传统 `XSSFWorkbook` 会将整个文件解析到内存，一个 100MB 的 Excel 在内存中可能膨胀到 500MB 以上。SAX 模式通过事件驱动的流式解析，在任何时刻仅持有当前行数据的内存。

**正例**

```java
BatchInfo batchInfo = new BatchInfo();
batchInfo.setCls(MyDealInterface.class);
batchInfo.setBatch(500);
batchInfo.setExcelSaxParser(true);  // 启用 SAX 流式解析
```

<font color="red">反例</font>

```java
// ❌ 大 Excel 未启用 SAX 解析
BatchInfo batchInfo = new BatchInfo();
// 未设置 excelSaxParser，默认 false

// ❌ 使用 XSSFWorkbook 直接读取大文件
XSSFWorkbook workbook = new XSSFWorkbook(fis);  // 极易 OOM
```

### 【强制】批处理任务必须配置合理的线程池参数，禁止使用无界队列

**说明：**

1. 必须使用有界队列
2. 拒绝策略不允许使用 DiscardPolicy
3. 核心线程数需经过压测

```properties
ftf.batch.upload.deal-thread-pool-core-size=4
ftf.batch.upload.deal-thread-pool-max-size=8
ftf.batch.upload.deal-thread-pool-queue-size=4
```

### 【强制】批量处理必须分批进行，单批不能超过配置上限

**说明：**

通过 `BatchInfo` 的 `batch` 属性控制每批处理的数据行数。单批次处理量不能超过 5000 行。过大的批次会导致单次事务时间过长、锁竞争加剧、GC 压力升高。

**正例**

```java
batchInfo.setBatch(500);  // 每批 500 行
```

<font color="red">反例</font>

```java
batchInfo.setBatch(50000);  // ❌ 单批 50000 行，事务过长
```

## 文件导出

### 【强制】导出 CSV/Excel 时必须启用危险字符转义（防 CSV 注入）

**说明：**

攻击者可以通过构造以 `=cmd|'/c calc'!A0` 开头的数据字段，在用户打开导出文件时执行命令。框架的 `convert()` 方法会对危险字符进行转义（在危险字符前后添加 `"\'"` ，数字前加制表符等）。

**正例**

```properties
ftf.batch.export.enable-convert-unsecurity-words=true
ftf.batch.export.convert-unsecurity-words=+,-,=,@,.,cmd,<,>
```

<font color="red">反例</font>

```properties
# ❌ 生产环境禁止关闭
ftf.batch.export.enable-convert-unsecurity-words=false
```

**注意**: CSV 导出自动将 ASCII 逗号替换为中文逗号，数字前加 \\t 防 Excel 自动转换; 如果导出的 CSV 需要被其他系统程序化解析（而非人工在 Excel 中查看），建议改用 XLSX 格;式导出。

### 【强制】导出记录数必须受控，禁止无边界的全量导出

**说明：**

导出链路通常会把查询结果转换成 Excel/CSV/PDF/HTML 等文件内容，如果不限制导出记录数，单次请求可能拉取大量数据库数据并在应用内存中组装文件，导致数据库压力升高、接口长时间占用线程、响应超时、Full GC 甚至 OOM。

对于 `CommonExportController` 和 `FrontDataExporter`，框架已有默认上限，超限时会直接中断导出并抛出异常，用户侧表现为导出失败。对于自定义 `CustomExport`，框架无法感知业务查询总量，也不会自动分页兜底；如果业务代码直接全量查询再导出，风险会转移到应用和数据库，严重时可能拖慢整个实例。

| 导出路径               | 上限                         |
| ---------------------- | ---------------------------- |
| CommonExportController | 默认65535 条                 |
| FrontDataExporter      | 2000 条                      |
| CustomExport           | 无框架硬限制，需自行控制分页 |

**正例**

```java
// 分页导出，每批 5000 条
int pageSize = 5000;
ExportPage page = new ExportPage();
page.setPageSize(pageSize);
while (true) {
    List<Map<String, Object>> data = loadDataByPage(pageIndex, pageSize);
    if (data.isEmpty()) break;
    exporter.exportOneBatch(data, page);
    pageIndex++;
}
```

<font color="red">反例</font>

```java
// ❌ 一次性查询全表数据导出，200 万条数据可能导致 OOM
List<Map<String, Object>> allData = mapper.selectAll();  // 无分页，全量加载
exporter.exportOneBatch(allData, ...);
```

# 数据库访问开发规范

## JDBC API 使用规范

### 【强制】LOB 数据读取必须控制长度

**说明：**

Core MyBatis 的 LOB TypeHandler 会根据 `LimitLobLengthThreadLocalContext` 判断是否限制 CLOB/BLOB 读取长度，长度上限由 `ftf.mybatis.lob-limit-length` 配置控制。默认开启限制；确需读取完整 LOB 时，必须把关闭范围控制在当前代码块内，并在 `finally` 中恢复。

**不按规范的风险：**

如果长期关闭 LOB 长度限制，单次查询可能把超大 CLOB/BLOB 全量读入内存，导致接口响应变慢、Full GC、内存飙升甚至 OOM。若线程复用场景下未及时恢复 ThreadLocal 状态，还可能影响同一线程后续查询，使其他普通查询也绕过 LOB 长度保护。

**正例**

```java
LimitLobLengthThreadLocalContext.open(); // LOB 长度上限由 ftf.mybatis.lob-limit-length 配置
try {
    result = mapper.selectByPrimaryKey(id);
} finally {
    LimitLobLengthThreadLocalContext.close();
}
```

### 【强制】SqlUtil.unlimitResutlSet()只能在最小范围内使用并及时清理

**说明：**

确需临时放开结果集限制时，必须限定在当前线程、当前代码块和可控数据量场景，并在 `finally` 中恢复上下文。禁止在入口方法、公共工具方法或长链路调用中放开限制。

SqlUtil.unlimitResutlSet() 会关闭当前线程的结果集行数限制，查询将绕过 ftf.sql.limit-result-set 的硬限制和告警保护。如果未在 finally 中恢复，后续 SQL 可能继续不受限制地拉取大结果集，造成数据库压力升高、应用内存膨胀、接口超时甚至 OOM。同时框架会统计关闭结果集限制的并发数，滥用该能力还可能触发并发关闭限制异常。

**正例**

```java
try {
    SqlUtil.unlimitResutlSet();
    exportSmallWhitelistData();
} finally {
    SqlUtil.limitResutlSet();
}
```

<font color="red">反例</font>

```java
// ❌ 禁止临时关闭sql结果集限制后不恢复
public void query() {
    SqlUtil.unlimitResutlSet();
    mapper.queryAll();
}
```

### 【推荐】数据库当前时间统一使用 DBDateUtil.getCurrentDBDateTime()

**说明：**

涉及创建时间、更新时间、审计时间、状态流转时间、流水号时间等需要与数据库数据保持一致的场景，必须以数据库时间为准，推荐使用框架的 `DBDateUtil.getCurrentDBDateTime()` 获取数据库当前时间。

禁止直接使用 `new Date()`、`LocalDateTime.now()` 等应用机器时间作为业务入库时间。应用服务器时间可能与数据库时间不一致，尤其在多节点部署、容器迁移、NTP 漂移、跨时区部署时，容易出现创建/更新时间倒挂、状态流转顺序异常、审计日志时间不可信、按时间分区或按时间查询结果不准确等问题。

`DBDateUtil.getDBDateTime()` 在源码中已标记为 `@Deprecated`，且返回类型为 `java.sql.Date`；新代码统一使用返回 `java.util.Date` 的 `getCurrentDBDateTime()`。

**正例**

```java
Date dbTime = DBDateUtil.getCurrentDBDateTime();
```

<font color="red">反例</font>

```java
// ❌ 禁止数据库当前时间使用应用机器时间
Date now = new Date();
```

### 【强制】序列号和流水号必须使用 SeqUtil 工具类或框架提供的序列服务

**说明：**

业务主键、流水号、序列值必须通过框架 `SeqUtil` 或数据库原生序列能力统一生成。禁止通过查询最大值后加一生成编号，否则会导致

1. 在并发场景下会产生重复号。
2. 插入数据库产生主键冲突
3. 绕过序列缓存和步长控制，降低性能
4. 多数据源/路由场景可能生成错误编号

**正例**

```java
//普通单实例数据源
Long orderId = SeqUtil.getSequenceId("SEQ_ORDER_ID");
//路由数据源
Long routeOrderId = SeqUtil.getSequenceIdWithPrefix("SEQ_ORDER_ID");
```

<font color="red">反例</font>

```java
// ❌ 禁止通过 max + 1 生成序列号，高并发下会产生重复编号
Long orderId = jdbcTemplate.queryForObject("select max(order_id) + 1 from orders", Long.class);
```

## 多数据源、读写分离与路由规范

### 【强制】读写分离上下文必须在获取连接前设置

**说明：**

Core 数据源路由依赖线程上下文。事务开启或首次数据库访问后，连接已经绑定到当前线程，此时再切换读写分离上下文不一定生效。读请求、写请求、强制主库读取等路由意图必须在 DAO 调用前确定。

**正例**

```java
SqlUtil.setJdbcType("readmysql");
try {
    return custMapper.queryCust(custId);
} finally {
    SqlUtil.setTargetJdbcType();
}
```

<font color="red">反例</font>

```java
// ❌ 禁止在事务开启或首次访问数据库后切换读写分离上下文
@Transactional
public void updateAndQuery(Long custId) {
    custMapper.updateStatus(custId);
    SqlUtil.setJdbcType("readmysql");
    custMapper.queryCust(custId);
}
```

### 【强制】路由数据源切换必须使用 try/finally 清理线程上下文

**说明：**

路由数据源通常通过 `RouteIDThreadLocalContext` 等线程上下文保存路由标识。Web 容器和线程池会复用线程，未清理上下文会污染后续请求，导致数据访问落到错误数据源。

**正例**

```java
RouteIDThreadLocalContext.set(routeId);
try {
    return orderMapper.queryOrder(orderId);
} finally {
    RouteIDThreadLocalContext.remove();
}
```

<font color="red">反例</font>

```java
// ❌ 路由上下文未清理，线程复用后可能污染后续请求
RouteIDThreadLocalContext.set(routeId);
return orderMapper.queryOrder(orderId);
```

### 【强制】禁止在同一事务中随意混用读写分离、路由切换和手工连接操作

**说明：**

Spring 事务开启后，事务管理器会从当前数据源获取连接并绑定到当前线程。同一事务内后续 JDBC/MyBatis 操作通常复用这条线程绑定连接，因此事务开始后再切换读库、写库或 routeId，可能不会重新获取连接，也可能造成同一业务事务访问多个不一致的数据源。手工获取、提交或关闭连接还会破坏事务管理器对连接生命周期的控制，引发读写库误用、脏读、连接泄漏、部分提交或数据不一致。

事务方法必须先确定数据源路由，再进入事务边界；一个本地事务内只处理一个明确的数据源上下文。确需跨库写入时，应拆分事务、使用可靠消息/补偿机制，或采用平台认可的分布式事务方案。

**正例**

```java
public void updateOrderOnRoute(String routeId, OrderDTO order) {
    RouteIDThreadLocalContext.set(routeId);
    try {
        orderService.updateOrderInTx(order);
    } finally {
        RouteIDThreadLocalContext.remove();
    }
}

@Transactional
public void updateOrderInTx(OrderDTO order) {
    orderMapper.updateOrder(order);
    orderLogMapper.insertLog(order.getOrderId());
}
```

<font color="red">反例</font>

```java
// ❌ 禁止在同一事务内写库后再切换读库
@Transactional
public void updateThenReadReplica(Long orderId) {
orderMapper.updateStatus(orderId);

SqlUtil.setJdbcType("readmysql");
orderMapper.selectById(orderId);
}

```

```java
// ❌ 禁止在同一事务内切换多个 route 并手工提交连接
@Transactional
public void updateTwoRoutes(OrderDTO order) throws SQLException {
    RouteIDThreadLocalContext.set("A");
    orderMapper.updateOrder(order);

    RouteIDThreadLocalContext.set("B");
    orderMapper.insertOrderArchive(order);

    Connection conn = dataSource.getConnection();
    conn.commit();
    conn.close();
}
```

## 事务开发规范

### 【强制】事务回滚异常必须以框架配置为准，禁止凭经验假设

**说明：**

Core 事务管理器支持通过 `ftf.transaction.rollback-exceptions` 配置默认回滚异常类型。当前框架默认配置以 `transactionConfig.properties` 为准，历史版本或项目配置可能存在差异。业务开发不得凭经验假设只有 `SQLException` 或只有 `RuntimeException` 才回滚，应在项目配置中明确确认。

如果未确认 `ftf.transaction.rollback-exceptions` 就凭经验判断回滚规则，可能出现“以为会回滚但实际已提交”的数据一致性问题。例如业务抛出的是 `BaseAppException`、普通 `Exception` 或自定义受检异常，但当前项目配置未覆盖该异常类型时，前面的 insert/update 可能已经提交，后续补偿困难。反过来，如果配置比预期更宽，也可能让部分原本希望提交的场景被统一回滚，造成业务状态与调用方预期不一致。

**正例**

```properties
ftf.transaction.rollback-exceptions=java.lang.Throwable
```

```java
@Transactional
public void importData() throws BaseAppException {
    mapper.insertData();
    throw new BaseAppException("IMPORT_001", "导入失败", BaseAppException.INNER_ERROR);
}
```

<font color="red">反例</font>

```java
// ❌ 未确认 rollback-exceptions 配置时，不能凭经验假设普通 Exception 一定回滚
@Transactional
public void importData() throws Exception {
mapper.insertData();
throw new Exception("导入失败"); // 未确认 rollback-exceptions 时，不得假设一定回滚
}

```

### 【强制】禁止事务方法静默捕获异常

**说明：**

事务依赖异常传播触发回滚。事务方法捕获异常后如果只记录日志并返回成功，事务管理器会认为方法正常结束并提交已执行的数据库操作。

事务方法吞掉异常后正常返回，事务管理器会按成功执行处理并提交事务，导致部分数据库操作已经生效，但调用链上层或外部系统可能认为业务已经被妥善处理。典型后果是订单已创建但库存未冻结、主表已写入但明细缺失、状态已流转但审计/消息未生成，形成半成功数据。后续只能靠人工修复或补偿任务处理，排查成本高，也容易引发重复提交、对账不平、幂等失效等连锁问题。

**正例**

```java
@Transactional
public void createOrder(OrderDTO order) {
    try {
        orderMapper.insert(order);
        stockMapper.freeze(order.getSkuId(), order.getQty());
    } catch (Exception e) {
        throw new BaseAppException("ORDER_001", "创建订单失败", BaseAppException.INNER_ERROR, e);
    }
}
```

<font color="red">反例</font>

```java
// ❌ 事务方法吞异常并返回 false，事务管理器会认为方法正常结束
@Transactional
public boolean createOrder(OrderDTO order) {
    try {
        orderMapper.insert(order);
        stockMapper.freeze(order.getSkuId(), order.getQty());
        return true;
    } catch (Exception e) {
        logger.error("创建订单失败", e);
        return false;
    }
}
```

## MyBatis 开发规范

### 【推荐】使用框架封装的Mybatis 功能

**说明：**

业务产品通过依赖 `core-boot-starter-mybatis`,引入框架封装的mybatis功能, 该模块提供了自动装配 MyBatis、分页插件、事务校验、安全 XML 语言驱动和多数据源支持。Mapper 扫描推荐使用框架提供的 `@CoreMapperScan`，确保框架增强能力生效。若未使用框架实现则需要产品里面保证可靠性。

**正例**

```java
@SpringBootApplication
@CoreMapperScan("com.ztesoft.demo.mapper")
    public class DemoApplication {
}
```

```properties
ftf.mybatis.auto=true
ftf.mybatis.mapper-locations=classpath*:mapper/**/*.xml
```

<font color="red">反例</font>

```java
// ❌ 使用原生 @MapperScan 可能绕过 Core MyBatis 增强能力
@MapperScan("com.ztesoft.demo.mapper")
    public class DemoApplication {
}

```

**注意：**

Core MyBatis starter 已提供一组安全默认配置，新项目原则上沿用默认值, 谨慎调整, 确需调整时必须评估 SQL 映射、事务校验、LOB 读取和缓存一致性影响。

| 配置项                                     | 默认/建议值                                                    | 说明                                   |
| ------------------------------------------ | -------------------------------------------------------------- | -------------------------------------- |
| `ftf.mybatis.map-underscore-to-camel-case` | `true`                                                         | 数据库下划线字段自动映射 Java 驼峰属性 |
| `ftf.mybatis.jdbc-type-for-null`           | `NULL`                                                         | 空值参数 JDBC 类型处理                 |
| `ftf.mybatis.transaction-verify`           | `true`                                                         | DML 事务校验                           |
| `ftf.mybatis.default-language-driver`      | `org.apache.ibatis.scripting.xmltags.SecuredXmlLanguageDriver` | XML SQL 安全语言驱动                   |
| `ftf.mybatis.lob-limit-length`             | `16777216`                                                     | LOB 默认读取上限                       |
| `ftf.mybatis.local-cache-scope`            | `SESSION`                                                      | MyBatis 一级缓存范围                   |

### 【强制】MyBatis 写操作必须纳入事务校验

**说明：**

Core MyBatis 默认开启事务校验，DML 操作必须在事务中执行。业务代码禁止随意使用 `@IgnoreTransactionVerify` 绕过校验，确需绕过时必须经过架构评审并说明原因。

**可能问题：**

- 多条 DML 不能保证原子性。前几条 SQL 已提交，后续 SQL 失败时无法整体回滚，容易出现半成功、半失败数据。
- 业务异常后数据仍可能已经提交。方法抛出异常时，调用方以为操作失败并回滚，但数据库实际已被修改。
- 同一业务流程中的 Mapper、`CoreJdbcTemplate`、手工 JDBC 可能不在同一个事务连接上，提交和回滚边界不一致。
- 数据状态可能短暂或长期不一致，例如主表更新成功、明细表插入失败，或库存扣减成功但订单状态未更新。
- 读写分离、路由数据源场景下，连接获取和数据源切换时机更难控制，可能写到错误数据源或读到不一致数据。

**正例**

```java
@Transactional
public void updateCust(CustDTO cust) {
    custMapper.updateById(cust);
}
```

<font color="red">反例</font>

```java
// ❌ 业务写操作禁止随意绕过 MyBatis 事务校验
@IgnoreTransactionVerify
public void updateCust(CustDTO cust) {
    custMapper.updateById(cust);
}

```

### 【推荐】路由数据源场景下不要使用 MyBatis 一级缓存

**说明：**

同一 SqlSession 内相同 statement 和参数可能命中 MyBatis 一级缓存。路由数据源切换或同一 SQL 需要访问不同数据源时，应避免在同一会话中复用缓存，必要时在 XML statement 中设置 `flushCache="true"` 或使用 `@Options(flushCache = Options.FlushCachePolicy.TRUE)`。

**可能问题：**

- 切换 route 后，相同 statement 和参数可能直接返回上一个 route 的缓存结果，出现串库、串租户或读到其他客户数据。
- 写库更新后再切到读库查询，或读库查询后再切回写库查询，可能读到会话内旧结果。
- 缓存对象如果被业务代码修改，后续相同查询可能拿到被污染的对象，导致判断、更新或返回值异常。
- 日志显示业务方法执行了，但 SQL 可能没有真正访问目标库，排查困难。

**允许使用前提：**

只有在确认同一 `SqlSession` / 同一事务内只访问一个明确的数据源或 route、同一 statement 和参数不会跨 route/读写库复用、业务能接受会话级重复读语义，并且增删改语句能正确触发缓存清理的前提下，才可以保留默认一级缓存。

路由数据源、读写分离、强一致查询或敏感数据查询场景，建议设置 `flushCache="true"`、使用 `@Options(flushCache = Options.FlushCachePolicy.TRUE)`，或将 `ftf.mybatis.local-cache-scope` 调整为 `STATEMENT` 后评估性能影响。

**正例**

```xml
<select id="queryById" resultType="CustDTO" flushCache="true">
    select cust_id, cust_name from cust where cust_id = #{custId}
</select>
```

# 安全开发规范

## 数据加密

### 【强制】Core 配置中的密码/密钥必须使用 KMS 或框架加密能力存储，禁止明文

**说明：**

业务应用中的所有密码、密钥、Token 等敏感配置值，必须使用框架提供的加密工具加密后再写入配置文件。

**正例**

```properties
ftf.datasource.password=ENC(AES256:xxxxxxxxxxxxxxxx)
ftf.cache.password=ENC(AES256:yyyyyyyyyyyyyyyy)
app.payment.apiKey=ENC(RSA2048:zzzzzzzzzzzzzzzz)
```

<font color="red">反例</font>

```properties
ftf.datasource.password=admin123         # ❌ 严重安全漏洞！
ftf.cache.password=redisP@ssw0rd          # ❌ 禁止明文存储密码
```

### 【强制】新开发接口优先使用 KMS 加解密能力，禁止继续新增框架旧加解密接口调用

**说明：**

框架原有加解密接口存在以下安全隐患，**新开发的业务接口禁止使用**：

**1. 算法本身不安全**

| 算法       | 安全问题                                                         |
| ---------- | ---------------------------------------------------------------- |
| `3DES-ECB` | ECB 模式不隐藏数据模式，易受统计分析攻击；有效密钥强度仅 112 bit |
| `TEA`      | 轻量级算法，存在等效密钥和 related-key 攻击风险                  |
| `MD5`      | 已被证明存在碰撞攻击，不应用于任何安全场景                       |
| `SHA-256`  | 仅提供哈希，不提供加密/解密能力，误用在加密场景无实际保护        |

**2. 密钥不支持轮转**

`CoreEncryptor` 通过本地配置 `ftf.security.encrypt.key` 注入静态密钥，无法做到定期自动轮转、泄露后紧急轮转、分应用隔离。

**3. 密钥长度不够安全**

| 算法     | 密钥长度                | 安全评估                           |
| -------- | ----------------------- | ---------------------------------- |
| AES-128  | 128 bit                 | 中等强度，量子计算场景下安全性不足 |
| 3DES-ECB | 192 bit（有效 112 bit） | 已被 NIST 标记为逐步淘汰           |
| TEA      | 128 bit                 | 密钥空间不足以抵抗暴力破解         |

**4. 密钥与代码耦合** — 本地配置模式的密钥存储在配置文件或代码中，代码仓库泄露导致密钥泄露，无法集中审计。

**5. 缺少审计能力** — 本地加密方案无法记录密钥访问记录，无法满足安全合规审计要求。

## 日志脱敏

### 【强制】日志输出前必须经过脱敏处理

**说明：**

为了符合日志安全输出规范，满足项目以及欧洲据点GPDR强制合规要求， 业务产品在适用框架日志工具ZSmartLogger输出日志时必须开启日志脱敏功能， 业务日志中禁止以明文形式输出密码、身份证号、手机号、邮箱、地址等敏感信息。框架在 Logback 层面集成了 `SensitiveMsgConverter` 和 `SensitiveMsgFilter`，实现日志自动脱敏。

**正例**

```java
ZSmartLogger logger = ZSmartLogger.getLogger(this.getClass());
CustInfo cust = new CustInfo();
cust.setIdCard("440101199001011234");
cust.setMobile("13800138000");
// 日志输出时，框架自动将身份证、手机号等字段掩码
logger.info(new TransId("TXN001"), "客户信息查询完成, cust: {}", cust);
// 实际输出：CustInfo(idCard=4401**********1234, mobile=138****8000)
```

<font color="red">反例</font>

```java
// ❌ 日志中直接打印敏感信息
logger.info("客户信息: 身份证={}, 手机号={}", cust.getIdCard(), cust.getMobile());
```

### 【推荐】对于Dto类型建议通过 SensitiveInfo 注解主动开启敏感字段脱敏

**正例**

```java
public class CustInfo {
    @SensitiveInfo(SensitiveType.ID_CARD)
    private String idCard;

    @SensitiveInfo(SensitiveType.MOBILE_PHONE)
    private String mobile;

    @SensitiveInfo(SensitiveType.PASSWORD)
    private String password;
}
```

<font color="red">反例</font>

```java
public class CustInfo {
    private String idCard;      // ❌ 缺少脱敏注解
    private String mobile;      // ❌ 缺少脱敏注解
    private String password;    // ❌ 缺少脱敏注解
}
```

### 【强制】返回前端的 DTO 必须标注敏感字段脱敏注解

**说明：**

所有返回前端的 JSON 响应中，敏感字段必须通过 `SensitiveInfo` 注解标注。

### 【推荐】启用第三方库日志脱敏

```properties
ftf.security.logMask.enabled=true
ftf.security.logMask.thirdPartyPkg=org.mybatis,org.apache.dubbo,com.alibaba.druid 
```
