## 说明

本文档旨在明确应用接入调用链及日志平台的标准流程与配置规范。关于平台功能的具体操作与使用说明，不在本文档范畴内。

### 名词解释

| 核心名词              | 概念说明                                                                                                                                                                       |
| :-------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Span（跨度）**      | 调用链监控中的基本工作单元。通俗地讲，代码中每执行一次重要的方法调用（如发起一次 HTTP/RPC 请求、执行一条 SQL 语句、调用一次内部方法等），都会生成一条记录，这条记录就是 Span。 |
| **Trace（调用链路）** | 一次完整的分布式请求调用过程。一条完整的 Trace 通常由多个相互关联的 Span 组成，记录了请求在各个服务间的流转轨迹。                                                              |
| **Agent（探针）**     | 挂载在应用进程中的监控组件，负责自动采集应用运行时的调用链（Span、Trace）及性能数据，并上报给服务端。                                                                          |

## 调用链部署和接入规范

### 基础镜像要求

> **说明**：当前调用链功能仅支持 JAVA 应用，暂不适配其他语言。

1. **基础镜像引用**
   ZCM 容器环境的标准基础镜像已完成调用链功能的集成。应用只需基于官方提供的 Tomcat 或 Java 基础镜像构建，即可完成接入。

   - 最新镜像列表请参考：[基础镜像发布页](https://docs.iwhalecloud.com/doi/c7dbhw)。
2. **环境变量配置**
   基础镜像通过 `APM_INIT` 环境变量控制调用链功能的启用。

   - **默认配置**：通常由 GTSC 在部署时通过租户环境变量或项目环境变量统一配置。
   - **自定义覆盖**：业务应用可通过应用级环境变量进行覆盖。
   - **生效规则**：若要启用调用链，请确保该变量值**不为空**（若为空值，则功能关闭）。

### JDK 版本要求

调用链 Agent 目前已适配并支持 **JDK 6 至 JDK 21** 全系列版本的应用接入。

### Spring 版本适配要求

- **Spring 5 及以下版本**
  默认支持，无需额外配置。
- **Spring 6**
  需设置环境变量 `SPRING_VERSION` 值为 `6` 以启用支持。
- **Spring 7**
  目前正在开发适配中。

### 资源预留要求（CPU & 内存）

调用链 Agent 与业务应用共享容器资源。为保障应用性能及监控数据的完整性，避免因资源竞争导致 OOM 或数据丢失，请务必预留足够的计算与存储资源。

1. 资源配置建议

| 资源类型 | 预留建议              | 说明                                                                                |
| :------- | :-------------------- | :---------------------------------------------------------------------------------- |
| **CPU**  | **0.1 ~ 1 Core**      | 用于保障 Span 生成、上下文传递及数据序列化处理。                                    |
| **内存** | **总内存的 5% ~ 10%** | 用于 Agent 运行内存及数据缓存（150M左右）。例如：2GB 堆内存需预留约 100MB ~ 200MB。 |

2. Agent 内存占用参考

Agent 内部维护了多个数据发送队列，以下为主要队列的预估内存占用情况，供资源规划参考：

| 数据队列类型   | 队列容量 (条) | 预估内存占用 |
| :------------- | :------------ | :----------- |
| Span 数据      | 10,240        | ~50 MB       |
| AgentStat 数据 | 10,240        | ~50 MB       |
| SQL 元数据     | 10,240        | ~10 MB       |
| API 元数据     | 10,240        | ~10 MB       |
| String 元数据  | 10,240        | ~10 MB       |

### 启动耗时影响与探针配置要求

接入调用链会增加容器启动阶段的耗时（Agent 下载与初始化）。为防止容器因超时被误杀，请务必调整健康检查探针配置。

1. 启动耗时增加说明

- **正常情况**：增加约 **2 ~ 5 秒**（Agent 下载及解压）。
- **异常情况**：若遇网络波动触发重试机制（30秒超时 x 1次重试），耗时可能延长至 **60 秒**。

2. 探针配置建议
   请在原有的 **就绪探针 (Readiness Probe)** 和 **存活探针 (Liveness Probe)** 延迟配置基础上，增加 **至少 60 秒** 的缓冲时间。

> **风险提示**：若未预留足够缓冲时间，可能导致容器在启动过程中被 K8s 误判为启动失败，进而触发无限重启或被标记为 Unhealthy。

### SQL 采集规范与限制

调用链默认采集并展示应用执行的 SQL 语句。为确保数据有效性及系统性能，请遵循以下开发规范：

1. 强制使用预编译
   必须使用 `PreparedStatement` 执行 SQL，**严禁使用字符串拼接**方式构建 SQL。

> **原因**：拼接 SQL 会导致大量无法聚合的 Unique SQL，造成调用链后端存储爆炸，且存在 SQL 注入风险。

2. SQL 长度限制
   单个 SQL 语句长度不得超过 **2000 字符**。

- **超长处理**：超过限制的 SQL 将被自动截断，详情页仅显示 `METADATA-OVERSIZED`，无法查看完整语句。
- **建议**：对于超长 SQL（如批量插入），建议拆分为多次小批量操作。

### 超长链路限制与优化建议

单条调用链路若包含过量 Span（如循环处理百万级数据），将导致平台查询 OOM 及数据写入异常。为保障稳定性，系统实施如下限制：

1. Span 数量限制

- **阈值**：单条链路最大支持 **200,000** 个 Span。
- **超限处理**：超出部分将被**自动截断**，平台仅展示阈值内的数据，且不保证剩余数据的完整性。

2. 优化建议

- **避免大循环**：禁止在单次请求中进行无限制或海量数据的循环处理。
- **链路拆分**：建议将大批量数据处理重构为 **分页处理** 或 **异步分批任务**，确保单次执行的 Span 数量控制在安全范围内。

> **风险提示**：违背此规范将导致关键监控数据丢失，并可能引发查询超时或平台服务崩溃。

### 导入导出文件大小限制

为防止 Zip 炸弹攻击及 OOM 异常，系统对调用链数据的导入导出功能实施严格限制：

1. 默认限制

- **大小上限**：**20 MB**
- **适用范围**：压缩包文件总大小及包内单文件大小。超过此限制将导致操作失败。

2. 调整配置（慎用）
   如确有需求，可在 `itracing-trace-service` 服务中配置以下环境变量进行调整（单位：字节 Byte）：

- `msp_file_upload_fileMaxSize`：压缩包总大小限制。
- `msp_file_upload_zipInnerFileMaxSize`：压缩包内单文件大小限制。

**配置示例**：
若设置为 `104857600`（100 MB），则允许导入/导出最大 100MB 的文件。

> **警告**：**强烈不建议**调大默认限制！处理超大文件极易引发服务端内存溢出（OOM），进而导致整个调用链服务不可用。

### 方法执行完整性要求

**禁止无限循环阻塞主流程**

调用链 Agent 仅在被追踪方法**执行结束**后才会采集并发送 Span 数据。若方法因死循环（如 `while(true)`）或长时间阻塞而无法返回，将导致：

1. **数据丢失**：该方法及其后续链路的监控数据无法上报。
2. **链路断裂**：调用拓扑图不完整，无法有效定位问题。

**规范**：

- 所有被追踪的方法必须具备明确的退出条件。
- 严禁在主线程或被追踪的业务逻辑中执行无休止的循环任务。

**异步任务超时截断机制（SGP 9.0.86+）**：

为防止异步任务长期阻塞导致资源泄漏，从 SGP 9.0.86 版本起引入了**2分钟超时截断机制**。
若异步 Span 创建时间距离当前时间超过 2 分钟，系统将自动终止跟踪并执行以下操作：

1. **生成提示事件**：提交 SpanEvent，明确提示异步跟踪已被终止。

2. **清理上下文**：清除相关跟踪上下文并释放资源。

3. **记录截断信息**：在调用链中追加提示信息：

   > "The asynchronous thread deviates from the main thread by 2 minutes and gets truncated."
   > （异步线程偏离主线程超过 2 分钟，已截断。）

**反例：**

```java
/**
 * 反例：被调用链跟踪的Controller方法或其内部调用的任务存在无限循环，导致span数据无法发送
 */
@RestController
public class InfiniteLoopController {

    // 线程池实例（实际应用中应避免这种方式创建线程池，此处仅为示例）
    private static final ExecutorService executor = Executors.newFixedThreadPool(1);

    /**
     * 处理请求的接口方法（假设该方法被调用链跟踪）
     */
    @GetMapping("/bad/loop")
    public String handleRequest() {
        // 提交包含无限循环的任务到线程池
        executor.submit(this::infiniteLoopTask);
        return "任务已提交（但将无限循环）";
    }

    /**
     * 包含无限循环的任务方法（被调用链跟踪的方法）
     * 因无退出条件，导致方法永远无法返回，调用链无法跟踪本方法以及下游应用的所有链路。
     */
    private void infiniteLoopTask() {
        // while(true)无退出条件，方法永远阻塞
        while (true) {
            try {
                // 模拟业务逻辑（实际中可能是扫描数据库或者MQ消费者相关的循环等待处理业务）
                ...
                System.out.println("执行无限循环任务...");
            } catch (InterruptedException e) {
                // 异常处理
            }
        }
        // 永远无法执行到此处，调用链span数据无法发送
    }
}
```

### 第三方组件适配要求

调用链的监控能力高度依赖于对第三方开源组件（如 Spring Boot、Dubbo、MySQL 驱动等）的字节码增强适配。

**核心原则：**

- **版本一致性**：仅支持《已适配开源软件版本清单》(附件) 中列出的组件版本。使用未适配的版本可能导致**链路断裂、数据丢失或服务异常**。
- **变更申请**：如需引入未适配的新版本组件，请务必提前联系调用链平台团队进行评估与排期。

### 业务代码获取 TraceId

业务应用如需获取当前调用链 ID（例如：用于日志关联或业务透传），可引入轻量级 SDK（无传递依赖）进行操作。

1. 引入依赖

```xml
<dependency>
  <groupId>com.ztesoft.zsmart.zcm</groupId>
  <artifactId>itracing-open-api</artifactId>
  <version>9.0.23</version>
</dependency>
```

2. 代码调用

```java
// 获取当前上下文的 TraceId（String 类型）
String traceId = ItracingContext.getEntity().getTraceId();
```

> **注意**：
>
> - 仅在应用**正确接入调用链**且当前线程**存在调用上下文**时，该方法才会返回有效的 TraceId。
> - 若未接入或无上下文，方法将返回 `null`，请注意判空处理。

## 日志中心部署和接入规范

### 基础镜像要求

ZCM 容器环境下，应用需基于 ZCM 标准基础镜像构建，并确保将日志输出到容器内的`$HOME/log`目录下。ZCM 容器平台会自动将容器内的`$HOME/log`目录挂载到宿主机的 `/tmp/zlogs/$CLOUD_APP_NAME/$DOCKER_CONTAINER_ID`路径下，部署在宿主机上的日志采集探针将从该宿主机路径下进行日志采集。

> 1. ZCM标准基础镜像参考上一章节 `调用链功能接入`相关介绍，`$CLOUD_APP_NAME`为应用名，`$DOCKER_CONTAINER_ID`为容器ID。
> 2. 日志输出到指定路径后，还需通过环境变量将 `日志类型`告知日志采集器，日志中心将日志输出格式，日志编码等信息抽象成 `日志类型`,并通过日志类型编码进行关联，日志中心对国际各产品线常用日志类型做了内置如下：

| 日志类型名称       | 日志类型编码 | 适用范围                  |
| ------------------ | ------------ | ------------------------- |
| 鲲鹏规范日志       | kp           | 基于ZSmart Core框架的产品 |
| 鲲鹏规范日志(计费) | kpcpp        | 国际计费产品（C++）       |

### 日志类型环境变量

为确保日志采集探针能够正确解析不同应用的日志格式，业务容器必须通过环境变量 `ITRACING_LOG_COLLECT_LOG_TYPE_CODES` 显式声明其输出的日志类型。

**配置指南：**

- **Java 应用**：适用于基于 ZSmart Core 框架的产品。

  - **变量值**：`kp`

  - **示例**：

    ```shell
    export ITRACING_LOG_COLLECT_LOG_TYPE_CODES=kp
    ```

- **C++ 应用**：适用于国际计费产品等。

  - **变量值**：`kpcpp`

  - **示例**：

    ```shell
    export ITRACING_LOG_COLLECT_LOG_TYPE_CODES=kpcpp
    ```

> **最佳实践**：建议在项目的 `Dockerfile` 中固化该环境变量，或在 ZCM 应用发布时的环境变量配置模块中统一进行设置。

### 采集模式一：Node模式 （默认）

日志中心默认通过 **Node 模式** 采集容器日志。该模式通过 DaemonSet 方式在 K8s 集群的每个节点上部署一个独立的 LogAgent 容器，统一负责该节点上所有业务容器的日志采集。

**工作机制**：
LogAgent 与业务容器通过挂载宿主机（Host）目录实现日志共享与采集。

**方案特点**：

- **优势**：

  - **资源效率高**：每个节点仅需部署一个 Agent，相比 Sidecar 模式（每个 Pod 独立部署 Agent），能显著降低 CPU 和内存消耗。
  - **规模效应**：集群规模越大，资源节省效果越显著。
- **限制与替代**：

  - **缺点**：依赖宿主机目录挂载权限。
  - **场景限制**：在部分第三方云平台或严格管控的环境中，若 K8s 禁止挂载主机目录，则该模式不可用。此时请考虑使用 **Sidecar 模式** 进行替代。

![image](uploads/259603/ac1a3372-9a09-4fba-a6f7-a28f71cdb776/image.png)

#### 挂载点路径和权限要求

为了实现日志文件的读取以及容器元数据的关联，LogAgent 必须挂载宿主机的关键目录。在配置 DaemonSet 时，请务必按照下表设置 Volume 挂载及对应权限：

| 宿主机路径 (HostPath)  | Agent 容器路径 (MountPath) | 用途说明                                                                                                | 权限要求                                                        |
| :--------------------- | :------------------------- | :------------------------------------------------------------------------------------------------------ | :-------------------------------------------------------------- |
| `/var/run/docker.sock` | `/var/run/docker.sock`     | 用于与 Docker 守护进程通信，获取容器、镜像及 Pod 的元数据信息。                                         | 建议配置为**只读 (ReadOnly)**，防止误操作影响底层 Docker 服务。 |
| `/tmp/zlogs`           | `/host/tmp/zlogs`          | 日志文件的物理存储位置。业务容器将日志落盘至宿主机的`/tmp/zlogs`，LogAgent 通过挂载该路径实现统一采集。 | 需确保宿主机目录存在，且 LogAgent 容器具备**读取权限**。        |

### 采集模式二：Sidecar 模式

**Sidecar 模式** 是指在每个业务 Pod 中部署一个专用的 LogAgent 容器（作为边车容器），独立负责该 Pod 内业务容器的日志采集。

**工作机制**：
LogAgent 与业务容器共享 Pod 内的存储卷（Volume），业务容器将日志写入共享 Volume，Sidecar LogAgent 从该 Volume 读取并上报日志。

**方案特点**：

- **优势**：

  - **环境隔离**：无需依赖宿主机路径挂载，符合 Serverless 或严格权限管控环境的要求。
  - **多租户友好**：每个 Pod 独立采集，互不干扰，适合多租户隔离场景。
- **缺点**：

  - **资源消耗高**：每个 Pod 都需要运行一个 LogAgent，随着 Pod 数量增加，集群整体的 CPU 和内存消耗会呈线性增长。
  - **维护成本**：Agent 数量与业务 Pod 数量成正比，升级维护工作量较大。

**适用场景**：

- K8s 集群禁止挂载宿主机目录（HostPath）。
- 使用 Serverless K8s（如 AWS Fargate, ASK 等）无法访问宿主机。
- 对日志采集有严格的租户隔离要求。

#### 挂载点路径与共享存储配置

Sidecar 模式要求业务容器与 LogAgent 容器通过 **共享 Volume**（通常为 `emptyDir`）进行交互。请参照下表配置 Pod 的 VolumeMounts：

| 业务容器路径 (MountPath)        | Agent 容器路径 (MountPath)      | 用途说明                                                              | 核心配置要求                                               |
| :------------------------------ | :------------------------------ | :-------------------------------------------------------------------- | :--------------------------------------------------------- |
| `/tmp/zlogs`                    | `/host/tmp/zlogs`               | 日志文件共享。业务容器将日志输出至此，LogAgent 从对应路径读取并采集。 | 业务容器与 Agent 容器必须挂载同一个`emptyDir` Volume。     |
| `/tmp/zcore/itracing-log-agent` | `/tmp/zcore/itracing-log-agent` | Agent 运行状态存储。用于存放采集位点（Offset）等运行时元数据。        | 必须配置持久化或共享存储，以确保容器重启后能实现断点续传。 |

### 硬件资源要求

为了保证 LogAgent 的稳定运行及高效采集，建议根据单节点的日志产出速率合理分配资源。下表展示了在不同资源限制下，Agent 所能支持的最大日志采集速率（条/秒）。

> **说明**：
>
> - **不稳定**：表示在该资源配置下，Agent 无法承受当前速率，会导致内存溢出（OOM）或频繁重启。
> - **日志速率单位**：表格中的 `0.5K/s` 表示每秒产生 500 条日志（单条日志平均大小为 0.5KB、1KB、1.5KB、2KB 时的评估）。
> - **CPU 单位**：m 代表 `millicores`（千分之一核）。例如 100m 即等于 0.1 Core（0.1个 CPU 核心），1000m 等于 1 Core。

> **💡 如何评估单条日志大小？**
> 单条日志的大小取决于日志内容的字符数（通常 1 个英文字符/标点 = 1 Byte，1 个中文字符 = 3 Bytes）。
>
> - **常规业务日志（~0.5KB）**：包含时间戳、线程、级别、类名及简短的业务提示信息。
> - **带参数的接口日志（~1KB）**：包含较长的请求/响应报文（JSON/XML 格式）。
> - **异常堆栈日志（2KB ~ 5KB+）**：包含完整的 Java Exception Stack Trace（例如带有 `at org.apache.dubbo...` 等数十行调用栈的报错日志），这类日志往往大于 2KB，对采集器性能消耗较大。

### 容器运行与日志输出规范

为确保日志采集的安全性与可靠性，请在应用容器化过程中严格遵守以下规范：

#### 1. 容器运行权限限制

**【强制】应用容器必须使用非 Root 用户启动。**

为保障宿主机安全及符合最小权限原则，所有接入日志中心的业务容器，其运行用户（User/UID）必须配置为非 root 账号。

**风险提示**：
若业务容器使用 root 用户运行，且日志目录权限被设置为 root 所有，LogAgent（非 Root 权限运行）将因 **权限不足（Permission Denied）** 而无法读取日志文件，最终导致日志采集失败。

#### 2. 容器标准输出（Stdout）采集限制

**核心限制：当前不支持采集容器的标准输出（Console/Stdout）日志。**

因为日志采集探针无法获取宿主机的 `docker` 权限（未挂载宿主机的 Docker Socket），也就无法获取容器控制台日志映射到宿主机的具体物理路径（`/var/lib/docker/containers/...`），所以不支持容器控制台的日志采集。

**接入要求**：

- 业务应用必须配置 Logback/Log4j 等日志框架，将日志输出到**文件**（输出路径：`$HOME/log/`）。
- **禁止**仅将日志打印到控制台（System.out/System.err），否则会导致日志无法被采集和存储。

### 高级日志特性接入

#### 日志贯穿功能

> **前置条件**：依赖调用链功能和日志中心功能，需先完成这两者的接入。

该功能通过全局事务号，将分散在不同应用、不同容器中的事务日志串联起来并提供集中查看的能力。其原理是解析业务日志，提取名为 `TranId` 的字段，并以此作为全局标记进行贯穿。通常使用调用链 ID 作为 `TranId`。

**接入方式**：
应用需在 `logback` 或 `log4j` 的 `PATTERN` 字段中通过 `MDC` 机制添加 `%X{PtxId}` 占位符，调用链会在运行时将调用链 ID 动态注入。基于 ZSmart CORE R9 框架的产品，已通过框架默认添加了该占位符。

业务应用需在应用级的 Logback 文件中，通过以下方式引用框架配置：

```xml
<include resource="log/logback-base.xml"/>
```

#### 号码跟踪功能

> **前置条件**：属于日志中心功能的子特性，需先完成日志中心接入。此功能为国际 BSS 产品线定制，依赖国际 R9 框架（需 `core-boot-starter-web` 启动依赖）。

在复杂的分布式系统中，排查业务失败问题往往需要在海量且多为 ERROR 级别的日志中寻找线索。号码跟踪功能提供了突破固有日志级别的能力，在设定的跟踪时效内，将符合特征（如特定号码）的所有级别日志强制输出，并串联集中查看，极大提升了排查效率。

**接入方式**：
在待接入应用中配置规则推送的 Zookeeper 地址。号码跟踪的规则配置会推送到 ZK，框架监听到规则变化后，会自动拦截请求并记录目标日志。

```properties
## 功能开关，默认开启
ftf.nbrtrace.zookeeper.enabled=true
## 号码跟踪 ZK 地址，用于存储跟踪规则，需与日志中心服务端配置保持一致（如有疑问请联系 GTSC）
ftf.nbrtrace.zookeeper.address=10.10.10.1:2181
```
