**前 言**

本文规定了浩鲸科技数据库模型设计的规范，并明确各角色的工作职责。

# 编写目的

本文用于描述浩鲸科技软件产品中数据库模型的设计规范（MySQL部分）。

# 适用范围

适用于业务相关的数据模型设计，涉及数据库的种类包含MySQL。

本文所指数据库模型仅包含表（表中主键、字段、索引），以及一些域表（定义见5.2.1.1节）的配置数据。

本文所指脚本范围不包含客服人员以维护系统或者割接为目的而使用的脚本，不包含数据库用户、权限、数据库实例等的建立和维护，此部分由相关集成部门提供，但建议各建库、运维等脚本也参考本标准规范。

# 角色和职责

1. SA：负责业务的概要设计和相关数据模型设计，并进行验证。

2. 测试：负责对数据库脚本进行第二次检查。

3. CMO：负责导出指定事务单中的相关数据库脚本，用于发布。

# MySQL数据库模型设计规范

## 基本设计规范

### 构成规范

【强制】数据库中各种名称必须以字母开头，但严禁使用sys开头。 **检查方式：**【工具检查（暂未支持）。检查工具：通过研发云的脚本录入界面检查，以下工具检查条目相同。】

【强制】名称只能含有字母，数字和下划线“\_”三类字符。 **检查方式：**【工具检查（暂未支持）】

【强制】表名要避免使用关键字，参见附录6.1 《MySQL保留字参考》。 **检查方式：**【工具检查（暂未支持）】

【强制】命名应采用能够准确反映其中文含义的英文单词或英文单词的缩写构成，避免出现英文单词和汉语拼音混用的情况。如果英文单词已定义了缩写，应该用缩写。缩写规则参见附录6.2《通用中英文对照及缩写表》，可以借助模型设计工具对配置表进行管理。【例外】政企产品的数据库由于特殊的市场环境，允许使用拼音。但也应避免中英文混用。 **检查方式：**【人工检查】

【推荐】在不同位置出现的、表示相同含义及内容的字段名称命名应该一致。

### 大小写规范

【强制】数据库中的数据库名、表名、字段名的所有字符，使用小写。【例外】第三方限制字段大小写的情况，比如：新电数据抽取DDL Mapping对大小写敏感，原字段名为大写的，修改字段长度时要保持大写。
【强制】如果使用PowerDesigner维护模型，则Database Generation界面Character case: 选择Lower。可以在生成建库脚本时自动把大写转成小写。方便从Oracle PDM向MySQL同步。

### 长度规范

【强制】所有对象标识符均不能超过30个字符，也即：MySQL中的表名、字段名，索引名的长度均不能超过30个字符。 **检查方式：**【工具检查（暂未支持）】

### 对象命名规范

【强制】针对规范发布以后的新版本和新产品，公司内部对各数据库对象统一命名，规范如下：

| **前缀缩写**         | **对象类型**        | **备注**                                                     |
| -------------------- | ------------------- | ------------------------------------------------------------ |
| 模块编码\_           | 数据库表 (产品版本) | 编码字符个数<=5 参考解决方案和产品模块缩写 【例外】多个模块公共表，可不设置模块前缀 |
| 项目编码\_模块编码\_ | 数据库表 (项目版本) | 同上                                                         |
| pk\_                 | 主键                | pk\_表名\_列名                                               |
| ux\_                 | 唯一索引            |                                                              |
| fx\_                 | 函数索引            |                                                              |
| idx\_ / ix\_         | 普通索引            | 电信集团采用ix\_开头                                         |
| tmp\_                | 临时对象            |                                                              |

**检查方式：**【工具检查（暂未支持）】

## 表

### 表的分类

此节为描述文字，用来明确表的分类。以便后续章节的规范使用表分类描述。非规范。

#### 域表（不提供配置界面，可以在程序中写死）

域表中的基础配置数据需要在程序中一一对应，即可以以'写死'的方式标记每条记录，增加或者修改记录都会引起程序变更。不提供配置界面。

例子：付款方式类型,paymeth_type表， 主键字段payment_type char(1),取值C、B等。

域表的表格式通常为xxx_type。此时主键字段名称和表名要保持一致，对应的数据类型为char(1)。表名格式也可以存在例外，如subs_event、all_serv_type，对应的主键和表名不一致。主键格式一般为表名\_id，对应的数据为类型
numeric(3) 或者numeric(6)。

域表的字段通常有三个：主键 char(1)/ numeric(3)/ numeric(6)、表名+_name
varchar(60)、comments varchar(120)/varchar(255)。

#### 配置表（提供配置界面，不可以在程序中写死）

配置表中的数据可以通过界面配置增加或者减少，对应的配置数据不能在程序中一一对应，即不可以以‘写死’方式标记每条记录。数据的增减不引起程序变更。

例子：证件类型，cert_type表，主键字段cert_type_id numeric(3)。

配置表的主键和表名一般不一致，格式一般为表名\_id，对应的数据为类型 numeric (3)
或者numeric(6)。配置表字段至少包含有三个：主键 numeric(3)/
numeric(6)、表名+_name varchar(60)、comments varchar(120)/varchar(255)。

#### 实例表（在运行过程中产生的生产数据）

资料表：类似订户、帐户、客户、个性化资费实例等保存客户资料的表。记录数量和现场用户数相当。

流水表：类似订单、账簿等和业务操作对应的表。通常数据量会随着时间推移不断快速增长。

### 表名

【强制】规范发布后的后续版本中，产品版本新增表名为模块名+正常表名。产品模块名参考行销团队发布的产品列表。【例外】多个模块公共表，可不设置模块前缀。 **检查方式：**【人工检查】

【强制】项目版本，项目缩写+表名。如EBS项目的表都ebs为前缀。 **检查方式：**【人工检查】

【推荐】对于表名还可以增加相应后缀做标识，即成：[项目编码\_模块编码\_]主体名\_后缀，另外，考虑到跨域实体，为了不影响理解，并保证命名的非二义性，可以在主体名前增加“子域名”作为前缀。

对于主体名，包含三个及三个以上单词的，建议采取缩写方式。

例如: 客户表 cust

客户信用度 cust \_credit

客户附加属性 cust_external_attr

【推荐】表名不使用复数名词。
说明：表名应该仅仅表示表里面的实体内容，不应该表示实体数量。

### 字段名称

#### 字段命名原则

【强制】不使用RDBMS的保留字作为字段名，比如alter、select等。 **检查方式：**【工具检查（暂未支持）】

【推荐】字段命名结构如下：BODY(主体名)_SUFFIX（后缀名）

例如: 客户编码 cust_nbr

其中，

- BODY为主体名，应该能够清楚地说明对象的含义,采用英文缩写；

- SUFFIX是后缀名，提供特殊的含义；

- 字段名称不能出现数据库中的关键字。

以下是一些特别的前后缀，代表了这个字段特殊的含义。在其他的情况，应避免使用以下的前后缀：

| **前后缀** | **定义**                                                                                                                                               |
|------------|--------------------------------------------------------------------------------------------------------------------------------------------------------|
| \_desc     | 参数表内的描叙字段 如字段名是offer_desc,表示销售品描述                                                                                                 |
| \_flag     | 布尔型字段                                                                                                                                             |
| \_nbr/no   | 编号字段                                                                                                                                               |
| \_num/_nbr | 号码字段                                                                                                                                               |
| \_id       | 标识字段                                                                                                                                               |
| \_type     | 类型字段，用来表示有类型含义的字段 如字段名是offer_type，表示销售品类型                                                                                |
| is\_       | 描述含有是否含义的字段,主数据值只有0/1或者N/Y两种情况，如is_default，表示是否默认 数据类型是char(1)（N/Y）或者unsigned tinyint （1表示是，0表示否）。  |

【推荐】表常备三字段：xxx_id, created_date,
update\_date表示主键、创建时间和更新时间。时间类型均为 datetime类型。

#### 说明字段

【推荐】描述、备注、说明用字段，使用comments varchar(120)/ varchar(255)/
varchar(4000)。

#### 状态及状态变更时间字段

【强制】状态变更时间state_date datetime –中国电信集团规范可用status_date datetime。 **检查方式：**【人工检查】

#### 时间字段

【推荐】生成时间用created_date datetime -中国电信集团规范可用create_date datetime；

【推荐】竣工时间用completed_date datetime；

【推荐】生效时间eff_date datetime；

【推荐】失效时间 exp_date datetime；

【推荐】记录创建时间rec_created_date datetime。

### 字段数据类型

【强制】布尔值字段：使用char(1)或者 unsigned tinyint。 **检查方式：**【人工检查】

【强制】固定长度字符串：使用char(n),长度根据需要定义。 **检查方式：**【人工检查】

【强制】可变字符串字段：使用varchar数据类型，对应长度为3/30/60/120/255/1000/4000。后续使用分库分表的表建议使用小值不超过255。 【例外】中国电信规范要求的可以按照集团规范使用的长度。 **检查方式：**【人工检查】

【推荐】数值字段：使用numeric数据类型，无小数，对应长度为3/6/9/12/15/18。实例表ID尽量取大（新增资料表为12位，流水表为15位或者18位），确保整个生命周期离最大值还差1到2个数量级。存储金额时需要15（超过15时java前台应用需要特殊修改）或者18。【例外】中国电信规范要求的可以按照集团规范指定的长度；
【例外】对金额字段，BSS域外或者原系统一直沿用的小数形式存放可以保持。

【推荐】数值字段：也可以使用int（tinyint、smallint、mediumint、int、bigint）,根据所存放的数据大小选择合适的子类型，且所有int类型都不使用长度限制。任何字段如果为非负数，必须是
unsigned。

【参考】合适的字符存储长度，不但节约数据库表空间、节约索引存储，更重要的是提升检索速度。
正例：无符号值可以避免误存负数，且扩大了表示范围。

| **对象** | **年龄区间** | **类型**          | **字节** | **表示范围**              |
|----------|--------------|-------------------|----------|---------------------------|
| 人       | 150岁之内    | tinyint unsigned  | 1        | 无符号值：0到255          |
| 龟       | 数百岁       | smallint unsigned | 2        | 无符号值：0到65535        |
| 恐龙化石 | 数千万年     | int unsigned      | 4        | 无符号值：0到约43亿       |
| 太阳     | 约50亿年     | bigint unsigned   | 8        | 无符号值：0到约10的19次方 |

【推荐】从性能考虑能用数字表达的不使用字符串。

【参考】可以使用int
unsigned存储IPV4。通过MySQL函数inet_ntoa（数字转化为IP）和inet_aton（IP
转化为数字）来进行转化。 多数据库通用的代码建议不要使用。

【强制】日期型字段：统一使用
datetime。注：本条是指时间类型用timestamp还是datetime。一些特殊场景，比如：考虑多种数据库兼容，日期使用字符串类型存放，不在此规范之列。 **检查方式：**【人工检查】

【推荐】大于4000个字节的字符串，可采用text类型字段。（如某些接口表存储xml数据的字段）。存储text的表和原表进行分拆，与原表主键组成新表存储，且每个表只允许有一个text系列类型字段。

【推荐】不要使用text来存储图片等特别大的数据。同时注意数据清理。

【推荐】字段尽量定义为not null，并设置默认值。不要使用default
null，所有的字段尽可能都设定为not
null并为其定义默认值。影响索引的统计信息和优化器的判断。复合索引中只要有一列含有NULL值，那么这一列对于此复合索引就是无效的。

【强制】不使用enum类型（设置值时极容易出错）。 **检查方式：**【工具检查（暂未支持）】

### 字段注释

【强制】要求每个字段有注释，默认中文便于理解，部分项目不能出现中文时用英文注释，或者在生成脚本时，配置管理员选择不生成注释的方式完成。 **检查方式：**【人工检查】

【强制】字段取值如果可以枚举，并且无对应域表时，需要在字段注释中针对每个字段取值进行枚举和含义解释。【例外】中国电信集团PDM中可以维护在standard
checks 中的list of values。 **检查方式：**【人工检查】

【推荐】字段取值非枚举，但一些特殊取值有特定的含义，比如：NULL值用于区分是优惠还是原费用的税记录，需要在字段注释中说明。

【推荐】字段注释、domain和配置表的区分使用：如果仅仅代码用于判断使用的字段，无需在界面展示，则可用字段注释说明字段取值含义。如prod表state字段，
subs_goods_inst表的state字段,acct表的state等字段。domain表和配置表的使用由设计时具体分析判断。

【参考】外键字段需要说明参照于哪个表。

【推荐】主键备注写明对应的序列。

【推荐】如果修改字段含义或对字段表示的状态追加时，需要及时更新字段注释。

### 主键

【强制】保证每个表有自己的主键，所有表必须显式定义主键，没有合适的字段，可以用自增列作为主键。 **检查方式：**【人工检查】

【推荐】主键最好设计成单一主键，尽量不用复合主键，尽量使用没有业务语义的字段作为主键，一般采用一个xxx\_id字段做主键，类型为int/numeric。

【强制】主键如果为自增列，数据类型必须为int或者bigint。  **检查方式：**【工具检查（暂未支持）】

【强制】主键在任何情况下不允许被更新。 **检查方式：**【人工检查】

【推荐】主键尽量选择数值类型字段，不选择字符串字段。

【推荐】不使用UUID、MD5、HASH这些作为主键。

### 约束

【推荐】尽量保证每个表的约束完整，仅针对有特殊性能或者数据归档需求时不需要约束。

【强制】考虑到数据量比较大的情况下外键对插入、删除的性能影响比较大。实例表上禁止建立外键，也不要作为外键的父表。数据参照完整性的保证在业务端实现。外键使父表和子表操作会相互影响，降低可用性。 **检查方式：**【人工检查】

【强制】对于需要做分库分表的表，不能建立外键。 **检查方式：**【人工检查】

【强制】作为表间连接关系的字段，数据类型必须保持严格一致，避免索引无法正常使用。 **检查方式：**【人工检查】

### 行记录长度建议

【推荐】一个表中的所有字段，尽量能存储在一个数据库（BLOCK）中，也即：表的单行字段总长度 < db_block。例如，MySQL数据库中基本block_size为16k，那么表的单行记录大小最好就小于16k。

### 大表的数据保留策略

【强制】大表需要有明确的数据保留策略。在设计阶段，需要明确业务字段的生命周期，并与数据生命周期匹配，制定表的数据迁移、归档、保留等策略。 **检查方式：**【人工检查】

【推荐】在表的物理设计阶段，建议每个表都添加几个有用的字段：记录创建日期、状态时间等，有助于分析记录中出现null数据或者数据丢失的原因。

### 临时表的清理机制

【强制】临时表需要业务本身考虑清理机制。业务确实需用中间临时表，设计时必须要考虑清理机制，表命名规范：tmp\_xxx。 **检查方式：**【人工检查】

【推荐】个人备份或临时表，必须使用维护用户创建，个人表以pers\_创建人名字全称\_为前缀，以跟业务用tmp\_临时表区分开，防止运维事故。

### 分区

【强制】不能使用分区表。  **检查方式：**【工具检查（暂未支持）】

## 索引

【强制】索引正常命名是idx\_表名/表名缩写\_字段名。（【例外】电信集团规范为ix_[pk]_tableshortname_columnshortname。
其中：ix：表示索引，普通索引；pk：用于主键的索引。）tableshortname：表名的缩写；columnshortname：索引字段名的缩写）比如：acct表的bank_acct_nbr字段索引
idx_acct_bank_acct_nbr。  **检查方式：**【工具检查（暂未支持）】

如果索引名称超30个字符，则idx\_表名单词首字母\_字段，例如基于ebs_subs_suspend_info表中的created_date字段建立索引，对应索引名称为idx_ssi_created_date。

【参考】不在区分度低的列上建立索引，例如：“性别”。

【参考】对于有些表的列，虽然列值就几个，但是如果要查询的某些值数量较少，则可以建索引
比如prod 表的prod_state。

### 关联查询的时候被引用对应列需要建立索引

【强制】关联查询的时候被引用对应列需要建立索引。未建索引，将有可能导致两个严重问题：

1. 两表做关联查询时性能低下。

2. 更新引用值或者删除行时性能很差。

**检查方式：**【人工检查】

### 建立联合索引需要谨慎

【推荐】需要结合单列查询考虑，决定前缀。

例如，对于表中两列col1、col2，其中col1列单独查询较多的情况下，一般倾向于建立col1在前的联合索引。

【强制】超过5个字段的联合索引需要避免。 **检查方式：**【工具检查（暂未支持）】

【参考】范围查询影响组合索引

组合查询中，如果有等值条件和范围条件组合的情况，等值条件在前，性能更高。

如where col1=2 and col2 >=100 and col2 <=120，此时是col1,col2的组合索引性能高过co2,col1的组合索引。

【推荐】需要考虑回表因素：

一般情况下，如果建索引可以避免回表（在索引中即可完成检测），也可考虑对多列建组合索引，不过组合索引列不宜超过5个。

例如：prod 表, 查询条件为prod_attr，结果为prod_attr,prod_attr_value字段。可以考虑在prod_attr, prod_attr_value字段上建立联合索引。

【推荐】如果有order by的场景，请注意利用索引的有序性。order by 最后的字段是组合索引的一部分，并且放在索引组合顺序的最后，避免出现file_sort的情况，影响查询性能。

正例：where a=? and b=? order by c; 索引：a_b_c 。

反例：索引如果存在范围查询，那么索引有序性无法利用，如：where a >10 order by b; 索引a_b 无法排序。

【推荐】建组合索引的时候，区分度最高的在最左边。 正例：如果where a=? and b=?，a列的值每条都几乎不同，接近于唯一值，那么只需要单建 idx_a索引即可。

### 单表索引个数

【强制】单表索引个数需要控制。不能超过5个，包含主键附带的索引。对于高并发DML操作的表中，超过5个以上的索引，如果记录数很大时，将会极大影响该表的更新性能；如果表业务主要侧重于读操作，可以根据业务需要建立适当个数的索引。 **检查方式：**【人工检查】

【参考】剔除掉多余的索引，一般来说，2个月内从未被用到过的索引均是多余的。

### 单表无任何索引

【参考】单表无任何索引需重视。

### 其他

【强制】业务上具有唯一特性的字段，即使是组合字段，也必须建成唯一索引。 **检查方式：**【人工检查】
说明：不要以为唯一索引影响了 insert
速度，这个速度损耗可以忽略，但提高查找速度是明显的；另外，即使在应用层做了非常完善的校验控制，只要没有唯一索引，根据墨菲定律，必然有脏数据产生。

【推荐】在varchar字段上建立索引时，如果字段内容比较长，可以使用前缀索引指定索引长度，没必要对全字段建立索引，根据实际文本区分度决定索引长度。

说明：索引的长度与区分度是一对矛盾体，一般对字符串类型数据，长度为20的索引，区分度会高达 90% 以上，可以使用 count(distinct left(列名,索引长度))/count(\*)的区分度来确定。

【参考】创建索引时避免有如下极端误解：
1）索引宁滥勿缺。认为一个查询就需要建一个索引。
2）吝啬索引的创建。认为索引会消耗空间、严重拖慢记录的更新以及行的新增速度。
3）抵制唯一索引。认为唯一索引一律需要在应用层通过“先查后插”方式解决。

【推荐】避免冗余和重复索引。尽量使用复合索引，而不是添加新的索引；比如索引idx1(a,b) 已经涵盖了索引idx2(a)，就可以考虑删除idx2(a)索引。

【强制】不在text、blob字段上建立索引。  **检查方式：**【工具检查（暂未支持）】

【推荐】避免在有NULL值的列上建索引。有索引（含组合索引）的列上不允许有NULL值。

## MySQL分布式数据库补充规范

这里描述的是在MySQL数据库规范基础上，使用分布式数据库时补充的一些规范要求。

### 基本规范

【推荐】自增列数据类型是无符号型。

【强制】禁止列设置字符集。 **检查方式：**【工具检查（暂未支持）】

【推荐】列不要使用bit数据类型。

【强制】不使用create table tbl_name like old_tbl_name；不使用create table tbl_name select statement。  **检查方式：**【工具检查（暂未支持）】

### 分片

【强制】关联表使用的分片算法一致。关联表数据拆分的节点必须相同。 **检查方式：**【人工检查】

【强制】所有分片表表结构必须一致。 **检查方式：**【人工检查】

【强制】使用union关键字的sql，要求其中涉及的分片表的分片规则及分片数一致，使用union all关键字的sql则无此要求。 **检查方式：**【人工检查】

【推荐】对分片和分表的规则，请根据具体选取的算法及分片数评估，避免数据条目都归集到同一个分片的同一个分表中。

【推荐】分表或分片字段尽量建立物理数据库索引，以提升查询速度。违反易导致查询时间长，数据库性能消耗高。

### 各种类型表占比

【强制】严格按照全局表的定义原则，非配置类型的表禁止设置成全局表，不符合定义为全局表的，建议调整成分片表，全局表的比例不超过10%。 **检查方式：**【人工检查】

【推荐】推荐的各种类型表占比：

| **表类型** | **比例规则** |
|------------|--------------|
| 分片表     | 大于60%      |
| 单片表     | 约30%        |
