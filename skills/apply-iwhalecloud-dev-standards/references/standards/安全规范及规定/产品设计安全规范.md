# 背景

安全开发生命周期（SDL）是一个帮助开发人员构建更安全的软件和解决安全合规要求的同时降低开发成本的软件开发过程。 安全应用从安全设计开始，软件的安全问题很大一部分是由于不安全的设计而引入的，微软用多年的经验总结出了安全开发生命周期（SDL），并提出了攻击面最小化、STRIDE 威胁建模等多种方法辅助安全人员对软件进行安全设计。安全设计对于软件安全的重要性尤为可见。

# 使用对象

本规范的读者及使用对象主要为设计人员，研发人员和测试人员等。

# 适用范围

该规范适用于产品研发安全设计。

# 术语定义

**说明：**某个规则的具体解释

**例外情况：**相应的规则不适用的场景

# 安全设计核心原则

SDL 安全设计核心原则:

Ø Attack Surface Reduction：攻击面最小化

Ø Basic Privacy: 基本隐私

Ø Least Privilege: 权限最小化

Ø Secure Defaults: 默认安全

Ø Defense in Depth：纵深防御

Ø Threat Modeling：威胁建模

## 攻击面最小化

攻击面是指程序任何能被用户或者其它程序所访问到的部分，这些暴露给用户的地方往往也是最可能被恶意攻击者攻击的地方。

攻击面最小化即是指尽量减少暴露恶意用户可能发现并试图利用的攻击面数量。打个比方说，某在线web应用向用户提供了一个通过搜索来获取帮助的功能，如果后端代码没有正确实现该功能就有可能导致存在SQL注入漏洞，但是即便如此，我们还是有办法降低或消除风险的，比如：

- 该帮助功能只能被授权的用户使用
- 后端代码对用户输入的数据进行了校验
- 帮助功能不支持搜索，只支持查看

可以看到，以上的第一、二点收缩了攻击面，即增加了攻击条件，减少了可以攻击的人数，而第三点则完全避免了风险，即攻击面完全消除了。其中第三点符合“简化系统设计”的原则，即不增加不必要的功能模块和特性。

## 基本隐私

用户使用软件时无可避免个人信息被收集、使用甚至分发，企业则有责任和义务建立保护个人信息的保护措施，抵御敌对攻击行为，确保用户基本隐私的安全性。隐私安全是建立可信任应用程序的关键因素。

在软件设计时考虑用户基本隐私的必要性及意义有:

- 履行法律规定和义务
- 增加客户的信赖

对于特殊的软件或者全球性的产品，设计人员需要明确软件的行为及针对人群。尤其要考虑当地国家的法律法规，如美国儿童网络隐私保护法COPPA(Children's Online Privacy Protection Act)等，企业在开发产品、服务时有必要制定明确的隐私准则。

Tips:

- 只收集程序必须用到的隐私数据，并明确告知用户并征得用户同意
- 对于用户隐私数据如密码、口令等均需要加密存储，最低要求是sha256+salt

## 权限最小化

如果一个应用程序或网站被攻击、破坏，权限最小化机制能够有效的将潜在损害最小化。常见的权限最小化实践如:

- 普通管理员/系统管理员等角色管理

- 文件只读权限/文件访问权限等访问控制

- 进程/服务以所需最小用户权限运行

  如果程序特定情况必须要较高级别的权限，也可以考虑特权赋予及释放的机制。

## 默认安全

在软件领域的含义就是：让默认的配置和策略尽可能的安全。在许多场合，安全和产品体验经常会发生冲突，这时候应当选择安全优先，在安全的前提下，可以允许通过手动关闭安全配置或策略来提升产品体验。

比如，产品应该默认打开密码复杂度策略，即不允许用户使用不符合密码复杂度策略的密码，但产品可以允许用户关闭这个策略来提升体验。

## 纵深防御

与默认安全一样，纵深防御也是设计安全方案时的重要指导思想。纵深防御包含两层含义：首先，要在各个不同层面、不同方面实施安全方案，避免出现疏漏，不同安全方案之间需要相互配合，构成一个整体；其次，要在正确的地方做正确的事情，即：在解决根本问题的地方实施针对性的安全方案。

纵深防御并不是同一个安全方案要做两遍或多遍，而是要从不同的层面、不同的角度对系统做出整体的解决方案。

Tips:

- 针对XSS的防护，除了要对用户输入的特殊符号进行过滤，还要区分是否是富文本进而进行相应编码操作，在输入过滤的同时在输出也进行过滤操作
- 即使做了过滤、编码等安全防护，为了更一步确保缓解 XSS 攻击，Internet Explorer 6 SP1 为 Cookie 引入了一个新属性，这个属性规定，不许通过脚本访问 cookie。Web 站点程序对 Cookie 启用 HTTP-Only属性后，可确保即使发生 XSS 攻击，也可以阻止通过脚本访问 Cookie 的操作

## 威胁建模

威胁建模是一种分析应用程序威胁的过程和方法。这里的威胁是指恶意用户可能会试图利用来破坏系统，和我们常说的漏洞并不相同。漏洞是一个特定的可以被利用的威胁，如sql 注入等。

作为 SDL 设计阶段的一部分安全活动，威胁建模允许安全设计人员尽在的识别潜在的安全问题并实施相应缓解措施。在设计阶段把潜在的威胁发现有助于威胁的全面和更有效的解决，同时也有助于降低开发和后期维护的成本。

威胁建模的一般流程如下:

- 与系统架构师及设计人员沟通，了解设计详情
- 使用成熟的威胁建模方法分析当前设计潜在的安全问题
- 提出安全建议及对潜在威胁的缓解措施
- 对安全设计进行验证并对整个设计方案进行回顾并再次确认

微软使用的威胁建模方法是 STRIDE 威胁建模方法。为了便于安全人员快速便捷的进行威胁建模，微软开发基于 STRIDE 威胁建模方法的 SDL ThreatModeling Tool2威胁建模工具，该工具可以帮助安全人员画数据流图、分析威胁、生成并导出威胁建模报告。

# 纵深防御

## 纵深防御介绍

基于上术的理论，纵深防御要从不同的层面、不同的角度对系统做出整体的解决方案。

## 纵深防御之分层

基于常见安全问题的特征，和我司的开发框架，我们将其进行分层：

| **层**           | **常见的问题**                                               |
| ---------------- | ------------------------------------------------------------ |
| 业务层           | ✪ 业务滥用，欺诈，信息滥用                                    |
| 安全功能需求     | 安全功能逻辑漏洞                                             |
| 应用接口安全     | ✪ 非法调用接口、非法请求数据、篡改请求、数据泄露、抵赖操作  |
| 应用安全配置     | 安全功能在项目上未开启                                       |
| 通用应用安全问题 | Xss,sql,xml注入                                              |
| 中间件配置       | Docker,tomcat,nginx等等中间件的权限控制，默认账号问题，弱口令 |
| 中间件已知漏洞   | 任意命令执行                                                 |
| 操作系统层       | 权限控制，默认账号，弱口令，多余的服务，任意命令执行         |
| 网络层           | Ddos, dos,信息泄漏，任意服务访问                             |
| 其他层           | 不同业务会有多余的层出现（物联网，云，工控）                 |

### 业务层的安全设计

✪ 这一层主要和业务开发团队强相关的需求，我们需要使用安全设计原则，基于业务逻辑进行安全设计，目标是做到让用户仅可以做产品开发人员设想的事。

例如：用户转账这种场景。

- 与业务强相关的，就是钱的处理。钱的数值有效的范围是：正数或0，小数点后有若干位。
- 基于攻击面最小化的原则：此功能所接受的参数应该是严格封装的，不允许处理任何多余的插入的参数。
- 基于基本隐私的原则：此功能需要保护转账双方的隐私。
- 基于权限最小化的原则：此功能需要限制用户仅可以运用自己账户的资金进行转账。
- 基于默认安全的原则：此功能需要在失败后，能将账号金额还原。

除此之外，由于业务的要求是，金额只能是正数或者0，需要保证，金额不能超出这个范围。

而由于转账时，可能会涉及误操作或其他风险，单次转账设置额度上限。

基于业务物特性，小数点后有若干位，那么在转账给不同系统时，需要保证小数点后的精度，不会出现A系统数度为0.001，B系统精度为0.01，A往B转账时丢失部分金额。

### 安全功能需求

✪ 这一层主要是常见的安全功能的需求，需要关注的主要是安全功能的核心能力，安全功能的标准，有效性，易用性，安全功能本身的逻辑问题。

例如：验证码。

- 首先需要明确验证码的核心目标，是防止机器人滥用接口。

- 基于防止机器人的需求（有效性原则）：功能需要保证能确认是机器人，还是人在对接口进行操作。

- 基于易用性的原则，验证码不能设计得人读不了。

- 基于功能的逻辑性，需要确保功能不被绕过，因此，验证码的验证需要和业务参数一同提交，服务器先验证验证码，后做业务请求。

### ✪ 应用接口安全

这一层主要是指，每一个具体功能需求中所涉及的安全问题。我司的业务开发团队需要关注的另一个重点：

实际上，在我司的开发业务中，在接口安全层，主要涉及的问题，只有如下几类：

- 绝大部分接口都需要在用户访问前确认用户是否已经登陆，且应该使用pot的session管理服务来获取用户的身份

- 确认用户是否有权限使用此功能，可以使用pot提供的rbac能力，从session中获取用户的信息，并利用rabc的校验模型，确认用户是否有权限使用接口或菜单，以防止用户访问其不可访问的接口，参考工单：2497987

- 确认用户是否有权限访问对应的数据，可以参考数字渠道的横向越权优秀实践，参考文档：

  横向越权最佳实践

- 确认哪些数据需要加密，加密后是否需要还原数据，可使用core框架的加密能力：AesEncryptor，选择256强度的算法，应用于需要还原明文的场景，sha256算法，用于加密后不需要还原明文的场景

- 确认用户是否可能会抵赖（使用重要操作记录日志方式，以使操作可追溯，缓解用户抵赖的风险，如果条件允许的话，在日志中加上用户的私钥签名，进一步加强防抵赖的强度）

- 确认是否会返回敏感数据

- 确认是否会在日志中打印明文口令，一般我们可以使用pot提供的日志过滤机制，将可能的关键字配置好，这样日志模块会自动将关键字相关字段过滤掉，不记录在日志中，如果业务开发没有使用pot的模块，那么需要自行在业务功能规避将敏感信息打印在日志中，以防止数据的泄露

- 重要业务接口，可以使用数字渠道产品线的消息体签名解决方案，来缓解黑客篡改请求带来的风险

- 当需要解析xml时，使用pot提供的xml解析器，或者自己引用解析器时，禁用外被实体功能，以缓解xml外部实体注入的风险

在我司的开发框架下，这一层是指，在业务产品开发和定制时，需要先打开业务框架的各种安全模块的开关：

例如

- 针对xss注入，业务开发团队可以对业务接口进行参数输入校验，仅接受符合规则的参数进入 以实现xss的防护。也可以使用pot团队开发的框架的能力Xssfilter ，来实现防护

- Csrfilter可以防止csrf攻击。

### 中间件安全配置和已知漏洞

在我司的开发模式下，中间件占比整个产品的75%以上，在引入中间件时，需要确保：

- ✪ 版本不存在高、中风险漏洞。

在引入中间件时，请去http://cve.mitre.org/搜索中间件关键字，确认版本是否存在高、中危漏洞

使用黑鸭子扫描，不存在高、中危漏洞

- ✪ 确保中间件的下载来源是可信源，如官方社区，或者阿里云开放的源，以防止黑客在包中植入木马。

- ✪ 关闭掉产品不使用的功能，以缓解黑客利用开源组件进行攻击的风险

- ✪ 确认业务可以使用到的中间件的功能，并将不使用的功能关闭

- ✪ 做必要的安全加固，以缓解黑客利用开源组件的配置漏洞进行攻击的风险

参考cis标准，或者中间件官方页面中的安全文档进行加固，实际上此原则主要包括如下几个方面：

​	1）权限最小化。例如：不可使用root启动应用程序，也不可使用root用户挂载网盘。Root用户是只有在万不得已时才能使用的权限

​	2）功能最小化

​	3）口令强度

​	4）传输加密以及加密强度和加密算法。例如，历史客户提出的问题，某中间件使用了ssl加密传输协议，但是允许的算法过于弱

如果存在困难，可以求助公司安全能力中心进行支持。

### 操作系统安全配置和已知漏洞

在我司的开发模式下，一般不需要业务产品进行操作系统层的安全事务处理。

在项目侧，需要实现的：

- 操作系统的版本不能存在中、高风险漏洞

在维护操作系统的镜像时，使用操作系统扫描工具nessus进行扫描，解决所有中、高风险漏洞，再发布至镜像仓库中。

- 操作系统需要基于cis进行安全加固

在操作系统层需要使用安全加固脚本进行加固，安全能力中心提供了加固脚本。

### 网络层安全

在我司，一般不需要业务产品团队做网络层的安全控制。

网络层的最基础的要求是做到隔离，更高的要求是要做到被攻击时能感知到。

在隔离这块，不同区域，不同业务，不同产品，不同服务之间，仅开放必要的入口，常见的网络隔离方法：

- 网闸

- 防火墙

- Vlan

- 云上的微隔离

在感知这里区分为不同层面的感知：

- waf,rasp，apigateway应用层感知。

- hids，蜜罐 主机层感知。

- ids,网络层感知

基于不同的业务场景和项目情况，需要选择不同的感知手段。

# STRIDE 威胁建模方法

## STRIDE 介绍

​    STRIDE 威胁建模是由微软提出的一种威胁建模方法，该方法将威胁类型分为    Spoofing（仿冒）、Tampering（篡改）、Repudiation（抵赖）、Information Disclosure（信息泄漏）、Denial of Service（拒绝服务）和 Elevation of Privilege（权限提升）。这六种威胁的首字母缩写即是 STRIDE，STRIDE 威胁模型几乎可以涵盖目前绝大部分安全问题。此外，STRIDE 威胁建模方法有着详细的流程和方法。

## 威胁建模流程

STRIDE 威胁建模的一般流程如下:

- 绘制数据流图
- 识别威胁
- 提出缓解措施
- 安全验证

#### 识别威胁

​    STRIDE 模型将不同类型的威胁分类:

| **类别**           | **Description**                                              |
| ------------------ | ------------------------------------------------------------ |
| **欺骗（仿冒）**   | 使用另一用户的身份验证信息，例如用户名和密码                 |
| **篡改**           | 恶意修改数据。 示例包括未经授权更改持久保存的数据（例如保存在数据库中的数据），更改通过开放网络（例如 Internet）在两台计算机之间传输的数据 |
| **否认性（抵赖）** | 指用户拒绝执行某个操作，但其他操作方无法证实这种拒绝无效 — 例如，购买某个产品的用户可能需要在收货时签收该产品。 然后，供应商可以使用签收单来证明该用户确实收到了包裹 |
| **信息泄露**       | 将信息透露给本应不该有权访问这些信息的个人 — 例如，用户能够读取他们未授权访问的文件，或者入侵者能够读取在两台计算机之间传输的数据 |
| **拒绝服务**       | 拒绝服务  (DoS) 攻击会拒绝向有效用户提供服务 — 例如，使 Web 服务器暂时不可用。 必须防范某些类型的 DoS 威胁，这只是为了提高系统的可用性和可靠性 |
| **特权提升**       | 无特权用户获得特权访问权限，从而拥有足够的访问权限来入侵或破坏整个系统。 特权提升威胁包括攻击者有效突破系统防御，成为受信任系统本身的一部分，这是非常危险的局面 |

STRIDE 威胁建模方法已经明确了每个数据流图元素具有不同的威胁，其中外部实体只有仿冒（S）、抵赖（R）威胁，数据流只有篡改（T）、信息泄露（I）、拒绝服务（D）威胁，处理过程有所有六种（STRIDE）威胁，存储过程有篡改（T）、信息泄露（I）、拒绝服务（D）威胁，但如果是日志类型存储则还有抵赖（R）威胁。具体可以对照如下表格进行威胁识别:

### 缓解措施

根据不同的数据流图元素及威胁，相应的缓解措施也不相同。如外部实体用户的仿冒威胁，其缓解措施简单来说就是对用户身份进行认证。对于一个 Web 应用来说，缓解仿冒威胁不仅需要较强的认证机制，还需要防止恶意攻击者用暴力破解、口令猜测等方法绕过认证从而造成仿冒用户的威胁。用户仿冒威胁的缓解措施举例:

- 对用户访问执行帐号密码、证书等身份认证;

- 用户帐号密码认证过程中，如果出现三次密码错误，则增加验证码机制。输入验证码且正确再进行身份认证;

- 当用户认证 5 次后仍然验证失败，则在 30 分钟内禁止该帐号登录;

- 用户密码必须包含数字、字母及特殊字符，且长度在 8 位以上，如果业务安全需要则增加密码过期机制，每隔 6 个月提醒用户修改密码;

​    在提出缓解措施时，有的时候不仅要考虑安全问题，同时也要考虑软件的易用性，所以不同的威胁，不同的应用场景。其缓解措施也要随之而改变以提高应用安全的同时也能给用户带来较好的交互体验。

# 常见安全缓解措施

## 审核和日志记录

**确保在应用程序中强制实施审核与日志记录**

登录认证日志：成功/失败的认证/登录、用户注销、超时退出、帐户锁定和用户注册等活动；

用户/权限管理：用户/权限的增删改以及密码的修改和重置等活动；

业务敏感数据访问：对IT基础设备和系统中的系统配置或者存储的数据进行操作(查询/修改/删除等)的活动等；

审核日志应捕获用户上下文。

**确保实施日志轮转和分离**

日志轮转是系统自动将陈旧的日志文件进行存档；

日志分离是指将日志文件存储在运行应用程序的不同分区中或将旧的日志移到其他目录

**确保应用程序不会记录敏感的用户数据**

​    检查是否未记录用户在站点中提交的敏感数据。敏感数据示例如下（各个项目可能会有不同的敏感数据要求）：

- 用户凭据

- 身份证号或其他身份信息

- 信用卡号或其他财务信息

- 私钥，或者其他可用于解密已加密信息的数据

- 可以用来增强应用程序攻击效果的系统信息或应用程序信息

## 身份验证

**使用标准身份验证机制向** **Web** **应用程序进行身份验证**

​    通过用户名和密码等凭据完成，包括但不限于web系统登陆，webservice请求等。

**应用程序必须安全处理失败的身份验证方案**

​    安全处理失败的身份验证机制：

- 在身份验证失败时拒绝访问特权资源
- 身份验证失败并且发生访问被拒绝后，显示常规错误消息
- 用户尝试失败次数过多后禁用账户

**安全实施忘记密码功能**

首先，输入用户名，进入到邮箱验证的页面，输入邮箱地址，判断用户名和邮箱地址是否匹配。（或增加手机短信验证）

第二，发送重置密码的链接到邮箱，通过登录邮箱进行密码重置；

第三，在获取新密码的过程正在进行时，不应锁定用户帐户；

第四，在新密码请求正在设置时，显示的消息应该普通化，防止用户名枚举；

第五，始终禁止使用旧密码并实施强密码策略。

**确保实施强密码和帐户锁定策略**

为了防范暴力破解和基于字典的猜测：必须实现强密码策略，确保用户创建复杂密码（例如，最小长度为 12 个字符，必须包含字母数字和特殊字符）。

帐户锁定策略：

- 软锁定： 每当用户输入错误的密码三次，应用程序会将其帐户锁定一分钟，以减慢暴力破解密码的过程；另一种做法是在达到失败尝试次数的阈值后实施验证码机制。

- 硬锁定：当检测到某个用户攻击应用程序时，应该应用这种类型的锁定并对其采取对策：永久锁定其帐户，直到响应团队对其取证。取证分析完成后，决定是要恢复该用户的帐户，还是采取进一步的法律措施。

**实施控制来防止用户名枚举**

在注册页等功能中，有时无法避免信息泄露。 在这种情况下，需要使用 验证码 等频率限制方法来防止攻击者的自动攻击。

## 授权

**处理业务逻辑流时按顺序执行各个环节**

业务系统确保处理流程按设定的流程顺序有序执行。

**确保实施适当的授权并遵循最低特权原则**

产品按角色划分权限，基于角色设置菜单权限，按钮权限，数据权限等。

**业务逻辑和资源访问授权决策不应该基于传入的请求参数**

检索某个用户的数据时，userID应存储在会话变量内部，应用程序从会话内部获取到userID到数据库检索数据。

**确保不可通过强行浏览来枚举或访问内容和资源**

不应在 web 目录中保留敏感的静态文件和配置文件。 对于不需要公开的内容，应该应用适当的访问控制或删除内容本身。

## 通信安全

**启用 HTTP安全通信协议HTTPS和SSL**

使用HTTPS+SSL确保通信安全。

## 异常管理

**不公开错误消息中的安全详细信息**

提供给用户的错误消息应不包含敏感的应用程序数据。 敏感数据示例：

- 服务器名称

- 连接字符串

- 用户名

- 密码

- SQL 过程

- 动态 SQL 失败详细信息

- 堆栈跟踪和代码行

- 内存中存储的变量

- 驱动器和文件夹位置

- 应用程序安装点

- 主机配置设置

- 其他内部应用程序详细信息

## 输入验证

**强化或禁用 XML** **实体解析防范XXE攻击**

如果应用程序不使用内部和/或外部 XML 实体解析，则必须完全禁用该功能；或者，如果绝对有必要使用此功能，需手动限制应用程序执行实体解析时可以消耗的内存和时间。

**确保上传文件时实施适当的控制**

上传的文件会给应用程序带来重大的风险。

应该针对文件上传功能实施以下安全控制：

- 文件扩展名检查（提供支持上传的文件类型白名单）

- 文件大小上限

- 不应将文件上传到 webroot；位置应是非系统驱动器上的某个目录

- 上传文件的名称采用随机命名的方式，防止文件覆盖

- 确保验证文件名和其他任何元数据（例如文件路径）是否包含恶意字符

- 检查文件格式签名，防止用户上传伪装的文件（例如，通过将扩展名更改为 txt 来上传 exe 文件）

**确保在 Web** **应用程序中使用类型安全的参数进行数据访问**

- 针对SQL注入使用预编译语句，对所有传入SQL语句中的变量做绑定，另外检查数据类型、使用安全的存储过程、使用安全编码函数等
- 对于特定场景，必须进行字符串拼接时，需要对传入的字符串参数进行安全检查

**在呈现之前为不受信任的 Web** **输出编码**

- 跨站点脚本（通常缩写为 XSS）使用 Web 保护库执行输入验证和输出编码

- 对COOKIE的LANGUAGE中XSS攻击增加白名单校验和输出编码的解决方式

**针对所有字符串类型的 Model** **属性执行输入验证和筛选**

​    传递未经净化的用户输入参数可能会导致代码注入安全漏洞

- 对输入参数进行验证
- 使用正则表达式设定允许列表进行验证

​    对于 Web 应用程序而言，入口点可能还包含Cookie、HTTP 标头和 Web 服务等参数。

**针对接受所有字符的富文本框应用净化**

- 使用 HtmlEncode 方法为字符串输入编码

- 过滤存在攻击的代码

- 采用白名单的方式允许解析某些标签

**验证应用程序中的所有重定向是否安全**

- 识别所有重定向

- 设定重定向允许列表

- 重定向是增加用户确认

## 敏感数据

**加密 Web** **应用配置文件中包含敏感数据的部分**

账户密码信息在配置文件中需要加密配置，保存在数据库中同样需要加密存储

**确保用户屏幕上显示的敏感数据经过屏蔽**

在屏幕上显示密码、信用卡号、身份证号等敏感数据时，不要显示明文信息。

## 会话管理

**缓解网页的跨站点请求伪造 (CSRF)** **攻击**

跨站点请求伪造（CSRF 或 XSRF），服务器向客户端发送一个附加令牌，要求客户端所有请求中包含该令牌（例如使用 CSRF-token），可以避免这种攻击。

**设置会话的非活动生存期**

会话超时是指用户登陆系统后在一段时间内不执行任何的操作。 当触发会话超时后，将用户会话的状态更改为“invalid”（即，“不再使用”）。

**通过应用程序实现适当的注销**

当用户按下注销按钮时，应用程序应销毁用户的会话，重置会话 Cookie 值并将其设置为 null，同时重置身份验证 Cookie 值并将其设置为 null。
