# 适用对象

使用分布式缓存产品的开发设计人员。

> **备注**：分布式缓存产品包含ZCache、ctgcache、开源Redis等

# 键值设计

## key名称设计

### 【建议】：可读性和可管理性

以业务名(或数据库名)为前缀(防止key冲突)，用冒号分隔，比如:  业务名:表名:id

```sh
ugc:video:1
```

### 【建议】：简洁性

保证语义的前提下，控制key的长度，当key较多时，内存占用也不容忽视，例如：

```sh
user:{uid}:friends:messages:{mid}
# 简化为
u:{uid}:fr:m:{mid}
```

### 【强制】：需要包含英文字母，并且不要包含特殊字符

key名称中可使用的字符包含：**英文字母**、**数字**，以及如下**关联字符**：冒号(`:`)、下划线(`_`)、减号(`-`)、大括号(`{}`)、点(`.`)

**<font color=red>反例:</font>**

- key名称中包含**空格**、**换行**、**单双引号**、**中文字符**以及其他**转义字符**
- key名称中只有数字
- key名称中只有关联字符

## value设计

### 【强制】：拒绝bigkey(防止网卡流量、慢查询)

- string类型最好控制在**10KB**以内，最大不要超过**32KB**
- hash、list、set、zset元素个数不要超过**5000**

**<font color=red>反例:</font>**

[UR2666614](https://zmp.iwhalecloud.com/queryFauDtl.action?faultId=2666614)：DXP使用的一个list类型的key，因为一直写入数据，而没有删除数据，并且key没有定期失效；导致数据量超过1200w

### 【推荐】：选择合适的数据类型

例如：实体类型，要合理控制和使用数据结构内存编码优化配置,例如ziplist，但也要注意节省内存和性能之间的平衡。

**<font color=red>反例:</font>**

```
set user:1:name tom
set user:1:age 19
set user:1:favor football
```

**正例**：

```
hmset user:1 name tom age 19 favor football
```

### 【推荐】：控制key的生命周期，redis不是垃圾桶

建议使用`expire`设置过期时间(条件允许可以打散过期时间，防止集中过期)，不过期的数据重点关注idletime

```shell
# OBJECT idletime 可用于查看指定key的空闲时间(单位：秒)
object idletime key
```

### 【建议】：缓存中应存储的是纯数据信息，而不是序列化的类对象

类对象序列化后包含的无用信息太多，相比于纯数据内容，实际内存和网络带宽使用量都会大幅翻倍，最终也会影响业务缓存访问的性能。

推荐使用**protobuf**进行数据信息的序列化/反序列化处理，业务解析性能非常高，而且能够有效降低数据占用的内存大小。

**正例**：

格鲁项目inv最初使用的用户实例资料使用类对象序列化存储，缓存使用量超过270GB，后来修改为使用**protobuf**来对数据信息序列化处理后，内存占用大幅降低到只有60G

## 访问设计

### 【强制】：避免热点key访问

**应对策略**：

- 将每次业务访问的key进行拆分，避免总是访问同一个key
- 对需要频繁访问的key进行本地缓存，本地缓存数据可以通过定时策略进行更新
- 优化业务处理逻辑，减少无效交互访问：例如一个服务里面有N次访问某个配置的逻辑，那么在服务逻辑开始时从缓存里面取一次配置就好，避免单一服务大量重复缓存交互

### 【建议】：防穿透

key对应的数据在数据源中不存在，每次访问缓存获取不到数据时，都会从数据源中查询，导致数据源压力非常大，影响系统性能，也容易被黑客利用攻击。

**应对策略**：

- 采用NullObject方式处理：如果缓存获取不到并在数据源也查询不到，则设置一个Null对象到缓存中，程序从缓存中获取为Null时则直接返回，不再从数据源查询。但是这样需要考虑数据源数据生成或恢复以后，缓存中的NullObject需要更新的问题，更新数据库的同时需要更新缓存。
- 业务侧最好能对查询的key做下预校验：比如订单信息查询，订单编号作为key，数字类型的订单编号至少不能有字符，对于订单编号的规则校验也能防止穿透的可能。

### 【建议】：防击穿

key对应的数据在数据源中存在，但在缓存中过期，若突然有大量并发请求过来，请求判断缓存没有会从数据源加载并塞回缓存，高并发可能会瞬间把数据源负载提到很高，如果加载的sql性能不高可能还会把数据源拖垮。

**应对策略**：

- 缓存数据不设置过期时间，当数据源中的数据更新后，由专门的应用进行缓存数据更新
- 采用L1（一级缓存）、L2（二级缓存）两级缓存机制，L2缓存失效时间设置比L1长，当请求基于L1缓存查询未命中时，则进行加锁处理，并且让当前请求线程获取到锁，然后线程同时从数据源中获取数据加载到L1、L2两级缓存中，其它线程依旧可以从L2缓存中获取数据。

### 【建议】：防雪崩

一般存在于缓存服务器重启或大量缓存集中在某一个时间段失效，这样会瞬间造成数据源端的超高压力，所有缓存请求都打到数据源上。

**应对策略**：

- 设置有效期时不要使用绝对时间而使用相对时间，并且可以在失效时间基础上增加一个随机值，比如1-5分钟随机，避免引发同一时间点集体失效的情况
- 对于过程类临时数据，过期后并不会触发访问数据源，需要避免设置过大的失效时间，浪费内存

# 命令使用

### 【推荐】：O(N)命令关注N的数量

例如`hgetall`、`lrange`、`smembers`、`zrange`、`sinter`等并非不能使用，但是需要明确N的值。有遍历的需求可以使用`hscan`、`sscan`、`zscan`代替。

### 【推荐】：禁用命令

禁止线上使用`keys`、`flushall`、`flushdb`等命令，可使用`scan`的方式迭代渐进式处理。

### 【建议】：Redis事务功能较弱，不建议过多使用

Redis的事务功能较弱(不支持回滚)，而且集群要求一次事务操作的key必须在一个slot上(可以使用hashtag功能解决)

### 【建议】：Lua使用上有特殊要求，不建议过多使用

- **所有key都应该由 KEYS 数组来传递**，redis.call/pcall 里面调用的redis命令，key的位置，必须是KEYS array, 否则直接返回error，"**-ERR bad lua script for redis cluster, all the keys that the script uses should be passed using the KEYS array**"
- **所有key必须在1个slot上**，否则直接返回error, "**-ERR eval/evalsha command keys must in same slot**"

### 【建议】：必要情况下使用monitor命令时，要注意不要长时间使用

- 建议通过**ZCache Manager**缓存库节点的实时监控进行查看

# 集群设置

## 【推荐】：设置合理的用户密码访问

通过设置密码认证，可以控制客户端的访问能力，从而提升系统安全性

另外建议不同集群设置不同的密码，防止应用误配置，导致操作了错误的缓存集群

## 【建议】：根据自身业务类型，设置最大内存使用

可通过设置Redis的`maxmemory`来设置节点的最大内存使用，并通过设置最大内存淘汰策略`maxmemory-policy`，来实现键值的自动剔除。

可选择的**淘汰策略**如下：

- **volatile-lru**：超过最大内存后，在过期键中使用lru算法进行key的剔除，保证不过期数据不被删除，但是可能会出现OOM问题。【默认使用策略】
- **allkeys-lru**：根据LRU算法删除键，不管数据有没有设置过期时间，直到腾出足够空间为止
- **allkeys-random**：随机删除所有键，直到腾出足够空间为止
- **volatile-random**：随机删除过期键，直到腾出足够空间为止
- **volatile-ttl**：根据键值对象的ttl属性，删除最近将要过期数据。如果没有，回退到noeviction策略
- **noeviction**：不会剔除任何数据，拒绝所有写入操作并返回客户端错误信息"**(error) OOM command not allowed when used memory**"，此时Redis只响应读操作

## 【建议】：每个节点使用不要超过10G内存

节点内存占用很大会有很多问题：

- `bgsave`和`bgrewriteaof`要在主线程执行**fork**操作，内存占用越大，执行时间越长，阻塞Redis可能性越大
- 内存占用越大，RDB落盘、网络传输、加载时间都是会较长，对于CPU、网络、磁盘IO的开销也会越大

## 【建议】：每个节点存储键值数控制在3000万

节点存储键值数很大同样存在一些问题：

- 随着存储键值数增多，Redis会进行Rehash处理，可能会瞬间因为申请桶资源而内存大涨
- 键值数太多，对于Redis重启后的数据恢复时间也会增大

# 客户端使用

## 【推荐】：避免多个应用使用一个集群

**正例**：

不相干的业务拆分，公共数据做服务化

## 【推荐】：使用带有连接池的客户端

连接池客户端可以有效控制连接，同时提高效率。

- **最大连接数**：参考应用实例并发线程数，同时需要考虑应用实例的个数，最终计算出来的连接总数不能超过服务端最大连接数
- **最小空闲连接数**：建议不要超过10个，一般默认取值为4个
- **超时时间**：建议不要超过2秒
