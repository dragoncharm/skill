# 处理开发事务单

## 运行原则

- 用户明确批准方案之前绝不修改代码。四个分析阶段本身就是交付物，不是铺垫。
- 每个结论必须基于实际读过的代码或查到的单据数据；推断要标注为推断。
- 审批门禁通过之前，目标项目一律只读。
- 方案与单子体量成比例——小缺陷修复也要走完四个阶段，但每个阶段可以只有几行。
- 实施过程中保留用户的无关改动，全程遵守公司开发规范。
- 引用具体的文件路径和符号，让用户能在编辑器里核对分析结论。

## 工作流

### 1. 查单

从用户请求中识别单号。如果用户只给了标题或关键词，用 `qryApiTaskDtoListByKeyword` 搜索；匹配唯一且上下文一致时直接继续，无法判定目标时才询问。

**快路径——优先用查询脚本。** 在调用 MCP 工具之前，先通过自带的 [scripts/devspace_query.py](scripts/devspace_query.py) 查询单据（路径相对本 SKILL.md 解析）：

```bash
python3 scripts/devspace_query.py basic    <taskNo>   # 核心信息 + 影响说明
python3 scripts/devspace_query.py comments <taskNo>   # 评论 + 状态流转历史
python3 scripts/devspace_query.py impact   <taskNo>   # 影响说明 + 变更说明
python3 scripts/devspace_query.py sql      <taskNo>   # 分支上已提交的 SQL 脚本
```

脚本直连同一个 devspace MCP 网关，剥掉网关每次附带在结果里的约 40KB 字段说明，只输出需要的字段——通过 MCP 工具返回约 50KB 的查询，走脚本不到 1KB。它从 `~/.zcode/cli/config.json` 读取网关 URL 和 Bearer Token，可用环境变量 `DEVSPACE_MCP_URL` / `DEVSPACE_MCP_TOKEN` 覆盖。其他只读需求可用 `raw <toolName> '<jsonArgs>'` 走同样的剥离直通。脚本失败时（无 python3、无配置、网关地址变更）不要阻塞，回退到下面的 MCP 工具。

脚本覆盖不到的内容再用 devspace MCP 工具获取（全部只读，严格按需调用）。每开一个 flag 都会增加响应体积，超限会被截断丢失尾部——只开启当前档位需要的：

| 用途 | 工具与调用时机 |
| --- | --- |
| 类型专用详情（需求单/缺陷单/任务单） | `qryUserStoryApiTaskDtoByTaskNo` / `qryBugApiTaskDtoByTaskNo` / `qryWorkItemApiTaskDtoByTaskNo`——结构与基础查询相同，二选一，不要同时调 |
| HLD/LLD 文档 | `qryApiTaskDtoByTaskNo` 加 `withTaskDoc: true`——大功能单，或描述/评论引用了设计文档时 |
| 处理计划负责人与时间 | `qryApiTaskDtoByTaskNo` 加 `withTaskPlan: true`——仅在需要联系设计/测试/走查负责人或核对截止时间时 |
| 父需求单 / 兄弟任务单 | `qryApiTaskRelationshipDtoByTaskNo` 或 `qryWorkItemListByUserStoryNo`——大功能单，或单子提到关联单时 |
| 特性分支 | `qryTaskBranchByTaskNo`——实施将使用分支时 |
| 已提交的代码变更 | `qryApiTaskChangeContentRespDtoByTaskNo` 传 `withContent: false`（只拿文件清单）；需要时再取单个文件的内容 |
| 已提交的 SQL 脚本 | `qryApiSqlDetailRespDtoListByTaskNo`——仅脚本单 |
| 关联测试用例 | `getTestCasesOfTask`（cloudtest MCP）——已有用例的返工单 |

如果 MCP 响应被截断，不要猜测丢失的尾部内容——减 flag 重查、用 `devspace_query.py raw` 走更窄的工具，或改用 `qryApiTaskFlowStageByTaskNo` 这类小接口。

**信息优先级。** 先提取 `withAction: true` 返回的 `taskActionDtoList` 中 `comment: true` 的评论，区分正式决定、建议和疑问。同一话题中明确修订旧要求的后续决定优先；不要仅凭时间较晚把任意评论当作最终要求。其次参考 HLD/LLD，再参考标题和描述。代码证明当前行为，不自动否决需要改变该行为的需求。

明确的后续决定可以更新旧设计，并说明采用依据。只有无法确定当前有效需求、且矛盾会实质影响方案时才向用户询问；继续完成不依赖该答案的分析。

**操作历史不进工作上下文。** 无论来自脚本还是 MCP 兜底，只把提取出的评论和一行状态摘要带入分析和设计文档；不整段复述操作流水，唯一例外是影响代码位置的分支/模块/负责人变更。

**返工与续接。** 分析之前，先在工作目录找已有的 `<单号>_*_开发方案.md` 设计文档（见第 8 步）。如果单子是返工（`regressionCount > 0`）或续接之前的工作，先读这份文档——增量更新而不是从零重新分析，第一阶段探查也只针对文档写成之后的变化。

在回复开头用自己的话总结需求——单号、标题、当前状态、分支/版本、一段话复述要构建或修复的内容，以及任何改变过方向的评论。如果需求的模糊点会影响设计，把疑问列进方案里，不要默默猜测。

如果 MCP 工具不可用或单号查不到，如实说明尝试了什么并直接向用户索要需求文本；不要编造单据内容。

### 2. 单据分档

根据当前有效需求做初判，再按实际变更范围确定档位。采用评论中的明确处理决定；若要求“脚本单”但实际必须改应用代码，说明不一致并澄清必要的范围变化。在回复开头声明所选档位。

| 档位 | 典型触发条件 | 强度 |
| --- | --- | --- |
| **脚本单** | 修改内容是数据订正、配置变更或纯 SQL 变更，不改应用代码。 | 最轻。四个阶段聚焦目标表和数据，核心交付物是执行、验证、回滚三件套脚本。 |
| **大功能单** | 新能力或大改造：跨多个模块、新接口、表结构变更、新配置。 | 全深度。每个阶段完整执行，调用链、数据模型和回归范围额外加深。 |
| **小bug单** | 影响面窄的小缺陷，只触碰少数代码路径。 | 压缩。每个阶段可以只有几行，但没有任何阶段被跳过。 |

只读 [references/mode-profiles.md](references/mode-profiles.md) 中所选档位的章节——脚本单、大功能单或小bug单（单据混合类型时再加读 混合单据一节）——不要整篇读入。每个章节定义了该档位下各阶段的要求和输出模板。单据混合类型时（bug 修复同时需要数据订正脚本），按主导档位执行，并向脚本单借用脚本交付物。

### 3. 第一阶段——定位影响面（只读）

按所选档位探查目标仓库，仅报告与变更相关的项目：

1. **入口**——需求涉及到的控制器、服务接口、定时任务、消息消费者或 CLI 命令。
2. **调用链**——从每个入口到数据层的路径，点名具体的类和方法。
3. **数据库表**——涉及的表、列和索引；读写它们的现有 SQL/mapper/ORM 文件。
4. **配置**——变更需要读取或新增的应用配置、开关、字典和常量。
5. **现有相似实现**——代码库里最接近的同类实现，引用路径，供风格和结构模仿。

优先用 `rg` 搜索和定点读取，不做穷举式清单；大文件优先读取命中区域及必要上下文；小文件或理解完整控制流时可通读。跳过构建产物和生成代码。

### 4. 第二阶段——修改方案

给出具体方案：

- 设计说明——改什么、为什么，讲到职责层面而不是逐行编辑；
- 涉及文件清单，格式为 `路径 — 改什么`，每项标注修改/新增/删除；
- 数据库变更（DDL、DML、脚本，如有），遵守公司 SQL 规范；
- 配置或开关变更（如有）；
- 明确排除在范围之外的内容。

脚本单在这一阶段的交付物是脚本三件套本身——执行、验证、回滚脚本，规格见 [references/mode-profiles.md](references/mode-profiles.md)——不是代码变更清单。

### 5. 第三阶段——风险分析

根据变更选择适用的风险维度，报告有证据的风险和缓解措施；无关维度可省略：

- **兼容性**——API 契约变更、序列化、存量数据或行、被改接口的其他调用方、回滚路径。
- **事务**——事务边界位置、传播行为、失败回滚、跨服务一致性。
- **缓存**——缓存了什么、失效和过期机制、变更后的脏读窗口。
- **空值**——可空字段、空集合与 null 的区别、默认值、存量数据的 NPE 路径。
- **并发**——幂等性、重复提交、竞态条件、锁范围、乐观/悲观控制。
- **回归**——共享被改代码路径的既有行为，可能被破坏的点。

需要各维度更细的检查清单时，读 [references/risk-analysis-guide.md](references/risk-analysis-guide.md)。

### 6. 第四阶段——测试方案

给出与变更体量成比例的测试方案，按适用性选择以下验证：

- 新增或更新的单元测试（点名测试类和关键用例，含第三阶段暴露的边界和失败用例）；
- 集成或接口验证步骤，给出具体请求示例；
- 针对上述共享路径的回归场景；
- 数据库变更时的 SQL/数据验证；
- 无法自动化时的人工验证步骤，明确标注「未执行」。
- 根据行为变化与风险选择关键等价类、边界和回归用例；复用已足够的覆盖，同类调用方可合并验证。需要更细的边界提示时，仅查阅 [references/closing-documents.md](references/closing-documents.md) 的“边界覆盖要求”。建立一次用例清单，收尾时回填结果，不重新展开分析。

### 7. 审批门禁

首次输出可审查的四阶段方案后，请用户批准；已有当前范围的明确批准时直接续接。首次批准前目标项目只读，可在回复中交付完整方案和脚本草稿。用户要求先分析时以方案交付为止。

结合上下文识别批准：“确认”“按方案做”“你看行就弄吧”等对当前方案的明确肯定或委托均可授权；含义不清且影响是否实施时才询问。

- 批准持续覆盖原范围内的实现细节调整、必要测试修复和等效工具替换，记录实际偏差即可。
- 范围、接口契约、数据风险或外部影响实质变化时，提交变化部分重新批准；继续不受影响的已授权工作。
- 部分批准只覆盖指定项。明确暂停、撤回或缩小范围立即生效。
- 本地实施批准不等于生产执行、破坏性操作、发布或通过 MCP 写单授权。仅在实际需要这些操作且尚未获授权时确认，不重复索取已有的明确授权。

### 8. 方案文档落地

用户批准后、写任何代码之前，把此前已确定的所有内容写入一份 markdown 设计文档，模板见 [references/design-doc-template.md](references/design-doc-template.md)：

- **文件名**：`<单号>_<标题>_开发方案.md`——单号、下划线、做过文件系统安全处理的单子标题（`/ \ : * ? " < > |` 和换行替换为 `-`，超长标题截断），再加 `_开发方案`。示例：`12012113_V9L-哥伦比亚ETB-月账单DIAN集成优化-BM拆单_开发方案.md`。
- **位置**：当前工作目录，除非用户指定其他位置。
- **内容**：单据摘要（含关键评论）、影响面、修改方案（脚本单为完整的执行/验证/回滚脚本文本）、风险分析、测试方案——外加实施记录、规范检查、静态检查、收尾文档的占位章节，由后续阶段回填。
- 工作推进过程中持续更新这一份文档，不要每个阶段另开新文件。它是这张单子唯一的完整开发记录。

### 9. 实施

获得明确批准后：

1. 加载并遵循 `apply-iwhalecloud-dev-standards` skill 做所有编码决策。
2. 严格按批准范围实施；发现需要扩大范围时浮出来讲，不许悄悄膨胀。
3. 贴合周边代码风格，参照第一阶段找到的相似实现。
4. 改动保持最小且连贯；不重构范围外的存量违规。
5. 补充或更新第四阶段的测试。
6. 在有意义的阶段完成时，更新设计文档的「实施记录」章节——做了什么、与批准方案的任何偏差。

### 10. 开发完成后复查

报告完成之前：

1. 重读完整 diff，逐个变更文件对照批准方案和公司规范核对。
2. 由本流程统一安排与行为变化相关的测试、构建和静态检查；复用相同代码、配置和环境下已完成的结果，相关变更后只重跑受影响的检查。
3. Java/JavaScript 变更需要公司预检时，加载 `precheck-company-lint` 并传递本次变更的检查与修复范围。SQL 按对应公司规范审查，有项目 SQL 检查工具时再执行；区分规范审查与工具扫描。纯 SQL 单不加载不支持 SQL 的预检 skill。
4. 把结果回填设计文档：实施记录（实际改了什么、与方案的偏差）、规范检查记录（引用了哪些公司规范文档及复查结论）、静态检查记录（运行的工具、修复的问题、未运行的检查及原因）。
5. 如实报告：改了什么、哪些检查跑了、结果如何、哪些检查没跑以及为什么。

### 11. 起草收尾文档（自测说明和影响说明）

复查通过后，起草研发云单据流程在开发完成时期望的两份文档：

1. **自测说明**——开发视角的测试用例，记录实际验证过什么，并回填测试方案中选定的适用边界；未执行的用例必须明确标记，不能写成通过。
2. **影响说明**——修改内容、业务影响、其他项目影响，中英文各一份。

严格遵循 [references/closing-documents.md](references/closing-documents.md) 中的字段结构和内容风格——该格式取自真实提交过的单子。

两份都作为草稿交用户审阅，并附到设计文档的收尾章节，使文档成为完整记录。除非用户明确要求提交，否则不得通过 MCP 写入任何单子（如 `addTaskImpact`、`addAndRelaTestCase`）。复用已有格式，不为模仿格式额外查询其他单据。已有明确提交授权时按其范围执行，不再次索要同一授权。

## 四阶段的输出格式

按单据档位使用该档位章节中定义的输出模板（见 [references/mode-profiles.md](references/mode-profiles.md)）——同一结构将成为设计文档的第一至五节。

## 失败与歧义处理

- 单据查不到时，说明尝试了什么，向用户索要需求文本。
- 区分预期行为与现有行为；只有无法确定有效需求且影响方案时询问。
- 分析发现多个可行设计时，推荐一个并简短注明备选，不做全景式罗列。
- 已批准步骤受阻时，尝试不改变范围或风险的可用替代方式并记录；仍受阻则报告原因，继续独立的已授权步骤。
