# 档位说明（Mode Profiles）

事务单工作流的分档要求。单据分档后（见 SKILL.md），按所选档位的说明执行。四个阶段和审批门禁对所有档位都生效，变化的是深度和交付物的形态。

## 脚本单

变更完全在数据或 SQL 脚本层面：数据订正、通过表实现的配置、数据回填、清理或 DDL，不改应用代码。如果必须同时改代码，就不是脚本单。

### 第一阶段——定位影响面

- 确定具体的表、列、索引，以及圈定受影响行的 WHERE 条件。
- 找到读取相关列的代码或任务，确认它期望的取值（枚举码、可空性、格式）。
- 用 `qryApiSqlDetailRespDtoListByTaskNo` 检查同单已提交的脚本，已有的不要重复生成。
- 给出预估影响行数，以及已有多少行本来就处于目标状态。

### 第二阶段——修改方案：脚本三件套

按以下顺序交付三个脚本，每个都可独立执行：

1. **执行脚本**——实际变更。遵守目标数据库引擎的公司 SQL 规范。大批量更新使用带显式提交点的分批语句，不要用一个巨型事务；说明批量大小和预计时长。
2. **验证脚本**——证明变更正确且范围可控的查询：
   - 执行前查询：执行脚本将会触碰的行的数量和样本（先执行它确认范围）；
   - 执行后查询：显示行已进入目标状态的数量和样本，以及无误伤的查询。
3. **回滚脚本**——恢复变更前状态：
   - UPDATE：从执行脚本自建的备份恢复（例如先把受影响的行连同主键 `CREATE TABLE ..._bak_YYYYMMDD AS SELECT`，再从备份表还原）；
   - INSERT：按插入时的确切主键删除；
   - DELETE：从备份表重新插入；
   - 不可逆 DDL（DROP COLUMN、TRUNCATE）：明确声明无法回滚并说明重建需要什么——不许悄悄省略回滚脚本。

如果回滚脚本依赖的备份不是执行脚本创建的，反过来修执行脚本，让它创建。

### 第三阶段——风险分析

按脚本实际行为选择适用风险，重点看：

- 大表或热表的锁范围和持锁时长、分批大小；
- 预期行数与实际的偏差（验证脚本就是防线）；
- 被写入或用作条件的列里的空值/空串；
- 执行期间触碰相同行的并发写入方；
- 回归：相同列或编码的其他消费方；
- 兼容性：DDL 之后存量数据形态是否破坏现有查询。

### 第四阶段——测试方案

- 执行顺序本身：执行前验证查询 → 执行脚本 → 执行后验证查询 →（失败时）回滚脚本 → 再次执行前验证查询。
- 条件允许时，建议先在具备生产级数据形态的测试环境演练。
- 边界矩阵至少覆盖：命中 0/1/N 行、预计数量上下限、空值/空串、重复键和重复数据、已是目标状态、批次首/中/末批失败、并发写入、脚本重复执行的幂等性、回滚后数据复原以及误伤范围；适用场景全部写入自测说明。

## 大功能单

新能力或大改造：跨多个模块、新接口、表结构变更、新配置或新开关。这是默认的全深度档位；SKILL.md 的整体流程即按此档位设计。

### 第一阶段——定位影响面

基础要求之外，还要：

- 映射**全部**入口，不只是主入口（API、定时任务、消息消费者、管理页面）；
- 追踪跨模块、跨服务边界的调用链，标出 RPC/HTTP/MQ 的过渡点；
- 列出新增或修改的表，细到列级，并说明索引影响；
- 找到最接近的同类实现；存在设计分歧时再比较第二个，并说明选用理由；
- 识别项目现有的配置或开关模式并模仿。

### 第二阶段——修改方案

- 先讲清职责和数据流层面的设计，再给文件级变更清单。
- 把实施拆成有序、可独立验证的步骤（如 表 → 数据访问 → 服务 → 接口 → 配置），让评审和测试可以增量推进。
- 每条表结构变更 DDL 都配上回滚语句。
- 如果项目使用开关，指明控制新行为的开关或配置项。

### 第三阶段——风险分析

按受影响的维度深入分析；需要细项时查阅 [risk-analysis-guide.md](risk-analysis-guide.md) 的对应章节，另按适用性考虑：

- 存量行的明确迁移或兼容策略；
- 跨服务变更的上线与回滚顺序；
- 新查询或新索引对大表的容量/性能影响。

### 第四阶段——测试方案

- 用必要的单元测试覆盖变化的成功、边界和失败行为，复用已有覆盖；
- 从入口到持久化的端到端集成测试；
- 共享代码中不同调用契约的代表性回归场景；
- DDL/回填的数据验证；
- 人工验证步骤，明确标注未执行。
- 需要细项时参考 [closing-documents.md](closing-documents.md) 的边界提示；在既有测试清单中记录选定用例，实施后回填结果与证据。

### 实施注意

- 按第二阶段的有序步骤实施，保持每一步可编译、可测试。
- 本地设计文档按主流程维护；仅在用户要求外部登记时使用 devspace MCP，按已有授权执行。

## 小bug单

影响面窄的缺陷：少数代码路径、局部影响、不改表结构或接口契约。如果修复过程中发现范围比这更大，切换到大功能单档位并明确说明。

### 第一阶段——影响面定位（压缩）

- 包含缺陷的入口和最小调用链；
- 精确到文件和行号的根因；
- 谁还在调用这段有缺陷的代码——这就是回归范围。

### 第二阶段——修改方案（压缩）

- 一段话修复说明 + 文件清单，格式 `路径 — 改什么`。
- 如果该 bug 同时需要数据订正，附上脚本单的脚本三件套。

### 第三阶段——风险分析（压缩）

仅报告与缺陷相关的风险，重点判断：

- **回归**：第一阶段识别的其他调用方，可能观察到行为变化；
- **空值/存量数据**：缺陷是否涉及存量行可能违反的数据形态。

其余无关维度可省略。

### 第四阶段——测试方案（压缩）

- 一个复现 bug 的定向用例（改前失败、改后通过）；
- 对不同调用契约选取代表性回归检查，同类调用方合并验证。
- 补充行为变化涉及的关键边界；保留能捕获缺陷和回归的最小充分用例集。

## 混合单据

一张单子既需要改代码又需要独立脚本（如 bug 修复 + 数据回填）时，按主导档位组织叙述，并把脚本单的脚本三件套作为独立交付物附在第二阶段（含验证和回滚脚本）。审批门禁同时覆盖两者。
