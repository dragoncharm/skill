# 风险分析指南

事务单工作流第三阶段的分维度检查清单。某个维度可能被触碰时就读对应章节；完全无关的维度直接跳过。

## 兼容性

- 被修改的方法签名、请求/响应字段或消息格式是否改变了契约？列出所有外部调用方和消费方。
- 存量数据行能否满足新逻辑？考虑变更之前写入、从未迁移过的行。
- 变更发布后如需回退，有没有回滚路径？新行为是否由开关控制？
- 枚举值、字典编码或常量的扩展，旧客户端能否解析？
- 其他分支或版本是否共享这个接口（如 Trunk 与主分支的合并）？

## 事务

- 相对于新增写入，事务边界在哪里？必须原子化的写入是否都在边界内？
- 事务内的远程调用（RPC、HTTP、发 MQ）会不会长时间占用连接，或回滚时造成不一致？
- 被调服务的事务传播与预期边界是否冲突？
- 每个失败点（部分写入、超时、重试）分别会发生什么？
- 跨服务或跨库的步骤，最终一致性是否可接受？如何对账？

## 缓存

- 变更读取或失效了哪些缓存实体或查询结果？
- 写入时缓存是失效、更新还是删除？与代码库其他地方对同一实体的处理是否一致？
- 有没有脏读窗口？消费方能否容忍？
- 新增缓存键是否设置了过期时间和容量上限？
- 失效后的热键会不会发生缓存击穿？

## 空值与空集合

- 哪些新增或被改字段可能为 null？为 null 时代码会做什么？
- 空集合与 null：代码是否区分两者？调用方期望哪一个？
- 有没有存量数据会踩中的 `Map.get`、自动拆箱、链式 getter、对 null 求流等 NPE 路径？
- 配置缺失、字典项缺失时默认值是什么？
- SQL 查询空结果流进新代码路径后的行为是否正确？

## 并发

- 同一请求会不会到达两次（重试、重复提交、消息重投）？操作是否幂等？
- 有没有需要加锁或改原子更新的「先查后改」序列？
- 锁的范围和预计持锁时长？与其他加锁顺序会不会死锁？
- 计数器、序列号生成、批量更新是否需要乐观版本号或行锁？
- 定时任务或多实例部署会不会并发执行新逻辑？

## 回归

- 哪些既有行为共享被修改的代码路径？点名依赖它们的功能。
- 是否有调用方依赖当前的边界行为（异常类型、顺序、默认值）而会被改变？
- 现有哪些测试覆盖被触碰的代码？它们是否仍编码着预期行为？
- 其他位置的相似实现是否依赖被修改的共享辅助代码？
- 能捕获此处破坏的最小回归场景集是什么？

## 清单的使用方式

每条有价值的发现都要说明风险、具体代码位置和缓解措施（已在方案中，或建议补充进方案）。不要罗列没有代码级证据的泛化风险——没有位置的风险就是猜测。
